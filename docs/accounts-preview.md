# Isolated account preview acceptance

The preview origin is `https://preview.crykit.lasers.app`, independently of production. Its concrete source configuration selects the production service entry and isolated preview storage, with account, signup and email gates disabled and no maintenance schedule. Sender, Access and recovery-policy settings remain absent until qualified. Configuration is not evidence that a serving deployment has changed. The [disabled example](../wrangler.accounts.example.jsonc) does not provision or activate anything. Keep guest use and hash routes reachable without account or administrator authentication.

## Evidence and remaining hosted gates

A read-only provider observation on 2026-10-15 found `crykit-preview` serving assets only, with no service bindings, handlers or schedules; its sole Custom Domain was the preview origin, and workers.dev/provider previews were disabled. This is historical placement evidence, not account readiness or a live launch claim. Refresh exact resource identities before any write. No source documentation receipt, local captured mail or simulated identity establishes hosted authority.

Isolated storage preparation on 2026-10-16 created the preview metadata database, a separate closed restore-staging database and distinct objects, backups and revocation-ledger buckets. Both databases received the ordered authored migrations. Live bucket inspection found public development URLs disabled and no custom domains. Their default lifecycle rule aborts incomplete multipart uploads; it does not expire stored managed objects. The concrete production-entry bundle passed a local Wrangler dry run with all account effects disabled. These observations establish preparation only; they do not establish a hosted account deployment, credential restoration, recovery admission or enabled administration/email.

On 2026-10-18, a candidate with complete successful local publication verification was deployed to `crykit-preview` using the production service entry and isolated preview bindings. Provider inspection confirmed the preview Custom Domain, disabled workers.dev/provider previews, empty maintenance schedule and unchanged production deployment. Account, signup and email gates remained disabled; the account API returned `SERVICE_UNAVAILABLE` with `Cache-Control: no-store`. Live browser checks covered guest Build persistence, prepared offline reload with blocked uncached network requests, exact original save downloads, edited save exports and mobile light/dark layouts. TLS, preview identity, no-index headers and absent analytics injection were checked at the public origin. These checks establish the closed preview deployment and guest journeys; hosted account, administrator, sender and recovery qualification remain separate gates below.

The history-navigation proof checks key retirement on every browser project. Chromium exercises an actual cached document with BFCache enabled. The pinned Playwright Firefox and WebKit builds disable BFCache in their [Firefox configuration](https://github.com/microsoft/playwright/blob/main/browser_patches/firefox/preferences/playwright.cfg) and [WebKit inspector patch](https://github.com/microsoft/playwright/blob/main/browser_patches/webkit/patches/bootstrap.diff), so those projects verify a fresh document with the previous key inaccessible. These results do not establish native Firefox or Safari BFCache behavior.

Email headroom, sender stored-preview state, suppression configuration, Zero Trust seat/MFA eligibility, hosted resource limits and provider restore promotion are explicit live unknowns until recorded by the deployment owner. Keep the corresponding gates closed; do not repeatedly guess undocumented provider endpoints. A service with backup capture visibly paused can exercise independently qualified preview features without claiming daily recovery.

## Local artifact and runtime evidence

Use `node --test scripts/accounts-deployment.test.mjs`, `node --experimental-strip-types --test scripts/offline-plugin.test.mjs`, `npm run test:worker -- worker/runtime.test.ts`, `npm run check:privacy`, `npm run build` and `npm run check:assets` for the focused packaging contracts. The missing-setup test calls the actual production entry repeatedly and preserves guest assets without creating account setup. The build excludes local fixtures and unsafe cache routes; `/api/v1/account`, `/api/public/v1/shares/id` and `/admin` never use the static service-worker cache. The named-environment example uses distinct placeholder identities and disabled activation. These checks do not certify substituted live bindings.

The browser build retains large catalog, rules and artwork-related resources. Attribute each final warning to actual emitted artifacts against its baseline; keep the normal warning threshold. Dynamic imports that also have static consumers do not create isolation. In particular, account password crypto must remain lazy behind account use; a cold guest must survive a failed crypto load. Read local timing and source/bundle evidence together without treating emitted size as initialization or hosted CPU proof.

Earlier full-workspace map-editing measurements observed about 17.7 seconds from the final descendant edit to fully clean hydration, roughly 8-12 seconds for individual local map work and about 33 seconds for a small remote fixture. These measurements predate incremental managed local saves and do not describe their ordinary-save boundary. The [local-save acceptance producer](../e2e/local-save-performance.spec.ts) measures request through durable acknowledgement and a usable next edit separately from bulk opening, background projection and cloud publication, including repeated edits with larger unrelated data and an active mapper. The earlier measurements remain workload observations with retained failures, not maximum-size, cross-browser or hosted promises. Preserve exact descendants, invalid drafts and original/history equality when measuring. Do not weaken assertions, skip closure validation or reset a per-command budget to conceal unfinished work.

Final composed/publication verification owns the full `npm run verify` under the shared coordination lock. Hosted acceptance then records actual provider behavior separately. Reuse passing checks on unchanged inputs, and preserve existing runtimes and databases while gathering new evidence.

## Deployment and recovery review

Follow [deployment preparation](accounts-deployment.md) and [capacity policy](accounts-capacity.md). Record the reviewed source/build, dry run, exact destination resources, migration outcome, secret-restoration result, Access coverage and each capability's enabled/paused state before activation. Deployment commands remain inactive until correct bindings and Access are verified. Never infer production activation, public upload approval or message permission from isolated preview authorization.

After a qualified deployment, check the visible preview identity, TLS/no-index/no-analytics behavior, guest editing, exact account workflows and private API no-store behavior through the actual origin. Keep any unsupported feature explicitly unavailable. For failure, pause cloud effects while retaining compatible local/guest access, and use [closed staged recovery](accounts-recovery.md). Do not roll back persistent schemas, repoint established devices to an uncertified ledger, delete protected history or rotate original secrets as a shortcut.
