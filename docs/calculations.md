# Calculation package

Crystal Kit's numeric character and combat calculations use versioned JSON rules and data. The [human-readable equivalent](calculation-reference.md) includes a stat overview, worked periodic-effect examples, equations, input contracts, and ordered stages generated from those rules. The package is available from **Export calculation package** on the character and Build calculation panels, or without a game installation:

```sh
npm run calculations:export -- --output calculations.json
npm run calculations:check
```

Running `node scripts/export-calculations.mjs` without an output option writes JSON to stdout. The export contains no saves, character observations, inventory, personal definitions, installation paths, or credentials. It can be consumed offline in another language or application. It contains factual numeric projections and arithmetic rules, not the game's executable, textures, descriptions, or decompiled source files. These projections do not grant rights to the original game assets.

## Contents and evidence

The `crystal-project-calculations` format defaults to `schemaVersion: 3`, with package ID `pc-1.6.9-package-v3`. The [version 3 JSON Schema](../src/calculations/package-v3.schema.json) describes its structure and combat expression grammar. The saved character model remains `pc-1.6.9-v1`; the combat module has its own ID, `pc-1.6.9-combat-v1`. Exported sections are:

| Section | Purpose |
| --- | --- |
| `rules` | Formulas, integer steps, rounding, caps, ordered sheet stages, modifier tags and scopes, gender identities, benchmark assumptions, and coverage |
| `data` | Job ratings and innate IDs, equipment and passive modifiers, gender bonuses, ability coefficients and costs, status modifiers, balance patches, and battle configuration |
| `verification` | Synthetic input/output vectors from compiled, unchanged methods extracted from the inspected executable, with evidence describing the probe |
| `combat` | Executable arithmetic for every native Calculator method not supplied by the character module, plus periodic effects, costs, random resolution, resource application, threat, difficulty, and rewards |
| `combatData` | Numeric monster/difficulty/status records and mode patches, native enum identities, source digest, and checksum |
| `combatVerification` | Independent compiled-native vectors, source hashes, and audited Calculator method inventory; each case's `input` indexes the shared `values` array |
| `previewVerification` | Native coefficient-power and hit-curve vectors plus learning-arithmetic checks, with direct input arrays and source fingerprints |
| `example` | An explicitly synthetic complete actor, recipient, ability, and battle-context fixture |
| `modifiers` | Native neutral defaults, scalar modifier operations, source-group aggregation evidence, and source hashes |
| `modifierVerification` | Synthetic vectors from unchanged compiled native modifier application and group merging, including negative values, scaling, and identity-specific lists |
| `enemy` | Preserved source evidence and constants for the difficulty-adjusted bestiary inputs |

Version 3 contains native-backed calculation models and the effective modifier aggregation used by battle scenarios. Existing consumers can request the unchanged [version 2 shape](../src/calculations/package-v2.schema.json) with `--schema-version 2`, or the [version 1 shape](../src/calculations/package-v1.schema.json), including its historical `legacy` section, with `--schema-version 1`. Community-guide estimates remain excluded from the default export and readable reference. Export format selection does not migrate saved plans. Battle scenarios use their own explicit versioned saved inputs.

The browser loads the package export module when exporting; the calculation panels also use its bundled native numeric rules. Offline preparation caches that module alongside the application, so a first export also works after an offline reload. Export errors remain visible with recovery instructions: save pending edits, restore the connection, and reload before retrying a failed module load. The [package API](../src/domain/calculation-package.ts) provides all supported versions without changing the original character-rule API.

The [PC rules](../src/calculations/pc-1.6.9-v1.json) identify the inspected executable by SHA-256 and name the relevant methods. [Numeric data](../src/catalog/native-stats-v1.json) is a generated projection of the [shared native game snapshot](../src/catalog/native-game-data.json), which supplies the catalog's base facts. Routine checks regenerate the projection in memory and reject drift from that shared source. The export records its source digest, database hashes, identity sources, and a checksum. Native catalog records carry explicit identities, and reviewed catalog bindings attach canonical base IDs to native database IDs with evidence. The pinned crosswalk establishes item and job identities. Additional passive bindings require the wiki's explicit owning class, membership in that native job's passive list, a normalized label, and the exact innate flag. Starter records with the same kind and normalized label receive the same reviewed binding. Foreign catalogs and similarly named personal definitions do not inherit these bindings.

The original Windows installation supplied PC 1.6.9.0. The compared macOS build has matching calculation code and numeric data; see [verified platform coverage](platform-coverage.md). Ordinary calculation claims use the shared game version, while executable fingerprints retain their original extraction platform. This does not establish Nintendo Switch, randomized, or modded parity. Imported Crystal Edit numeric records can supply their own ratings and modifiers; unavailable innate references and unsupported numeric effects remain unresolved. The Standard, Vanilla, and Chaos selections apply the corresponding inspected database patches. They do not infer additional runtime configuration.

Bestiary previews select Game mode (Standard, Vanilla, or Chaos) independently from Difficulty (Easy, Normal, or Hard). They use the selected mode's native enemy override by numeric ID, inheriting the base record only when that patch leaves the ID unchanged, and apply the corresponding difficulty definitions. [Enemy arithmetic evidence](../src/calculations/enemy-difficulty-v1.json) pins the inspected `BattlerMonster.RecalcBaseStats` and `RecalcEquipStats` source file to the same executable. HP/MP use boss or ordinary-enemy rates; attributes and physical attack/defense and magical defense inputs use their recorded rates. Integer division truncates before HP/MP rounding. Only changed HP/MP are rounded: values below 100 round to multiples of 5 with an offset of 2, and values at least 100 round to multiples of 10 with an offset of 5. Unmodified values, rewards, and unrelated combat ratings are retained. Unsupported source scopes, missing inputs, conflicting inputs, and overflowing integer arithmetic remain unresolved. These are difficulty-adjusted inputs before other stat modifiers and battle effects, rather than a full encounter simulation. Original fields from the selected record remain in Technical details. The URL retains the native record identity, `mode` selection, and native `difficulty` ID, where Normal is 0, Easy is 1, and Hard is 2. Preview selection leaves saved Game Setups unchanged. Changing a personal version to a mode with a different record opens that catalog record and preserves the personal version.

## Arithmetic format

An expression is a numeric literal, a variable-name string, or an array whose first entry names an operation. For example:

```json
["trunc", ["div", ["add", ["mul", "rating", "level"], "growth"], 2]]
```

This is the integer growth seed `(rating * level + growth) / 2`. A formula declares ordered `inputs`, optional named `steps`, and a `result`. `call` supplies arguments in the called formula's declared input order. Each step can use earlier variables and replaces its own named variable when applicable. `sheetStages` run in order against `stat.*`, `percent.*`, `tag.*`, `context.*`, and `config.*` variables. Every numeric sheet formula and its ordering live in the rules data; the evaluator supplies arithmetic primitives and resolves records and loadout context.

| Operation | Behavior |
| --- | --- |
| `add`, `mul` | Fold at least two arguments from left to right |
| `sub`, `div`, `pow` | Two arguments; division by zero and nonfinite results are errors |
| `min`, `max` | At least two arguments |
| `trunc` | One argument, truncated toward zero |
| `roundEven` | One argument, rounded to nearest integer with midpoint ties to even, matching `Math.Round` |
| `floor`, `ceil` | One argument; round toward negative or positive infinity, respectively |
| `lte` | Two arguments; returns numeric 1 or 0 |
| `eq` | Two arguments; returns numeric 1 for equality or 0 otherwise |
| `and` | Two arguments; returns 1 or 0 with short-circuit evaluation |
| `if` | Condition, true expression, false expression; evaluates only the selected branch |
| `call` | A formula name followed by its arguments |

Use IEEE-754 doubles and preserve the expression's operation order. Integer divisions appear explicitly as `trunc(div(...))`; do not combine or move rounding steps. Native integer products are verified over ordinary character and game-data inputs, not arbitrary values that overflow the game's signed integer arithmetic. Missing variables, invalid operations, nonfinite values, division by zero, and evaluation-budget exhaustion produce unresolved calculations. Depth and operation limits are part of the rules. The [reference evaluator](../src/domain/calculation-rules.ts) uses a finite operator list; it does not use `eval`, `Function`, or imported code. Crystal Kit evaluates only its bundled arithmetic data and never executes imported descriptions or formula packages.

The combat module extends this syntax with explicit booleans/null, own-property paths, comparisons, collection operations, requirements, checked signed-integer intermediates (`i32`), and single-precision rounding (`f32`). Its `operators` section defines the argument order and semantics, including lexical `find`, `sum`, and `fold`. Formula `requirements` run before its sequential steps. See the [combat interpreter](../src/domain/combat-expression.ts) and [bundled-rule API](../src/domain/combat-calculations.ts). `calculateCombat(name, inputs)` returns the result; `traceCombat(name, inputs)` also returns ordered, formula-qualified intermediate steps. This preserves outputs such as `damageModifiers.mpShieldReduction`, which the game applies separately to MP.

For example, `calculateCombat('periodicHP', [1000, 15, 0, 100, 100, 100, 100, 100, false])` returns 135. The arguments are max HP, combined percentage rate, combined flat amount, percentage-damage multiplier, DoT multiplier, periodic-healing multiplier, Vitality, Spirit, and recovery suppression. A negative rate represents regeneration. Formula inputs and notes are exported and rendered in the human reference.

## Sheet inputs and order

Growth history sums each allocated class rating multiplied by its assigned levels. Allocations must total the player level, including level 1. The equipped primary class also supplies the current job rating. Gender bonuses apply before base-stat rounding. Neutral, male, and female totals each run through the complete sheet pipeline, so their differences include rounding and derived effects on accuracy, evasion, penetration, critical values, and turn time.

Choose **Calculation gender** on the loadout's stat overview to apply a profile in its Total, derived stats, and damage benchmarks. An unspecified gender displays a labeled no-bonus preview while preserving the separate comparisons. In the native baseline, Male boosts HP, Spirit, and Luck; Female boosts MP, Agility, and Speed. The versioned formulas apply their level-dependent bonuses before integer rounding and the rest of the sheet pipeline. Model-less plans use the same native formulas. Retained custom per-stat bonuses remain explicit unsupported assumptions.

Enabled mod records can replace those gender flags and add named profiles to the selector. Their selected Total, growth, derived stats, contributions, and benchmarks use the effective flags with the same native formulas. Incomplete profiles remain unresolved without removing neutral or other complete comparisons. The exported native package stays a baseline arithmetic reference; it does not embed a user's configured mods. See [mod calculations and their boundaries](mod-calculations.md).

The overview columns are **Base**, **Equipment**, **Level**, **Gender**, and **Total**. Base is the level-1, unequipped, no-gender value with the primary class assigned to level 1. Level is the difference between that baseline and the saved level and growth history. Equipment is the neutral loadout total minus its base value, including equipped passives, class innates, percentage modifiers, caps, and enabled scenario status and turn modifiers. Gender is the selected loadout total minus the neutral total, after the complete calculation pipeline. The PC columns sum exactly to Total, including modifiers that depend on level and gender; they describe net contributions rather than changing the game's calculation order. An effect lost to a cap contributes zero to the final difference.

Equipment, class innates plus equipped passives, and active statuses accumulate modifiers in separate native groups. Flat and additive percentage fields add; multiplier fields truncate each multiplication within a group and again when combining the groups. Ability-specific cost modifiers add by numeric ability identity; ability damage and element modifiers multiply by identity. Native neutral values come from `BattlerStats.Clear`, rather than the synthetic example fixture. Per-level modifiers truncate before accumulation. Resting per-turn modifiers use zero turns. Turn-time multipliers truncate within each group and when combining groups. Primary-class innates apply automatically; the explicit sub-job innate effect adds the selected secondary class's innates. Paired-equipment bonuses follow the inspected same-ID hand and accessory checks. A physical copy shared between hand slots counts once.

The ordered stages apply unarmed Strength, core percentage bonuses, HP multiplication, unarmed Attack, derived bonuses, equipment-stat percentages, special overrides, Two-Handed and Dual Wield, and final caps. DEF and RES come from equipment and modifiers; VIT and SPI additionally matter in defense reduction. Crit bonus damage is the extra percentage on a critical hit. AP is maximum capacity, not the character's accumulated battle AP.

Unknown equipment observations, unknown passive lists, unmapped selected definitions or equipment roles, incomplete growth, and unrecognized numeric tags keep affected totals unresolved. Known modifiers with unavailable inputs invalidate only their affected fields and dependent stages. Automatic statuses leave resting totals available and appear as excluded battle effects. An explicit battle scenario can include selected active statuses and eligible automatic statuses. Base growth remains visible when known. Equipment legality and learning remain separate checks; a mathematical loadout total does not establish that a character can equip or use it.

## Damage scope

The physical benchmark uses base power 0, Attack rate 100, and Strength rate 100. The magical benchmark uses base power 100, Attack rate 0, and Mind rate 100. Both use a synthetic target with DEF/RES 100 and VIT/SPI 100. They preserve native integer steps and the inspected single-defense reduction formula. They show the consequences of stat changes without simulating an encounter.

The benchmark formulas use the selected calculated stats, including stat changes from an enabled battle scenario. They exclude additional damage-stage modifiers, elements, critical hits, and variance. The separate `combat` module supplies hit/crit chances, full deterministic ability damage, ordered modifiers, HP-dependent defense, elements, variance/Luck, returns, status chance/duration, costs, DoT/regeneration, resource arithmetic, threat, difficulty, EXP/JP, and escape/steal arithmetic. Its `coverage.calculator` maps the audited native method inventory to the owning formula module. The two native steal overloads correspond to `stealChance` and `combinedStealChance`; the latter describes the display, not the sequence of actual rolls. [Steal mechanics](steal-mechanics.md) provides additional source context.

## Battle scenarios and effective costs

Builds, character calculation snapshots, and read-only shares use the same effective source aggregation. **Effective ability costs** applies equipment, class innates, equipped passives, and selected scenario statuses to HP amounts, MP/AP costs, CT delay, and cooldowns. Base parameters remain visible for comparison. Missing core growth does not hide independently calculable MP or AP costs. The calculator includes ability-specific cost adjustments, native multipliers and flat adjustments, and applicable minimum-cost behavior.

Choose **Add battle scenario** to save an explicit snapshot with separate actor and target turn counts, active actor and target statuses and their remaining counts, optional automatic battle-start statuses, current resources, repeat count, threat relationships, and prior status applications. Select a native or supported mod monster, or the actor, as the recipient. Effective monster stats include the pinned difficulty and enabled modifiers. The panel evaluates target-aware damage and healing before variance, critical amounts, hit and critical chances before Luck, variance amounts, periodic resource effects, and status-application chances and durations. It retains the coefficient-only and base hit-curve stages as separately labeled reference values.

Automatic battle-start statuses require known applicable conditions. Immunity, status category immunity, application history, life state, chance, and duration can prevent or leave inclusion uncertain. A random application or a finite status whose remaining lifetime cannot be derived from the snapshot requires explicit active-status selection; only affected calculations become unknown. An automatic status with no numeric effects does not invalidate independent totals. Selecting an active status states that it is active in this snapshot; remaining counts matter only to calculations that consume them.

A scenario is an explicit state snapshot, not an encounter simulator. It does not roll random outcomes, schedule actions or reactions, derive a complete status lifecycle, enforce target legality or ownership, or automatically execute source descriptions. On-application and removal events, cover/reflection, survival effects, actual resource payments, and action-history transitions remain runtime boundaries. Current resource values and threat relationships are supplied assumptions, never reconstructed from the exported synthetic example. The package also exposes lower-level arithmetic for callers supplying explicit random draws: percent rolls must be integers 1 through 100, variance rolls 0 through 200, and the number of full variance draws must match the supplied Luck factor.


## Compatibility and maintenance

New Build plans and edit drafts for checkpoints without calculation inputs default to level 60, Standard PC rules, and all growth in the primary class. Opening an editor does not write that draft into the saved checkpoint; saving creates a new revision. Untouched growth follows primary-class and calculation-level changes. Editing a class allocation, amount, or row switches to manual mode. Manual allocations survive class and level changes, including an over-budget level decrease, until the user corrects them. **Follow primary class for all growth** explicitly restores automatic tracking. Sliders retain the full level scale and clamp increases to the shared remaining allowance.

The planner treats PC versions 1.6.6 and 1.6.6.0 as calculation-compatible with the native 1.6.9 rules under a maintainer-approved assumption. This assumption does not establish independently verified version parity or Switch parity. Unsupported versions and platforms retain explicit calculation blockers without changing the saved Game Setup.

When totals cannot be calculated, the interface explains the blocking input and omits entirely unavailable tables and columns. Known base components and recorded character values remain visible. Build editors offer **Review Game Setup** for setup blockers; incomplete growth and unknown calculation levels retain their editable controls. Read-only shares keep their saved assumptions and show the same diagnostic without mutation controls.

Character calculation assumptions are saved in new immutable snapshots alongside unchanged observations. Calculation level does not rewrite recorded level, and calculated totals never replace recorded totals. Build checkpoints, cloning, comparison, backups, and offline use preserve the model and growth mode. Plans without a model use native arithmetic when their numeric source records are supported, preserving their manual allocation and stored fields. Custom per-stat bonuses and legacy active-status selections remain saved and unresolved until explicitly cleared or, for statuses, adopted into a battle scenario. Adding a scenario does not reinterpret or discard the retained legacy selections; the separate adoption action copies them into its active-status list. Plans without `battle` retain resting semantics. Battle inputs use `version: 1` and travel with immutable revisions, backups, copied shares, comparison, and offline data. Unknown levels are not replaced with preview defaults. A plan without calculation inputs stays valid. Source or version changes require a new model ID; correcting preview arithmetic never overwrites recorded observations.

Calculation plans accept an optional `gender` field with `male` or `female` values, or an optional versioned `genderSelection` for an additional record ID. Validation requires at most one selection. Older persisted plans and share links without either field retain their existing unspecified-gender semantics, including an explicitly labeled no-bonus preview and separate comparisons. No migration fills in a missing gender. Selections survive build revisions, copied shares, character calculation snapshots, and backup restore without becoming a recorded character observation. See [mod selection compatibility](mod-calculations.md#gender-bonus-profiles).

To reproduce the numeric projection offline from the shared native snapshot:

```sh
npm run calculations:update
npm run calculations:reference
```

The updaters verify source identity, project reviewed numeric fields, and replace generated files atomically. Use `node scripts/update-native-stats.mjs --input "$CRYSTAL_PROJECT_INSTALL_DIR"` to verify the installed executable and database hashes against the bundled source. Updating the shared snapshot follows the [native catalog workflow](catalog-sources.md). Installed-input verification remains pinned to the original Windows executable hash; the compared macOS executable has a separate identity despite its matching calculation code. Shared gameplay scope does not relax these checks or authorize overwriting the dataset. Routine checks need no private inputs or network requests.

Authored combat expressions live in [the rule definitions](../scripts/lib/combat-rules.mjs). The readable reference is generated from the native character and combat formulas and a maintained plain-language introduction. It omits per-formula evidence lines; source fingerprints and numerical verification remain in the machine package and this technical guide. `calculations:check` rejects rule, projection, schema, or documentation drift. Schema tests validate the supported exported formats and reject malformed combat operations. Domain tests compare the bundled rules with synthetic results from unchanged native Calculator methods, selected native costs/periodic methods, and native FNA curve methods compiled in a private .NET harness. Modifier parity additionally executes unchanged `BattlerStats.Clear`, `ApplyStatMod`, and `Add` methods against synthetic source groups, validating every supported scalar operation and identity-specific list merging. Source stubs supply explicit state and do not establish scheduler parity. Only numerical fixtures and portable source hashes are checked in; the harness and decompiled code are not. Native preview regressions compare the power coefficient and the complete physical hit curve with compiled native methods. Learning display and affordability rules pin the native learn-menu source. Persistence and rollback coverage keeps saved assumptions and observations separate.

Male and female previews apply the native gender bonuses used in normal gameplay. An unspecified gender provides a no-bonus comparison baseline. The engine's `EnableGenderBoost` flag is an internal development control, not a player-facing option. Gender assumptions never change recorded character observations. Arithmetic outside the supported signed 32-bit range remains unknown.

Mod applicability follows the selected Game Setup revision. Only enabled imported layers supply supported constants. Definitions selected from a disabled, unknown, or conflicting mod remain in the saved loadout, but their effects are not applied and totals remain unresolved with a reason. Catalog browsing and personal definitions do not enable a mod. Imported formulas remain inert; custom calculations use only supported typed fields and versioned rules.
