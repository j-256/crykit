# Workspace persistence

`WorkspaceProvider` captures one `WorkspaceRepository` for the rendered planner. Managed guest and account operations use admitted local roots with transactional head checks, rollback and undo. Retained guest databases remain available through the source recovery boundary. Account opening uses an opaque lifecycle token and a separate encrypted database; it never copies guest samples or records. A new account supports planning without an observed Playthrough. Tracking requires creating or selecting one explicitly.

The account database layout is versioned separately from planner domain revisions. Its local planner cache, history entries and pending intent bodies are encrypted with the account key through the lifecycle's generation-fenced key callback. Source originals are immutable encrypted revisions referenced by exact document/revision pairs; the legacy materialization facade returns real bytes within explicit limits. It never substitutes missing originals with empty data.

Cipher chunks are staged before activation. A single IndexedDB transaction checks the persisted expected fence and reference readiness, then publishes the cache head, history closure, encrypted intent, journal and new fence. Crypto and network work stay outside this transaction. Generation invalidation aborts an active transaction. Failed staging or activation preserves the preceding active data; inactive ciphertext stays available until a future reachability-aware cleanup can establish that it is safe to remove. Broadcast messages carry only a fence hint; subscribers read and authenticate persisted state before notifying the planner.

`AccountProjectionSchema`, `AccountHistorySchema` and `AccountIntentSchema` describe local-only records. `stageAccountBytes`, `stageAccountJson`, `openAccountJson` and `activateLocalAccountCommit` provide the prepare/open/activate seams. An `unmapped-planner-intent` retains its original operation ID, exact base and target references, local fence revision and additive mode. These records are not cloud documents or upload requests. Document mapping must consume their retained bases atomically before any transport can publish them.

Profile changes remount the planner, dropping its optimistic queues, drafts, recovery callbacks and subscriptions together. Old repository handles retain their captured authority and reject after invalidation. Account route preferences stay in memory; account-specific planner selections are encrypted with the planner. Guest route preferences retain their existing browser storage.

Ordinary guest planner saves retain their stable wrapper and adopt the exact committed head. A concurrent read can encounter that new head before adoption and must reject its captured predecessor. While a save is pending, that read failure leaves the retained-data monitor alive for the owning save and subsequent commands. Idle stale wrappers still release their monitor. Lineage replacement, profile invalidation and bulk successors also retire the old monitor.

Guest admission validates the complete inherited archive through bounded native read windows, checking the selected head and both the stored record digest and archive digest. Already collected buffers within the ordinary chunk bound use native Web Crypto SHA-256 outside the IndexedDB transaction. Larger records retain incremental hashing, and all paths preserve exact original bytes and the same persisted SHA-256 format.

A separate versioned device preference stores only guest selection or an opaque selected account ID. It grants no authority. Startup reopens a remembered selected account through `unlockRememberedProfile` and the real account repository, initially with disconnected online access. Missing, invalid or unreadable selections after known account use present access choices. An explicit tab Lock or sign-out suppresses automatic reopening. The infrastructure `ProfileTransitionReason` distinguishes `pagehide` from the default transition only for that UI marker: both clear keys, jobs, URLs and rendered account access. A restored page remains locked; a reload can perform verified remembered reopening.

Planner ZIP export preserves the native format's bounded source and history rules and validates the resulting archive. It is not a complete account backup: encrypted pending intents and all protected account resources require the complete backup implementation. Account feature adapters use the captured repository boundary for their complete workspace commands. Removal controls remain disabled pending the complete backup/review composition. `accountPendingWork` and `removeEncryptedAccountData` provide real prerequisites for `removeProfileFromDevice`; the latter transactionally clears all account ciphertext tables while retaining the empty database shell so a profile switch can still abort removal. It must only be called through the reviewed lifecycle operation.

Managed local catalog frames use the existing compact mod representation with an exact baseline pin. Admission reconstructs the complete effective view before validation and use; older expanded frames remain readable. Original uploaded bytes, source metadata and historical planner values are retained. Exact deeply immutable catalog views can reuse derived presentation and unchanged storage records. Mutable imports and shallow-frozen containers still require complete recomputation and validation; IDs and digests alone never establish this eligibility. The native format owner constructs reusable expanded views from exact admitted immutable sources and retains their compact input and baseline identity privately. Graph validation compares that complete compact input against the expected source composition; raw or separately admitted full catalogs still require the complete expanded comparison. Preparation for the optimistic UI and captured repository can share one result only for the exact frozen source array and complete originating Game Setup value.

New local frames also use the existing versioned packaged-catalog codec for an exact built-in catalog. Nonidentical inputs must corroborate every JSON value before their ID, revision and checksum can name the packaged snapshot; object property order does not change JSON content. Imported and composed catalogs retain their required bodies. Reading resolves the exact package before validation and rejects unavailable pins explicitly. Supported historical packages must remain available, or their exact bodies must be transactionally materialized before removing a relied-on pin. Older full frames remain readable and unchanged when reused. Workspace views and complete portable backups contain full catalogs, independently of future package availability.

Historical shape admission belongs to a private immutable-value owner. Compact checkpoint reconstruction retains admitted before/after identities, while old full frames keep their native schema normalization. Reconstructed endpoints receive complete shape admission and freezing before catalog-sensitive graph validation, so later checks of that exact endpoint can reuse the successful result; a failed graph check never grants domain reuse. Reusing a historical domain check requires the same ordered, format-owned immutable catalog context. Intrinsic historical edge keys may be reused, but their resolution still checks the actual dependency map. These pure results do not authenticate storage: mapping still reads and validates its stored inputs and fully admits the stored target before issuing its receipt. Current planner validation remains separate. Pending carry-forward and retention inspect their finite fixed-state closure lists with one parsed-body scope, while checking each closure identity and dependency graph independently. This structural reuse does not replace source authentication or the full stored target validation.

## Build picker library imports

Adding JSON from an unsaved Build picker archives its exact source bytes without saving the Build, enabling a layer, changing an existing project's Reference choice or setting a future default. A new private project starts outside Reference. Choose from library opens the Build's mod controls; enabling a version or selecting its definitions remains unsaved until Save. Cancelling the form keeps the independently imported library source.

`importOwnedLibrarySource` uses the existing owned-file command and receipt protocol. The provider captures the form owner and strict input version, drains the App's planner queue before capture, checks the saved planner identity/revision, and preserves unrelated draft, navigation, pending-command and profile guards. Guest publication uses the complete coordinator journal; account publication uses the encrypted local transaction and fence. Receipt resolution verifies the complete saved result and exact selected successor before the keyed App remount recreates callbacks and revision bookkeeping. Loading planner data or receiving a broadcast cannot confer this authority.

`BuildInputController` retains only volatile form values across this owned transition. It does not migrate callbacks or admit descendant edits: an input change invalidates automatic continuation. The successor confirms hydration before new commands are available. A rejected completion after publication reports the durable library import separately from pending Build recovery. Retry reconciles that same receipt; Download Build input exports inert form values without owner identities, receipts or repository permissions. Profile changes revoke the volatile input. Unknown dirty registrations and independently edited Build details remain blockers.

Encrypted reopen validates each captured record against its own exact dependencies. A Build retains its setup, whose closure authenticates the imported layer catalogs. A dependent record invokes unavailable-source classification only for its own missing catalog pins; setup and history owners always verify their source receipts. This keeps complete owned layers reopenable without inventing missing-source receipts or widening parent dependency lists.
