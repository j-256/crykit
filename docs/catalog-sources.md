# Built-in catalog sources

Crystal Kit ships a static, revisioned reference catalog so a blank Playthrough can search and inspect Crystal Project definitions without importing a file or making a runtime network request. Catalog definitions remain separate from inventory, character learning, party progress, and other personal observations. Finding an entry never establishes that the player owns, learned, unlocked, or can use it.

## Catalog certainty and identities

`catalog-v1` is the bundled baseline. It combines fingerprinted Windows 1.6.9 records with Moonlight Project 2.2, Equipment Expansion 1.3, and Learnable Innate Skills 1.0 evidence. Definitions use `base:` or `mod:<project>:` identities directly in catalog construction, artwork bindings, and source receipts. Numeric model families remain distinct, and mode variants keep separate IDs. Provenance belongs in source metadata. Development catalog revisions and source-prefixed entity links are not shipped. Imported catalogs and saved user revisions retain exact identities and checksum pins.

The wiki supplies acquisition and location guidance, supplemental descriptions, and full-body class artwork for Progress. Some reviewed name and identity bindings still use wiki class membership and labels, checked against native records. The database and mod imports supply source-backed gameplay definitions. World, map, and script placement data are not fully ingested, so some remaining wiki dependence reflects importer coverage. Wiki text never establishes a missing native mechanic or platform equivalence.

Moonlight's committed snapshot is [moonlight-project-v2.2.json](../src/catalog/moonlight-project-v2.2.json), exported from Xenon's Moonlight Project - Classes project. Its identity links validate the export digest, numeric class IDs, tree coordinates, node kinds, and recorded names. Freelancer and Brawler are Moonlight content. Brawler observation squares whose definitions differ from that export remain unmapped in capture suggestions.

An explicit source null is known absence, displayed as **Not set in source**. It does not establish the runtime result of an optional override. Zero resource costs, false flags, empty modifier lists, authored descriptions, class equipment permissions, and PP costs are retained from the records. Planning details show supplied fields that apply to the definition kind. They do not add PP or equipment-slot uncertainty to an ability. Personal inventory, learning, progress, and enabled-mod choices retain their own knowledge states.

The [certainty audit](catalog-certainty.json) lists remaining gaps by field, kind, reason, and example identity. Supplemental geography and competing acquisition claims require separate evidence. Barbarian and Tempest observations lack corresponding ingested exports. Unimplemented calculations and unsupported modifier semantics retain their actual limits. The native and mod records do not establish every platform's version parity, authored strategy, artwork binding, or content license.

Generate a new portable mod snapshot with an owned Crystal Edit export:

```sh
npm run mods:bundle -- --input <mod-export.json> --output src/catalog/<new-snapshot>.json --key <project-key> --mod <recorded-mod-name>
npm run mods:bundle -- --check --output src/catalog/<new-snapshot>.json
npm run certainty:audit
npm run certainty:check
```

The bundler preserves supported model records, version metadata, authorship, the source digest, and numeric identities. It excludes comments and private paths, never executes descriptions or formulas, and refuses to overwrite an existing snapshot. A new snapshot must be registered in a new catalog revision with reviewed identity links and its canonical checksum. Adding a file alone does not make it visible in the application. Offline checks require the committed snapshot rather than the original installation.

## Native gameplay facts are the base

The default catalog is generated from the Windows 1.6.9 game installation. The executable's PE version resource independently reports matching file, product, and assembly versions of 1.6.9.0. The bundled gameplay snapshot records that evidence, its executable hash, relative database names, database format versions, source hashes, and executable-derived enum labels. It contains enemies, enemy actions and nested conditions, drops and steals, abilities, status effects, equipment, items, classes and learn trees, passives, recipes, biomes, encounters, overworld enemy behavior, difficulty settings, growth records, and selected game configuration. Developer comments and unrelated system content are excluded.

Native definitions are ordinary catalog definitions available in reference, inventory, learning, and planning. Exact reviewed numeric identity links connect base definitions where supported. Unmapped records receive database-and-ID identities. Equal names do not merge records or establish that a wiki monster is the same native enemy. Native fields take precedence within verified identities; retained wiki fields and guide descriptions supplement gaps with their own provenance. When a native record supplies no description, its retained secondary description is labeled **Supplemental description**. Pickers prefer base definitions and offer **Include other sources and mode variants** for overlapping supplements and patch records. Reference offers the same records under **Additional reference > Other sources & mode variants**. This presentation preference does not merge their identities. Saved plans pin exact immutable revisions; imported and user-created catalog revisions remain available for their references.

The definition header labels the native platform, version, and mode once. Repeated native field citations and complete supplemental claims corroborated by the game reference stay out of the fact list. Unsupported supplemental claims and unresolved values retain their evidence. **Source and version details** preserves the full source trail, applicability, and executable evidence. The [game-code source audit](source-corroboration.md) records internal proof locators and checks every bundled revision without changing persisted catalogs.

The maintainer's manual observations are scoped to Nintendo Switch 1.6.6. Windows 1.6.9 and Switch 1.6.6 content equivalence is unresolved. Different version numbers do not establish missing Switch content or update lag. A team with a different recorded platform or version retains an unresolved parity check, with a direct action to review its pinned Game Setup. Game Setup supports an exact Windows platform and installed game version; an unspecified PC platform does not establish Windows equivalence. Wiki and guide material have their recorded, often unverified version scope; the older Crystal Edit class export does not become Windows 1.6.9 evidence through this import.

The snapshot preserves the separate Vanilla and Chaos patch records. The inspected Windows loader applies them by native ID after loading the base databases. Patch definitions are labeled overrides, not inferred enabled modes. Raw enemy attributes and combat ratings are inputs, not a simulated battle sheet: automatic stat generation, difficulty, player-style enemies, modes, and mods can change effective values. Steal loot availability and per-attempt success stay separate. Repeated names, test enemies, and dummy records keep their distinct native IDs rather than being advertised as unique normally encountered enemies. Numeric enums provide labels, not automatic verification of every engine mechanic.

`src/catalog/native-game-data.json` is committed build-time input. The app bundles its normalized catalog for offline use and never reads a game installation or requests game data at runtime. Refresh it with Node.js 22.12 or later, a .NET runtime, and the ILSpy CLI:

```sh
dotnet tool install --tool-path <local-tool-directory> ilspycmd --version 11.1.0.9782
npm run game-data:update -- --input <game-content-directory> --decompiler <local-tool-directory>/ilspycmd
npm run game-data:check
npm run check
```

The updater decodes database containers and inspects executable metadata and enum declarations; it does not execute the game. Review source, identity, version, mode, and normalized changes before committing. Changed gameplay facts require a new bundled revision and its canonical checksum; never replace the content of an existing immutable revision. The offline check validates content digests, the generated catalog checksum, and exact bindings against the committed reviewed identity crosswalk. Fresh app checkouts require only the committed snapshot and ordinary Node dependencies; .NET, ILSpy, and an owned installation are needed only to refresh it. Native game data retains source-specific rights and receives no AGPL or wiki CC-BY-SA grant through this project.

Native enemy pages present identity, scoped version, HP/MP, level, rewards, combat inputs, attributes, drops, steals, and action references as compact bestiary entries. The Game mode dropdown offers Standard, Vanilla, and Chaos independently of Easy, Normal, and Hard difficulty. It opens the matching native enemy override by numeric ID, or retains the base record when that patch leaves the ID unchanged. Enemy rewards and actions come from the selected record, and action links use the selected mode's definitions with base inheritance. The Difficulty dropdown defaults to the source data's Normal difficulty and previews the inspected Windows 1.6.9 rates for HP/MP, attributes, and attack/defense inputs, including boss rates and changed-vital rounding. Selection stays in the link's `mode` and `difficulty` query parameters and leaves saved Game Setups unchanged. Native difficulty IDs are Normal 0, Easy 1, and Hard 2; display order is Easy, Normal, Hard. Unknown selections remain unselected and show raw inputs. Shared corrections remain scoped to exact records; changing a personal version to a different mode record opens that catalog entry without changing the saved personal version. Stat modifiers and battle effects can change final values. Loot availability and per-attempt steal success stay separate, and action weights are not displayed as probabilities. Original engine fields, complete records, relationships, and provenance remain under Technical details, where money is an integer in copper units. Missing exact artwork uses a neutral bestiary emblem. Money rewards and prices elsewhere use gold, silver, and copper denominations; source values and editing inputs retain their copper units. Definition links retain browser tab behavior. Global search leads with base records, identifies same-name enemies by level, location, and record ID, and exposes other sources and mode variants through an explicit control. Filters stay on the Reference results page; source corrections and personal versions remain available from the entry actions.

## Community wiki snapshot

The supplemental reference layer is generated from the public [Crystal Project community wiki](https://crystal-project.fandom.com/wiki/Crystal_Project_Wiki) through its MediaWiki API. It includes class infoboxes and stat growth, class skill and passive tables, resource and learning costs, prerequisites, targeting and effect text, documented Vanilla-mode differences, equipment and item tables, item pages, monster templates, statuses, areas, commands, crafting recipes, and other substantive game-reference pages. Every extracted entity keeps its exact page revision, section or row locator, source applicability note, and page link.

The committed catalog contains normalized factual fields and plain text. Artwork is bundled separately as described below. The catalog does not retain advertisements, scripts, interactive maps, or executable wiki markup. Structured lists, records, and tables render as data in the reference view. The application never fetches the wiki at runtime.

The wiki identifies its content terms as [CC-BY-SA](https://www.fandom.com/licensing). Wiki-derived content remains under those terms and retains page-level attribution; the application's AGPL-3.0-only license does not replace source-content rights. Refreshing the snapshot requires reviewing both the generated changes and the upstream licensing declaration.

Currency amounts display as gold, silver, and copper coin icons, with the amount before each icon. `WindowHelper.DrawCurrency` in the fingerprinted Windows executable corroborates the conversion of 100 copper per silver and 100 silver per gold; its locator is recorded in the [code evidence](../src/catalog/game-code-evidence.json). Whole and mixed prices use descending nonzero denominations; zero remains zero copper. This applies to explicit currency amounts in costs, tables, descriptions, and read-only previews. Original source values remain intact in stored definitions, editing fields, and exports. Unknown or unsupported amounts stay as text, and metal item quantities such as Gold Ore are not treated as money. Coin images have accessible denomination labels and text fallbacks.

Community documentation can be incomplete, stale, internally inconsistent, or based on a different game release. The catalog therefore does not claim complete Nintendo Switch coverage, parity with a particular official mod-pack snapshot, or verified calculation order. Source disagreements remain conflicting claims. Missing kind-specific fields remain explicit unknowns.

The Quintar breeding guide uses the pinned wiki breeding entry's Method 2 for its ordered pairings, bundled monster descriptions for capture directions, and the pinned Quintar Shop table for the Ocarina price. [Respwner's breeding guide](https://steamcommunity.com/sharedfiles/filedetails/?id=2794448715) supplies cumulative race-win thresholds by the partner's type, including its documented reduction of Black's threshold. The [code audit](source-corroboration.md) corroborates pairing results and distinct-track counting, but Windows 1.6.9 requires one partner win for Desert and Highland where the guide recommends two. These supplementary race claims retain their citations and remain unverified for Switch and mods. Keep/release advice is derived from each parent's last use in this route, not from observed nursery contents. The guide does not calculate food quantities, recovery time, or total cost.

Reference details show every competing field value with its source, locator, revision, applicability, and any claim note. Different values can reflect wording or scope differences; the importer does not decide whether they describe the same fact. Choose **Review source differences** or **Create personal version** to review normalized field claims for the selected playthrough. **Keep unresolved** preserves all evidence by default. Selecting a claim and saving creates a preferred personal revision with that exact value and source attribution. Original catalog claims, saved inventory observations, and build references retain their earlier definitions. The catalog detail links to an existing preferred personal version without removing its source conflicts.

### Native game artwork snapshot

Native items, equipment, classes, monsters, status effects, UI icons, and the Quintar guide use artwork extracted from a maintainer-owned Windows installation. This is a build-time snapshot only: the application never reads an installation, scans the machine, or requests game data at runtime. The extraction manifest records a content fingerprint over every inspected database pack, texture pack, and the game executable without retaining the machine-local input path.

The extractor strictly reads the game's byte-inverted JSON databases and named PNG texture packs. The binary layouts are independently documented by the pinned [CrystalProjector database schema](https://github.com/iconmaster5326/CrystalProjector/blob/79320b343d603aa069aa023fd54020d36419e082/schema/ksy/database.ksy) and [texture-pack schema](https://github.com/iconmaster5326/CrystalProjector/blob/79320b343d603aa069aa023fd54020d36419e082/schema/ksy/texture_pack.ksy). Indexed icons use the exact 32x32 cell rule verified against the fingerprinted Windows executable. Class artwork combines both explicitly recorded actor-sheet variants using the executable's class-icon crop. Catalog bindings do not identify sprites from filenames, visual resemblance, or display-name similarity.

Native catalog definitions use their own database ID and mode scope to bind artwork from the exact retained source record. The updater requires the inspected executable and gameplay database fingerprints to match `src/catalog/native-game-data.json`; the artwork manifest also pins that snapshot's bytes and version. Base records and Vanilla or Chaos overrides receive separate bindings, even when their artwork is identical. Monster artwork uses the complete named texture from each record, preserving distinctions between same-name enemies. Null texture references do not inherit artwork from another mode, an alternate texture, or a similar label.

`src/catalog/game-identities.json` is the explicit bridge from bundled catalog IDs to native database IDs. It is generated from a full pinned commit of the public Crystal Project Archipelago item table and its constants, whose numeric codes document the native database ID plus a category-specific offset. The generator accepts only an exact supported source namespace and one upstream record. Display-label differences between that source and the installed database are preserved in coverage metadata; the numeric crosswalk, not punctuation or spelling, establishes the record identity. Catalog entries from other sources remain explicit identity gaps.

`src/catalog/game-assets.json` inventories every named embedded texture, every inspected data file, all database references to those textures, input hashes, extraction regions, catalog, guide, and UI bindings, and unresolved artwork cases. `src/catalog/game-artwork.json` is the smaller runtime projection. Content-addressed PNGs in `src/assets/game-assets/` contain only the exact images needed by catalog, guide, and UI bindings. An ability record with no direct texture path stays unresolved rather than inheriting a guessed generic icon. Source-label discrepancies and records without direct artwork stay reviewable in manifest coverage.

UI sprites use explicit `uiArtwork` bindings in the [extraction manifest](../src/catalog/game-assets.json) and [runtime manifest](../src/catalog/game-artwork.json), which retain source texture hashes and regions. Offline checking rejects missing bindings or changed extraction regions and source identities. These UI sprites use the same content-addressed asset directory and refresh command as catalog artwork.

The Quintar guide's native artwork is pinned in the same manifests under `quintarGuide`. The Babel Quintar and Quintar Ocarina tiles use indexed icon cells checked against their installed item database records. Wild capture tiles use texture paths checked against the installed monster database, and the game system's type labels resolve Teal to River and Yellow to Desert. Breeding tiles use a named Quintar egg texture because the game files do not identify a distinct image for each bred result. The Golden tile uses a bounded frame from the named Golden Quintar actor sheet. Images illustrate guide steps and do not represent observed nursery contents. All images are bundled for offline use and retain the game's separate artwork rights. Each tile links to the exact bundled Reference entries available for its items, wild quintars, eggs, breeding method, and places. The bundled Reference has no separate entries for individual bred variants.

The Travel & unlocks checklist includes item identities absent from the public crosswalk. `src/catalog/game-travel-identities.json` records reviewed item database IDs and the exact `item.dat` checksum inspected for them. The asset updater checks each record's ID and label against that database before extracting its icon; a changed database requires review of these bindings. Native record IDs, texture crops, and database fingerprints remain in the committed extraction manifests; ordinary Reference details omit this proof of provenance. Personal definition overrides do not inherit the bundled item's icon.

Refresh the identity crosswalk and native artwork independently:

```sh
npm run game-identities:update -- --ref <full-archipelago-commit>
npm run game-identities:check
npm run game-assets:update -- --input <game-content-directory>
npm run game-assets:check
```

Add `--unpack <new-output-directory>` to `game-assets:update` to write every named embedded PNG plus an inventory outside the repository for local inspection. The target must not exist and the command refuses repository-local unpacking. The default committed snapshot keeps the complete hashed inventory but bundles only artwork used by catalog, Quintar guide, or UI bindings. Review all crosswalk, input-fingerprint, coverage, and asset changes before committing. Offline checks validate the committed crosswalk, native gameplay input fingerprints, record and mode identities, exact crops, complete artwork coverage and reasoned gaps, runtime projection, exact PNG bytes, content bounds, and one-to-one asset-directory membership.

Native game artwork remains copyrighted Crystal Project material and receives no AGPL or CC-BY-SA grant through this project. Provenance and checksums support auditing, not a claim of ownership or redistribution rights. The snapshot establishes only the inspected Windows installation's appearance. It does not establish Nintendo Switch or optional mod-pack parity.

### Equipment Expansion sprite snapshot

`src/catalog/mod-sprites.json` maps Equipment Expansion identities to content-addressed PNG cells in `src/assets/mod-sprites/`. The generator uses the equipment record's texture path and index with Crystal Edit's 34-pixel, seven-column icon layout. Loose custom sheets take precedence; otherwise, the generator reads the named PNG payload from the base game's version-0 `Content/Textures/Equipment.dat` archive. It records source digests without retaining private input paths. `npm run mods:check` requires an exact binding for every exported equipment definition and verifies each file against its SHA-256 filename and exact dimensions. These exact mod-export bindings take precedence over wiki fallbacks for the same catalog identity.

### Wiki sprite and icon fallback

The Progress class mastery board uses the pinned wiki full-body world sprites instead of native class-icon crops. These sprites retain their exact class bindings, content bounds, and local offline assets. Other catalog artwork continues to prefer exact native bindings.

When no exact native or mod-export catalog binding exists, Reference results and details use local artwork where the wiki establishes an explicit association. Class images come from the class infobox at the catalog's recorded page revision. Equipment and status icons come from literal cases in the wiki's link templates. Monster images use pages with `MonsterBox2` and its verified `File:PAGENAME.png` rule. The manifest records both page and template revisions. Same-name skills, personal definitions, foreign catalogs, and unsupported mappings do not inherit guessed artwork. Missing mappings and missing wiki files remain recorded in manifest coverage; detail pages without any source say **No exact artwork linked**.

`src/catalog/wiki-sprites.json` records each file's source URL, upload timestamp, file-description revision, dimensions, MIME type, original SHA-1, local SHA-256, license label, and catalog bindings. The PNG, GIF, and WebP files in `src/assets/wiki-sprites/` retain the downloaded bytes. Entity artwork requires a byte-for-byte checksum match with the wiki upload. For older menu-icon PNGs that the CDN recompresses even with `format=original`, the downloader requires the original format and dimensions, records `representation: cdn-png`, and retains the upload SHA-1 and size separately from the downloaded-file SHA-1, SHA-256, and size. Offline checks verify the exact committed bytes. Individual images and the total snapshot have bounded sizes. Download, format, and checksum failures stop the refresh before the manifest is replaced. Cached verified downloads can be reused on a subsequent refresh.

Menu icons use a separate `icons` map in the sprite manifest, keyed by equipment category, skill type, element, or command. Weapon glyphs come from named wiki icon files; shield and armor glyphs use exact native equipment-menu cells. The icon template and command images in pinned class infoboxes or matching section headings supply the other associations. Equipment, type, category, command, and element fields can display these symbols beside their original labels. An ability named Fire does not acquire a fire-element icon from its name, and unknown or conflicting fields retain their recorded state. Unsupported categories remain text-only.

Character details, Reference fields, inventory, definition pickers, build previews, and learned-skill lists share compact artwork. Exact native artwork takes precedence, followed by exact mod-export cells and then wiki artwork; all remain restricted to their catalog identity. Generic skill icons describe a recorded type or category. Failed images leave the text readable. **Artwork source** retains custom mod artwork and wiki attribution. Shield and armor category icons use the exact native `Icon/SystemB` cells documented in [the equipment icon source](../src/assets/menu-icons/README.md). Native game artwork and reused base-game cells render without a provenance disclosure; their database identities, texture crops, fingerprints, and crosswalk remain in the committed manifests. **Menu icon sources** in character and Reference details links to the pinned public file descriptions and their rights labels.

Artwork has separate rights from wiki text. For example, the [Warrior sprite file](https://crystal-project.fandom.com/wiki/File:Warrior-world-sprites.webp) and [Short Sword icon file](https://crystal-project.fandom.com/wiki/File:Short-sword-icon.gif) use the wiki's `Fairuse` declaration. That label and the Equipment Expansion sprite metadata describe copyrighted third-party artwork; they do not place it under the project's AGPL license. Follow **Artwork source** on a reference detail for custom mod or wiki attribution; inspect the committed manifests for native extraction evidence. Nintendo Switch and mod-pack appearance parity remains unverified.

Refresh artwork independently from the factual catalog:

```sh
npm run sprites:update
npm run sprites:update -- --cache
npm run sprites:check
```

The first command fetches the required source revisions, template mappings, file metadata, and images. `--cache` performs an offline replay from `.wiki-cache/sprites/` and requires its input catalog digest to match. `sprites:check` validates the manifest and local image bytes without network requests or writes; it also runs as part of `npm run check`. Review generated bindings, gaps, source/rights changes, and asset additions or removals before committing. Superseded asset files are left for explicit review and removal, and the privacy check rejects sprite files absent from the manifest.

Vite emits native, mod, and wiki images with the static application assets, so offline preparation caches them together with the shell. No game installation, wiki, or CDN URL is used as an image source at runtime. Artwork metadata remains separate from immutable catalog facts and personal backups; refreshing artwork does not alter catalog checksums or recorded playthrough data.

## Native class growth ratings

The native catalog supplies vanilla numeric growth ratings from its versioned game database. Growth calculations prefer **Growth ratings** from the native record over the older Crystal Edit copy. A preferred field with unknown, conflicting, missing-stat, or invalid data stays unresolved rather than filling gaps from a lower-priority source. Historical and imported class definitions without that field continue to use their pinned Crystal Edit ratings. Explicit mod replacements retain their imported class values.

Native exports establish ordinary known facts for their recorded version and platform. Normal details omit export citations, copied IDs, redundant growth tables, and native artwork proof. Source-neutral labels describe the facts. Stored sources and backups retain the evidence, community attribution remains visible, and unresolved competing claims retain their citations. Windows scope does not establish Switch or mod parity.

Its game-release match is a maintainer assumption tied to the export date; the editor version is recorded independently. ## Supporting identity sources

Stable base item, equipment, class, and Monster Magic identities also come from the public [Crystal Project Archipelago world](https://github.com/Emerassi/CrystalProjectAPWorld), principally its [item table](https://github.com/Emerassi/CrystalProjectAPWorld/blob/main/worlds/crystal_project/items.py), [class constants](https://github.com/Emerassi/CrystalProjectAPWorld/blob/main/worlds/crystal_project/constants/jobs.py), and [Scholar ability constants](https://github.com/Emerassi/CrystalProjectAPWorld/blob/main/worlds/crystal_project/constants/scholar_abilities.py). That project targets a Steam Archipelago branch and does not establish Nintendo Switch compatibility. Its repository is MIT-licensed, and this catalog uses its factual labels and source links.

Equipment Expansion identities began with the [public Equipment Expansion item sheet](https://docs.google.com/spreadsheets/d/1s3kWj2DONAln5hRx7p4JyEfr71wkLIM-KC3LTA3gNks/edit#gid=0); the bundled versioned project export now supplies the detailed definitions. Nintendo's [Mod Pack 1 description](https://www.nintendo.com/us/store/products/mod-pack-1-quality-fun-70050000048696-switch/) supplies its named rule changes, and Nintendo's [Mod Pack 2 description](https://www.nintendo.com/en-gb/DLC/Mod-Pack-2-New-Challenges-2646897.html) supplies high-level entries for Passive Trainer, Doge Shield, Equipment Expansion, the custom classes, and additional bosses. These publisher descriptions establish that the features exist and preserve the details they state, but they do not provide bundled source revisions. They do not establish that the supplied PC exports match the packaged Switch revision.

## Explicit gaps

The **Travel & unlocks** roster uses explicit item identities for mount instruments, reusable shrine stones, and selected capability items. The bundled travel supplement promotes Ibek Bell, Owl Drum, and Salmon Cello from the pinned Mounts sections, and New World Stone and Old World Stone from the [Tools table revision](https://crystal-project.fandom.com/wiki/Tools?oldid=7601). Their definitions retain section or row attribution and unverified platform/mod applicability. The Old World Stone table lists Particular Ore without a full route; the reference preserves that limited evidence. These definitions are part of the bundled baseline. Acquiring an instrument does not establish a particular bred Quintar, current inventory quantity, character skill, or build permission.

The built-in reference entry named `Wiki catalog coverage gaps` collects source names without matching wiki detail, links to wiki pages that do not exist, pages that were not represented as standalone definitions, parser issues, and the unresolved platform-parity warning. An unmatched preexisting name stays available with `Wiki coverage` marked unknown rather than receiving inferred mechanics. Each matched entity also lists expected fields that its sources did not document.

Redlinks are leads, not proof that the named concept is a distinct game entity. Pages without standalone definitions include redirects, collection pages, and source-only table or summary pages as well as material the extractor could not classify. Review the source before promoting any gap to a new definition.

## Refreshing the snapshot

Run `npm run catalog:update` to fetch main-namespace pages, expanded categories, latest available revisions, redirects, and the item-category tree. The command writes an ignored source cache, regenerates `src/catalog/wiki-data.json`, and updates the combined starter digest in `src/catalog/data.ts`. Use `npm run catalog:update -- --cache` only to reproduce generation from the existing local cache.

Review the generated entity and gap changes, preserve stable starter IDs where identity is unchanged, and bump the built-in catalog revision before publishing a changed snapshot. Run the complete local verification suite. Keep GitHub Actions disabled for private repositories; see [deployment](deployment.md) for the public repository workflow.

The supporting source digest covers the source map, name records, generated wiki content, and confirmed Switch supplement. The bundled catalog checksum hashes the complete canonical catalog content, including native data, mod definitions, and supplemental evidence. Export digests remain provenance metadata.

## Confirmed Switch skill names

The bundled Switch supplement records in-game class and skill identities with explicit provenance. Reviewed Brawler and Freelancer observations are reconciled against the Moonlight export. Brawler observation squares whose definitions differ from that export remain unmapped in capture suggestions. Barbarian and Tempest mechanics, costs, and weapon requirements remain gaps until their exports are ingested. A same-name skill from another class does not supply those missing details. The supplement participates in the catalog content checksum without personal screenshots or character records.

Barbarian and Tempest entries follow their corresponding mod settings. Brawler and Freelancer export definitions are associated with Moonlight Project. Preparation is a Tempest passive distinct from the Squall innate. Neither Squall nor Barbarian's Toughness is learned from the confirmed trees. Shapeshifter represents appearance-passive unlocks and is not included as a combat class.
