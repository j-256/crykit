# Closed qualification release tooling

`scripts/qualification-release.mjs` validates, packages and releases only the independent qualification Worker. It cannot activate account, signup, email, confirmation, backup capture or maintenance capabilities. Qualification does not establish production readiness. The production release helper keeps its separate fixed destination and is unchanged by this tool.

Run `node scripts/qualification-release.mjs --config /secure/config.json --identity /secure/identity.json` to check inputs. Add `--dry-run` after building assets with `npm run build` to validate and inspect the exact production-entry bundle without provider writes. Add `--deploy` only under explicit qualification release authorization after establishing the isolated resources, disabled ingress/logging and independent Tail attachment. The CLI does not create resources, apply routes or schedules, provision secrets, configure Access or prove canary acceptance. Active account qualification requires a separate admitted effect budget and ingress proof; this closed publisher deliberately rejects that configuration.

Both input files must be absolute owner-owned regular JSON files, inaccessible to group or other users, without final symlinks and outside the source checkout. The identity inventory is version 1 with exactly these fields:

| Field | Meaning |
| --- | --- |
| `version` | Integer `1` |
| `workerName`, `origin` | Exact `crykit-qualification` and `https://qualify.crykit.lasers.app` |
| `databaseId` | Created qualification metadata database UUID |
| `limiterNamespaceIds` | Unique decimal strings ordered network, account, auth, location |
| `adminIssuer` | Exact approved HTTPS Cloudflare Access issuer |
| `adminAudience`, `confirmationAudience` | Distinct qualification audience strings |
| `excludedDatabaseIds` | Nonempty unique baseline database UUID inventory |
| `excludedLimiterNamespaceIds` | Nonempty unique baseline limiter namespace inventory |
| `excludedAccessAudiences` | Nonempty unique baseline Access audience inventory |

Obtain the complete baseline and qualification identities from provider readback before preparing this inventory. The validator rejects overlap and pins configuration to this reviewed input; it cannot establish whether an operator omitted a baseline resource or mislabeled an Access application. The publisher separately verifies the actual database name and UUID and exact bucket names before uploading. Do not copy production or preview storage, secrets, sessions or memberships into qualification.

The Wrangler input selects `worker/index.ts`, the pinned OPAQUE adapter, the qualification Custom Domain, `crykit-qualification-metadata`, and exactly `crykit-qualification-objects`, `crykit-qualification-backups` and `crykit-qualification-revocations`. It requires every original secret name, distinct rate-limit bindings, explicit disabled alternate ingress/logging and `crykit-qualification-alerts`. CPU and application storage cannot exceed the qualification ceilings enforced in the validator. Native email is restricted to the fixed sender and an exact bounded list of authorized `@crykit.lasers.app` test recipients, although sending stays disabled. Secrets are inherited by name; this tool never reads, generates, rotates or proves original secret values.

Each publication checks effective live ingress, producer logging and Tail policy before account code upload, verifies the single uploaded version's runtime and complete binding inventory, then assigns that exact version full traffic. It reads serving authority and effective policy afterward. An interrupted deployment is read back before any retry; an ambiguous or mismatched result fails without automatically publishing a second version. Private subprocess diagnostics stay bounded in an owner-only temporary directory. Preserve their confidentiality and inspect actual provider state before retrying.

The Node recovery reader accepts a separate version-1 envelope `{version:1, environment:"qualification", secrets:{...}}` with the original seven secret values. This is distinct from the multi-environment operational store described in [account deployment](accounts-deployment.md#original-secrets-and-restoration). Qualification must be named explicitly in both the file and reader call. Existing local, preview and production envelopes retain their meaning. The reader preserves ownership, mode, no-follow and byte-limit checks; it does not create or migrate protected files.

Focused verification is `node --test scripts/qualification-release.test.mjs scripts/production-release.test.mjs` and `npx vitest run --project worker worker/operations/recovery-secret-source.test.ts`. These contracts establish tooling boundaries, not deployed Access enforcement, original-key custody or hosted workload capacity.

## Shared controller budget

`scripts/qualification/budget.mjs` is a Node-only library for the single private qualification controller. It does not enter the production Worker or browser bundle and does not enable any capability. It uses [Node's built-in SQLite API](https://nodejs.org/docs/latest-v24.x/api/sqlite.html); use Node 24, or the supported Node 22 runtime with `--experimental-sqlite`. The qualification budget test command supplies that flag explicitly. Node 24 is the deployment workflow's configured runtime.

The stable policy name is `crykit-private-qualification-v1`; owner approval and its private evidence remain in the coordinator records, not this library. Create one ledger with `createQualificationBudget(absolutePath, runId)` in an existing owner-only directory outside source. Use that exact path and retained run ID for all controller processes and retain its SQLite database with the private evidence. The library creates an owner-only regular file and rejects existing files on creation, final symlinks, shared file or parent-directory modes, unknown formats and missing ledgers. Missing, corrupt or lost state must stop the run; creating another ledger would reset accounting and is not a recovery procedure. Do not move a database during an active transaction or reconstruct it by subtracting observed successes from limits.

Before every effect, call `reserveQualificationWork(path, request)` and dispatch only when its result has `dispatchAllowed: true`. A reservation has exact fields `id`, `clientId`, `accountId` (an opaque synthetic ID or `null`), `emailRecipients` and `costs`. Use a new reservation ID for each actual retry, including an uncertain first attempt. Repeating the same accepted ID returns `dispatchAllowed: false`; changing its costs, account, client or recipient set fails. This avoids authorizing a second effect when the first reservation response was lost. Reservation acceptance follows a committed `BEGIN IMMEDIATE` [SQLite transaction](https://www.sqlite.org/lang_transaction.html), which serializes competing processes. Lock timeout or commit ambiguity fails closed without dispatch.

Every cost field below must contain an explicitly known, nonnegative safe integer. A missing, fractional, negative, unknown or nullable cost fails; zero is an assertion that the controller has conservatively established no work in that dimension. Reserve a worst-case bound before dispatch, including possible descendants and automatic retries, rather than charging only successful outcomes afterward.

| Cost fields | Units and ceiling scope |
| --- | --- |
| `operations`, `opaquePairs` | Driven application operations including retries and job steps; OPAQUE start/finish pairs also require their two operations. Admission uses reservation timestamps, a rolling minute and a run total |
| `emailAttempts` | Native attempts across application and alert tests, charged to the UTC day and run total; `emailRecipients` must be an exact authorized test-alias set |
| `ciphertextBytes`, `revisions` | New synthetic ciphertext across the run; revisions also accumulate per synthetic account |
| `loadMs` | Conservatively reserved active load duration per controller reservation, charged to the UTC day and run total |
| `d1RowsRead`, `d1RowsWritten`, `r2ClassA`, `r2ClassB` | Conservative upper bounds for native storage work across the run |
| `d1MetadataBytes`, `d1RestoreBytes`, `r2Bytes` | Conservative additional physical allocations, per named database or all qualification buckets |
| `sourceContextBytes`, `restoreContextBytes` | Conservative application allocations in each independent context, including retained liabilities |

The library applies the finite qualification policy encoded in its named constants. Synthetic account identities stay counted after completion. An accepted reservation holds a client slot until `finishQualificationWork(path, id, outcome)` records `complete`, `failed` or `uncertain`. Completion frees only that slot; it never refunds operations, attempts, duration, revisions, native work or allocation charges. A crashed process therefore leaves charged work and an occupied slot until the controller resolves its outcome. Resolving a slot does not establish that a remote effect stopped; verify termination before reusing concurrency capacity.

A load reservation returns `notAfter`. The driver must actually stop its generator by that deadline and honor cancellation; the ledger does not kill processes or remote requests. Windows crossing UTC midnight must be split into separately admitted segments. Parallel reservations charge their durations separately, conservatively consuming allowance faster than elapsed wall time. An observed completion after its deadline marks the outcome uncertain and halts further admissions. Clock rollback also stops the affected operation. The clock is trusted controller input, not an independent provider measurement.

`recordHistoricalQualificationWork(path, request)` records work observed before the controller existed. It always returns `dispatchAllowed: false`, never occupies a client slot and labels the charge as historical. Its costs consume the same remaining allowance, conservatively charged at recording time; the original event time and evidence belong in the private coordinator record. Repeating its ID cannot authorize a later reservation. An observed overage remains recorded and halts further admission rather than being discarded. This is not evidence that the historical work was reserved before execution.

`readQualificationBudget(path)` returns the retained run identity, cumulative totals, separately labeled `historicalTotal`, daily totals labeled by `reservationDayUtc` from the last retained event, account count, active-client count and halt state. The daily projection does not advance during an idle period; admission uses the actual supplied reservation time. Inspect this alongside actual provider usage between stages. Cumulative allocation reservations are intentionally conservative: deletion or a failed allocation does not restore allowance. They do not establish measured physical usage, provider billing or headroom; existing physical occupancy and effects from every writer must also be covered before admitting work.

These guarantees apply only to callers using this one ledger and declaring sound bounds. Admission timestamps do not establish when downstream effects actually occur; drivers must dispatch promptly and use runtime guards where timing matters. They do not intercept browser background retries, scheduled Worker jobs, Tail alerts, email transport attempts or another writer. In particular, reserving an email allowance in the controller is not an actual send-boundary guard. Keep mail, schedules and any automatic work disabled until their complete effects can be bounded at the runtime boundary or an equally strong verified arrangement. Unknown costs or incomplete provider metrics block the affected stage. The controller budget does not authorize active releases, establish public-production readiness or provide a provider-enforced spending cap.
