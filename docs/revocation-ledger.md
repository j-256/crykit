# Independent revocation ledger

`worker/jobs/ledger.ts` owns a private, independently retained `REVOCATION_LEDGER` binding. It must not point at the payload or service-backup bucket, belong to a restorable D1 snapshot, or inherit snapshot expiry or garbage collection. The local configuration and Miniflare fixture use distinct buckets. Hosted provisioning, access policy and retention verification belong to service deployment; a local binding does not establish those properties on a provider.

The module is an internal storage producer. It does not authorize requests, remove accounts, stop public access, reconcile D1 jobs or reopen restored metadata. Its event kinds are `share-stopped`, `account-deleted`, `operator-revoked` and `invitation-revoked`. Strict versioned schemas admit only the applicable opaque identities, intent ID, session epoch and timestamp. Email, username, filenames, keys, content and unknown fields are rejected. Event and manifest identity objects have no delete or expiry interface.

## Durability and interruption

Provisioning calls `initializeRevocationLedger(context)` on an empty independent bucket. Initialization never replaces a missing head when other objects exist. An absent binding or head prevents append acknowledgment without changing ordinary account login or sync readiness.

`appendRevocation(event, context): Promise<void>` resolves only after exact canonical event bytes, its immutable index slot, head coverage and discovery membership have been verified. SHA-256 digests bind the index to the event envelope, including any liability association. GET bodies establish integrity; PUT responses, HEAD metadata and ETags alone do not. LIST size/ETag checks establish consistency with those already verified bytes. ETags also provide conditional write predicates.

Events are immutable by intent. Replaying identical canonical bytes does not create a second logical member; changed bytes reject. An intent reservation selects a monotonically numbered index slot. Writers create slots conditionally and never replace them. A losing reservation can move only after another intent permanently occupies its old slot, which prevents a delayed writer from filling an abandoned slot afterward. Writers help a winning slot advance the retained head before trying another slot. Head compare-and-swap never overwrites a newer head. No D1 transaction spans these writes.

A lost event, page, index or head response can leave independently retained work while the call rejects. A fresh context retries the same intent and exact bytes. An orphan event or incomplete manifest never implies acknowledgment. The caller must retain its exact command and preparation evidence, keep affected authority blocked or pending, and compose successful append with its own guarded final D1 transition before returning a completed lifecycle receipt. Incomplete preparations remain visible to verification and keep restore closed; durable job reconciliation and recovery of those preparations belong to the lifecycle owner.

An unrelated orphan event, reservation or manifest preparation blocks complete restore verification but does not itself block a new append: append checks its own membership and any next slot it must help publish. An incomplete or corrupt next index winner can block both head advancement and new acknowledgment. Reconciliation must use the original authorized intent and exact retained preparation evidence; it cannot invent a target, change frozen bytes or erase the incomplete objects. If that evidence cannot be recovered, restore remains closed. The storage producer does not promise recovery from every lost preparation.

Failures use bounded authored `LedgerFailure.code` values. Provider errors and stored values are not included in diagnostics. Checkpoint events distinguish event, index, head and acknowledgment boundaries. A mutable head changing between GET and LIST retries within the same append budget; other missing or inconsistent coverage rejects. Exhausting the bounded contention budget leaves the caller pending, even if an immutable slot already exists.

## Readers and closed restore

`readRevocation(intentId, context)` returns `null` for an absent event and otherwise requires exact target coverage. `readRevocationHead(context, minimum?)` checks the head and its final index digest, plus a caller-supplied trusted minimum head when available. These bounded target reads do not replace a complete ledger scan.

`verifyRevocationLedgerPage(context, continuation?, minimum?)` reads bounded ordered LIST pages and verifies their event, claim, index and manifest references. The continuation is trusted internal work state, not a browser credential or an independently authenticated proof. Consumers must retain all continuation fields without alteration and stage page results until `next` is `null`. Exact category counts detect omitted list members even when direct GET remains readable. Each index checks its predecessor digest; the final scan must cover the entire pinned head. Corrupt, missing, truncated, orphan or regressed coverage rejects. A head change requires restarting the scan; no seamless concurrent restore guarantee follows from paging.

Restore must supply its authenticated snapshot's minimum head, verify complete independent coverage and coordinate the final latest-head check with its own closed promotion fence. This module supplies neither that fence nor a provider-wide atomic snapshot. Hashes bind bytes under the trusted private storage boundary; they do not protect against an actor able to rewrite all independent state and its trusted baseline.

## Closed managed-key liabilities

`prepareRevocationLiabilities(intentId, pages, context)` freezes a separate versioned association and writes its exact pages before account-deletion append can succeed. Empty liabilities require an explicit empty association. Pages retain only opaque `sync/` key identities, assigned content-free marker identities and SHA-256 digests, fixed marker byte charges, and closed/released evidence. The reader checks marker encoding, digest, page order and duplicate keys. It does not establish that a live payload was actually fenced; the deletion owner supplies and proves that evidence before final account removal.

The event envelope binds every page digest through the immutable association. `readRevocationLiabilities(intentId, context)` returns verified pages only for an independently covered event. Missing or corrupt pages prevent both append acknowledgment and reads. Changing a frozen association under the same intent rejects. Invalid input is checked before allocation, and association identity freezes before its pages so a changed retry cannot allocate unbound pages.

The versioned codec allows at most 32 pages per association and 32 entries per page. Each object is limited to 16 KiB. Verification lists at most eight objects per scan page; append makes at most sixteen contention attempts. A call has bounded work, including referenced-page verification, but these limits are not hosted CPU, subrequest, latency or Free-plan compatibility evidence. The association limit is not a new customer quota or a guarantee of deletion at every admitted account size. Larger-account composition requires a versioned extension that preserves already acknowledged association and event bytes, with separate scale and recovery proof; existing associations cannot be extended in place.

Focused tests exercise the pinned Miniflare R2 primitive, including conditional writes, delayed and uncertain responses, competing writers, discovery disagreement, paginated verification and complete bounded manifests. This establishes local behavior only. Hosted overlap, resource capacity, original-key recovery, account removal, stopped-share receipts and closed promotion require their composed service proofs before activation.
