# Navigation and local links

Crystal Kit uses semantic hash routes so links work on static hosts, in a subdirectory, and with the prepared offline application. The path after `#` identifies a page, selected record, settings section, or modal action. Record links retain exact identities instead of using names as unique keys.

The app opens at the Build library without selecting a Build. The main menu contains Builds, Teams, Reference, World Map, and Mods, followed by a Tracking group containing Characters, Inventory, and Progress. The expanded sidebar lists Class seals, Travel & unlocks, Summons, and Quintar breeding as nested links under Progress, highlighting the selected page. Collapsing the sidebar hides these subitems; the Progress pages also provide their own navigation tabs. Mobile navigation uses one horizontally scrollable row, preserving the main destination order with a divider before the tracking destinations. Every destination keeps a visible label and keyboard access. Explicit page and record links still open their requested destinations. Build library, team scenarios, comparison views, character views, and settings sections have separate routes. Inventory observations, character captures and learning records, Build creation and editing, progress edits, custom-definition edits, and Game Setup collection also have their own addresses.

World Map uses `#/map`. Selected markers, map layers, and mod previews retain their view parameters in the address. A map link reopens the view without changing any saved Game Setup or Playthrough observations. Imported source choices still require the exact source to exist in the destination browser. Build drafts remain mounted while researching World Map or Reference; use **Return to build draft** to resume, and save before reloading or closing the tab.

Progress pages use `#/progress/seals`, `#/progress/unlocks`, `#/progress/summons`, and `#/progress/quintar`. The `#/progress` root opens the first page in the shared Progress navigation order and replaces the address with that page's explicit path. The Progress menu destination follows the same order. Progress record edit addresses remain `#/progress/<record-id>/edit`.

The Progress trackers use variants of a shared page layout for their header, page links, and gold total panel. Class-stage counters and the Quintar next-step panel extend that summary; acquisition confirmation notes remain visible in the unlock variant. The seals panel uses seal artwork, and the Quintar panel follows the next unmarked step's artwork, showing the Golden Quintar when the guide is complete. Each tracker retains its own controls and queued save behavior.

For example, `#/inventory/new` opens the inventory form, `#/builds/teams` opens tracked party plans, and `#/settings/game-setup` opens Game Setup settings. A character's Member screen uses `#/characters/<character-id>/current`, and class and skill records extend that path with `classes/<entity-reference>/edit` or `skills/<knowledge-or-magic>/<entity-reference>/edit`. Snapshot inspection uses `#/characters/<character-id>/history/snapshots/<snapshot-id>`, and comparison uses `#/characters/<character-id>/history/compare/<snapshot-a-id>/<snapshot-b-id>`. Each ID must belong to the selected character; missing snapshots show recovery controls without substituting the current snapshot.

A catalog definition preserves its exact catalog and revision pin, followed by slash-separated entity identity segments and a required readable name slug. Bundled definitions use the `v1` alias for that pin: `#/reference/catalog/v1/mod/moonlight-project/ability/565/100-pun-storm` opens Moonlight Project's 100-Pun Storm, and `#/reference/catalog/v1/base/monster/316/brutish-quintar-desert` identifies the native desert variant. Imported catalogs and composed Game Setups retain explicit pins in `#/reference/catalog/<catalog>/<revision>/<entity-path>/<name-slug>`. The identity resolves the definition; the trailing name describes it. Incorrect or outdated name slugs normalize to the definition's canonical slug without adding a history entry. Labels come from the selected catalog revision; reviewed routing labels distinguish the native Brutish Quintar variants. Base definitions use native database IDs such as `base/item/203/quintar-berries`; mod definitions use model IDs scoped to their project, and mode variants retain their additional identity segments before the slug. Arbitrary IDs from imported catalogs use `id/<escaped-id>/<name-slug>`. Identity and name segments containing URL-special characters or action words are escaped so they remain distinct from editor and search actions. Slugless and encoded-colon entity URLs are not accepted. See [publication verification](development.md#publication-verification) for source identity compilation and route contracts.

**Use with Tracking** is an optional collapsed section on saved Builds and Teams. Recording a build or adopting a Team requires explicit confirmation that it was applied in game; saving a plan alone never changes tracked state.

The build sheet opens directly at `#/builds/library/new` on desktop and mobile, and saves its initial checkpoint together with the build. Build fields are editable search inputs with anchored selection lists; they do not create free-text definitions. Their picker routes preserve search text through Back and Forward. Existing build and checkpoint links open the inline sheet.

Definition dropdowns and their create/edit dialogs extend the parent route. Universal search has an address too. Back and Forward traverse these layers while keeping the parent form available. A picker route opens a compact dropdown anchored to its field without making the form inert or blurring it. Create and edit actions open centered modal dialogs; returning from an editor restores the dropdown search. Cancel or the close button returns to the parent view; a directly opened dialog has a safe parent destination even without an earlier app history entry.

Team member editing stays inside the Team route. Its picker and member draft are temporary editing state; saving returns to the Team, and cancelling preserves pending Team fields.

URLs describe navigation, not a backup of unsaved form fields. Refresh can reopen the same form or picker, but unsubmitted input is not a durable saved record. Save the form before relying on a bookmark to preserve its contents. Navigation guards keep protected Build, Game Setup, and definition drafts open until they are saved or explicitly discarded. Universal search keeps an underlying form open until it is finished or closed before navigating to a result.

Personal record links depend on the active playthrough and browser storage at the same origin. A copied link does not transfer the referenced data to another browser or device. Import a native backup and select the relevant playthrough before opening its record links. A missing record or unavailable catalog revision produces a recovery message instead of silently opening a different record.

Planning pages use a persistent header for their title and commands, including Build and Team save actions. Tracking pages and Team adoption show the **Playthrough** selector; tracking pages and party-plan views also show **Party plan**. The latter selects a tracked scenario, separate from the character-independent Teams library, and **None selected** clears the selection without deleting a plan. Builds keep their own Game Setup. Manage reusable rules under **Data & settings > Saved setups**, then explicitly apply a saved revision under **Playthrough** when it should govern tracking.

Playthrough and party-plan choices persist in browser storage. Their selector search and open state are temporary and do not add URL history entries. A Playthrough switch returns to the current destination's list, avoiding reuse of another Playthrough's record address. Selecting a party plan while browsing party plans opens its address. Context changes check open drafts even when they leave the route unchanged. A party plan's selector entry shows its pinned Game Setup and identifies differences from the Playthrough's selected revision.

Import previews depend on the file selected in that browser session. Their URLs cannot restore the file bytes after refresh; reopen the local file to review the preview again. Visiting any route does not approve an import or perform a saved-data mutation.

Reference and inventory filter parameters remain in the address where needed. Source filters display readable labels while retaining the exact source values for filtering and provenance. Search results and reference selections use semantic paths; JSON-encoded target and selection queries do not navigate to records.

Mods open temporary Reference pages with a `library-mod` identity in the query. List searches, filters, and detail links retain that catalog scope. A reload decodes the selected bundled source again or reuses its latest explicitly saved revision; it does not import the mod. Temporary filters are omitted from the standing Reference's session storage. Clearing search filters keeps the selected catalog; **Return to Reference** restores the standing library and its previous search.

A slot action in the recorded character sheet opens the capture route with its definition-picker descendant. The picker focuses search on opening and returns focus to its field on closing. A changed snapshot form blocks outside dismissal, Escape, and navigation away until saved or explicitly cancelled, and warns before browser refresh. After a storage failure, closing the form leaves the application recovery draft available for Retry save or backup export.
