# Account cryptography feasibility

The account cryptography gate uses `@serenity-kit/opaque` 1.1.0 (MIT) and the browser-only encryption layer. Production remains assets-only. The isolated preview configuration selects the account Worker with customer, signup and email gates closed pending hosted qualification. Local cryptography proof does not activate those capabilities or establish production readiness.

## Passwords and identities

Passwords contain at least 15 Unicode code points and at most 1024 UTF-8 bytes. Unpaired UTF-16 surrogates are rejected before encoding. Spaces and decomposed Unicode are preserved exactly: no trimming, normalization or truncation. The pure policy lives in `src/account/password-policy.ts`.

Client `finishRegistration` and `finishLogin` explicitly receive `{ 'argon2id-custom': { memory: 65536, iterations: 2, parallelism: 1 } }`. The [pinned release source](https://github.com/serenity-kit/opaque/blob/%40serenity-kit%2Fopaque%401.1.0/src/lib.rs) forwards these values to Rust Argon2 `ParamsBuilder`, with Argon2id version 0x13. [Rust Argon2 defines memory as 1 KiB blocks](https://docs.rs/argon2/0.5.3/argon2/struct.Params.html), so this requests 64 MiB, two iterations and one lane. The package's default profile is not used. Its declarations put key stretching on the finish calls; the README's reference to start calls is not the implemented API contract.

Stable credential identifiers are `crykit/password/<account-id>` or `crykit/recovery/<account-id>`, where the suffix is canonical base64url for 16 random bytes. They are not emails or usernames. All relevant client/server calls bind the credential ID as the client identity and `crykit/accounts/opaque/v1` as the explicit server identity. Changing the identity, KDF profile or setup breaks the existing credential's proof. Preserve these parameters with the credential format.

Only the client's 64-byte OPAQUE export key derives the password wrapping key. The server-visible session key is omitted from both adapters and cannot unlock the wrapped 32-byte account key or decrypt an account revision. The client wraps its independently generated account key; it never sends that key, a plaintext password or the export key to the server. The server adapter imports no browser encryption/decryption module. This is a key-separation boundary, not protection against malicious browser code or an origin serving modified JavaScript.

Revision encryption and authentication use the pinned libsodium secretstream implementation. Stored SHA-256 digests and their encodings are independent of the hashing provider: bounded cipher buffers use the [platform digest API](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/#SubtleCrypto-method-digest), with the pinned sodium implementation retained when native hashing is unavailable. Decryption captures its ciphertext before awaiting a digest so the authenticated stream consumes exactly the hashed bytes. Native metadata hashing keeps one owned buffer of at most one protocol plaintext chunk (4 MiB); the platform digest makes its own input copy. Owned plaintext is cleared on completion or cancellation, and source chunk boundaries are preserved. Larger sources and insecure guest contexts retain incremental hashing and backpressure. The provider change requires no persisted-data migration.

`OPAQUE_SERVER_SETUP` is a configured long-term secret. Generate it once when provisioning, back it up securely and restore the identical bytes. Never regenerate it on startup or silently replace it during recovery. Only the isolated local fixture/dev command creates a disposable setup. A matching restored setup preserves credentials; a different setup fails authentication. Unknown users pass a null record into the pinned library, which delegates dummy-record construction to opaque-ke. Authentication failures have the same public error code; randomized protocol responses are the same fixed size, not identical bytes. Distributed route limits are implemented below; production response-timing analysis remains an activation gate.

## Worker packaging and build contract

The published ESM embeds WASM as base64 and starts asynchronous `WebAssembly.compile` during module initialization. An unadapted bundle hung in local workerd. `scripts/opaque-worker-module.mjs` verifies the complete pinned ESM SHA-256, extracts the exact embedded module and replaces only the loader prefix with a static `.wasm` import. The wasm-bindgen wrappers, initialization and cryptographic bytes remain unchanged. Source mismatch fails generation, requiring review before a dependency upgrade. The browser uses the published package without this adaptation.

`node scripts/build-account-tests.mjs --prepare-opaque` deterministically regenerates ignored static-WASM assets and the upstream license. The local Wrangler config aliases the package to that generated Worker module and reruns generation through its custom build command. Vitest's bundle-only watch triggers include the generator and package source. The regular fixture build regenerates before bundling, then constructs Miniflare modules from emitted metadata, including `CompiledWasm`; it does not rely on config autoload or stale ignored modules.

The account-service configuration, including isolated preview, must use the same reviewed generator, package alias and collected WASM handling for every deploy, watch and dry-run build. It must provision the setup secret through the owning service workflow. Do not copy generated modules into a deployment or activate existing assets-only configs to bypass this preparation.

The local proof executes the emitted loopback Worker and an independent emitted server-adapter Worker with production-equivalent packaging. The actual inactive production entry remains separate, excludes local probes/browser private-key code and rejects fixture identity. It has no authentication consumer at this stage. Once account routes import the adapter, repeat the composed real-workerd authentication proof against that actual production entry before service activation. Independent composed-flow review is required before that activation.

The composed browser proof registers, stores an account envelope and encrypted revision through HTTP/D1/R2, and recovers the same key and revision in an independent browser context. HTTP and storage artifacts exclude the password, export key, recovery secret, account key and plaintext revision; safe-event assertions use the real workerd fixture.

## Guarded D1 transactions

`worker/db/guarded-batch.ts` provides `runGuardedBatch(db, guard, statements)` for a single atomic service command. Its first prepared statement inserts a scalar predicate result into the CHECK-constrained `transaction_guards` table from `worker/migrations/0001-service.sql`. A false, NULL or zero-row scalar SELECT becomes zero and raises a real SQL constraint error. A zero-row UPDATE or an INSERT conditioned by WHERE does not provide this guarantee. Guard insertion, caller statements and guard deletion run in the same D1 batch; success returns only caller statement results, and failure rejects without a separate cleanup transaction. The primary key isolates concurrent guard rows; successful and rejected commands leave no guard rows behind.

`SqlGuard.sql` must be a trusted internal scalar SELECT that returns one truth value for the complete command. Bind all request-derived values using `SqlGuard.bindings`; never accept SQL text, table names or predicate fragments from the browser. The helper supplies transaction mechanics, not authorization. Credential activation must include expected credential/account revision and account policy; sync publication must include ownership, every expected head, ready owned dependency closure and account policy; quota reservations must include capacity and reservation/idempotency state; admin commands must include target revision/policy and their authorized command preconditions. Put each command's durable receipt and audit records inside the guarded batch with its state changes. Later route owners must use this primitive and review their complete predicates before activation; no account or admin handler is established by the feasibility fixture.

Validate and deduplicate bounded expected-head arrays before binding their JSON. A scalar `NOT EXISTS (SELECT ... FROM json_each(?) ...)` predicate can compare `json_extract` values against account-scoped heads in one statement, using `IS`/`IS NOT` to distinguish a missing head from a concrete revision without SQL NULL equality gaps. The local test covers the maximum commit head set, including an expected absent head. Account ownership must constrain every lookup; JSON is prepared data, never SQL authority. Snapshot reads outside the batch cannot replace these predicates, because a concurrent command can invalidate them before writes begin. Do not mix unrelated database bindings or nontransactional R2/email effects into the SQL transaction guarantee.

[Cloudflare documents D1 batches as transactions whose failed statements roll back the sequence](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), checked on 2026-10-11. The real Miniflare/workerd fixture observes exactly one successful competing expected-head command, the winner's dependency/head/receipt/quota state and no loser graph. It also induces SQL errors after the guard, dependency insertion, head update, quota update and receipt insertion, and compares the complete prior database state after each rejection. Separate database instances repeat these observations. Raw database exceptions remain internal; future HTTP callers must classify conflicts and operational failures into the safe API error envelope without exposing SQL or bindings.

This proves the local transaction primitive with the pinned runtime, not production D1 concurrency, topology, workload cost or the correctness of future composed authorization predicates. Before activation, repeat the same competing-writer and rollback probes against isolated deployed D1 bindings, including bounded JSON head predicates, credential activation, quota reservations, sync publication and audited admin commands. Measure CPU, latency, rows read/written and resource limits under representative contention. Preserve assets-only production and keep preview cloud capabilities closed until their independent hosted concurrency and resource gate passes.

## Durable transactional email

`worker/email/jobs.ts` stores recipients and service capabilities only inside authenticated encrypted payloads. A keyed digest binds the exact message kind, recipient, capability and expiry to a stable random job ID; request correlation changes do not change command identity. Reusing the ID with different message material fails. AES-GCM associated data binds payload format, job ID and request digest, preventing ciphertext transplantation. The dedicated `EMAIL_STATE_SECRET` and HKDF purposes are separate from customer account keys and session/cursor/capability secrets. Losing or replacing this service secret requires explicit recovery; the sender cannot substitute a customer key.

`prepareServiceEmailEnqueue(message, jobId, context)` encrypts and validates before writing and returns `{ guard: SqlGuard, statements: readonly D1PreparedStatement[], jobId, requestDigest }`. A01/A02/C01 conjoin this trusted guard with their authority predicate, bind both sets of parameters in SQL order and execute the authority writes plus prepared statements through one `runGuardedBatch` call. Do not execute nested/separate enqueue transactions or expose SQL/guard values to clients. The guard allows an exact existing request digest; its insert and queued-audit statements become no-ops without resetting the existing ciphertext, expiry, request ID, eligibility, attempts or outcome. Different material under the same job ID fails the guard. `enqueueServiceEmail` is the convenience wrapper for service operations that have no accompanying authority mutation. Real D1 tests verify rollback in both authority/outbox failure directions, audit failure, and exact retry after acceptance.

Enqueue, lease acquisition, persisted send-start, result recording and their audit rows each use the CHECK-first D1 batch primitive. Only one competing dispatcher can acquire an attempt. The durable `leased` stage is known-unsent; committed `sending` crosses the external-effect boundary. There is no transaction spanning D1 and email. A lost send response or result-write failure cannot establish that nothing was sent: the job remains uncertain, including if its capability expires or authority is revoked while the native call is in flight. Recovery compares its observed attempt stage again inside the guarded transaction so a concurrent send-start cannot be reclassified as unsent. A stale completion cannot overwrite a recovery winner or emit a false accepted status.

The automatic/send attempt budget is cumulative and never exceeds three per job, including manual retries. `retryEmailJob(jobId, context)` restarts only a failed, eligible, unexpired, known-unsent job with budget remaining and never resets attempts or reenables eligibility. Suppressed, expired, cancelled, accepted and uncertain jobs cannot use Retry. `resendServiceEmail(sourceJobId, resendId, context)` allows one explicit resend for an eligible accepted/uncertain root before expiry; concurrent requests coalesce to the same child even with different proposed IDs. A child cannot create another resend. The original outcome stays intact. Expired capabilities require a future authorized caller to issue a new capability, not reuse the retained one. Missing sender readiness or unknown shared-account headroom leaves jobs waiting without spending an attempt.

These helpers are internal service operations, not authorization by possession of a job ID. A01/A02/C01 caller authority records must retain the root job ID. Capability consumption/revocation, account deletion/restriction and invitation revocation must include `emailInvalidationStatement(db, jobId)` in the same guarded D1 transaction as the authority change. This prepared-statement helper executes no transaction itself. Invalidating any linked root/child disables the complete resend lineage. Lease acquisition, manual retry, resend creation and persisted send-start all require root eligibility; no client can supply eligibility. Known-unsent work is cancelled, while an already committed send-start preserves its accepted/uncertain outcome. The mail cannot retract an already-started native send and never unlocks encrypted data.

Sanitized job status exposes only random job/request IDs, job state, delivery status, attempt count, next-attempt time and authored error codes. Safe events and durable email audit omit recipient, capability, provider message ID and raw provider errors. Payloads are erased after expiry through bounded maintenance. Terminal attempt detail expires after seven days, audit after 90 days, and nonsecret identity metadata is removed after its audit horizon and any dependent resend records. Dispatch must run regularly for these maintenance horizons; provisioning must supply and monitor the schedule. Hosting log/aggregate retention remains an operational activation gate.

Fixed templates use `/#/account/verify/<capability>`, `/#/account/confirm-email/<capability>` and `/admin#/accept-invitation/<capability>`. Loading a link does not consume it. A05 and the admin UI must clear its fragment before an explicit confirmation POST; no confirmation UI or real auth/admin caller is established by the local email proof. All required kinds are exercised through reserved-domain local capture, including retry/quota, expiry, suppression, uncertainty, cancellation lineage and actual SQL audit/result failures. Repeat composed signup, email-change and operator-invitation journeys when those owners integrate the service, and repeat isolated native/D1 resource and concurrency gates before activation.

## Verified account access and session authority

Signup reserves a random account ID and lowercase screen name for 24 hours. Email lookup trims surrounding address whitespace and compares case-insensitively without provider-specific dot or plus folding; the original trimmed delivery address remains private. Reserved product and administrative names cannot be registered. Registration stores only the OPAQUE record and encrypted account-key envelope in pending state. A guarded D1 batch writes that state, its idempotent transaction receipt, verification hash and root email-job linkage together with the prepared encrypted outbox statements. No account or credential becomes active until the single-use, 30-minute verification capability is consumed. That activation batch creates the account and credential and invalidates the complete verification email lineage. Verification grants no session or decryption key; a subsequent OPAQUE login unlocks the account key in browser memory.

`DUMMY_IDENTITY_SECRET` is a dedicated, stable, server-only 32-byte secret encoded as canonical unpadded base64url. Provision it independently from session, cursor, capability and email secrets and restore the original bytes with `OPAQUE_SERVER_SETUP`. Unknown normalized login targets use a domain-separated HMAC under this secret to derive stable, distinct dummy account-shaped identifiers. `credentialIdForRole` applies the same frozen password/recovery identity format to real and dummy IDs. Existing accounts use their real account suffix for both roles, including a missing role whose OPAQUE record remains null. Role availability must not change the public identity suffix. Dummy values never allocate accounts or authorize a login. Changing or losing this secret changes repeated unknown-target identity behavior; rotating rate-limit buckets must never change it.

Authentication starts share distributed target and network limits: ten starts per ten-minute normalized-target window and thirty per ten-minute network window. Signup and login finishes share a separate finish budget, with ten attempts per ten minutes per kind-and-attempt target and thirty per ten minutes per network. Verification has its own budget with the same limits per capability and network. These checks precede authority lookup, consumption and expensive proof or email work, including schema-valid invalid attempts and receipt retries; rate rejection preserves unconsumed authority. Permitted exact signup retries retain their original receipt. Resend limits are one per minute and five per hour per target, with a network limit as well. Counter keys are HMACs of their opaque targets or network inputs; network keys rotate daily and never retain raw IP addresses. Counters expire within an hour and expired rows are removed on the next limit check. Within the rate budget, invalid or expired login finishes consume their attempt once. Missing email readiness disables signup and resend, while existing OPAQUE login, session access and data authorization remain available.

The `__Host-crykit-session` cookie is always Secure, HttpOnly, SameSite=Lax and Path=/, without Domain. Ordinary sessions have an eight-hour idle lifetime and 24-hour absolute lifetime; remembered sessions have seven-day idle and 30-day absolute lifetimes. Only remembered cookies receive Max-Age. Renewal replaces the token and nonsecret session ID while retaining the original authentication stamp and absolute expiry. A new login revokes the incoming replaced cookie's session in the same batch that creates its device and session. Logout requires the current cookie, CSRF and captured matching nonsecret session ID; a mismatched captured ID does not revoke or clear the newer session.

`requireCustomer` validates the hashed cookie, account access, device revocation and both expiry boundaries. Private mutations also require the exact configured Origin and session-bound `x-csrf-token`. `requireRecent` rejects authentication stamps ten minutes old or older. `assertCustomerWrite` rejects pending, missing, revoked, blocked, deleting and read-only authority. Its preflight result is not a transaction guard: later upload/commit/publication code must include the full live-session, active-account and verified-state predicate in its own F04 batch so revocation cannot race a write. `liveSessionSql` exposes the shared captured-session predicate and takes bindings in order: session ID, account ID, current time, current time.

Account responses contain only the owner's metadata, capacity, policy, bounded device list, session ID and CSRF. They expose no private document categories. Account keys, OPAQUE export keys and passwords never enter server storage or safe events; session and verification authority retain keyed hashes rather than bearer tokens. Browser `registerAccount` discards the new key after submitting its encrypted envelope; `loginAccount` returns an in-memory `UnlockResult`. Local remembered-key persistence and profile lifetime belong to the later profile integration.

The local dev command creates an isolated migrated database state directory and per-port synthetic secrets for each invocation. Its captured-email browser test exercises the real production authentication handlers and proves browser acceptance, HttpOnly invisibility, authenticated metadata access and rotation of the unchanged Secure host cookie. The production bundle imports the reviewed static-WASM OPAQUE alias; local capture and probe modules remain excluded. Hosted routing, managed-secret restoration, native email acceptance and provider Free-plan usage measurements still require the account-service activation gates. This local proof does not activate hosted cloud capabilities or change assets-only production.

## Credential changes and recovery

The account metadata response includes `credentials: { passwordRevision, recoveryRevision }`. A null recovery revision means recovery is unconfigured; the account UI derives its persistent reminder from that value, including after an explicit signup skip. Credential registration captures the account, current session, role and revision without replacing working access. Activation uses the shared guarded batch to recheck live session/device authority, active moderation state, the strict ten-minute authentication boundary and the expected credential revision. It writes the new OPAQUE record, wrapped existing account key, revision and immutable transaction receipt together, and revokes other sessions only on success. Password changes never rewrite private workspace bodies or change the account key.

Recovery codes contain a random 32-byte secret and a four-byte SHA-256 checksum, encoded as grouped Crockford Base32. Parsing and checksum validation complete locally before any request. OPAQUE receives a canonical base64url encoding of only the secret; the wire carries only its OPAQUE transcript. The recovery envelope uses the F02 recovery HKDF domain with the decoded secret. `loginWithRecovery` returns an unlocked result only after both protocol authentication and local envelope decryption succeed. Replacing the recovery credential invalidates the old code for online access. The service never receives raw recovery secrets, passwords, client export keys or plaintext account keys.

`changePassword` resolves only after confirmed activation. If the activation response is lost, a transaction lookup discovers the candidate receipt and an exact replay of the saved commit body verifies its request digest. A receipt alone cannot prove that a reused transaction ID belongs to the attempted change. `CredentialChangeUnconfirmedError` carries the transaction ID when confirmation remains unavailable. `resumeCredentialChange` retries the same memory-only command for its captured account and session, returning the replacement recovery display only after confirmation. Pending commands expire after ten minutes, with expiry enforced on preparation and resume; `clearPendingCredentialChanges` drops their references explicitly. Lock, sign-out and profile switching must call this cleanup seam. No pending command or recovery display is written to durable plaintext storage. Reloading, expiry or explicit cleanup loses the pending command; none cancels a server transaction, and an online password change can still have succeeded. `CREDENTIAL_CHANGE_LOCAL_STATE_CLEARED` describes only local cleanup, never server rollback. If a pending command is gone, use fresh password sign-in or recovery to establish working access. The account UI must distinguish unconfirmed activation from a rejected change and offer reauthentication/reconciliation rather than asserting that the old password remains active.

The offline profile integration calls `updateOfflinePassword` only after `changePassword` or its resume returns confirmed success, under its captured profile generation. A later local envelope-write failure is a cache failure after a successful online change. Remembered account-key wrapping needs no rewrite because the key is unchanged. Generation fencing and durable offline writes belong to the profile integration; credential handlers do not create a substitute local store.

Reauthentication uses a session-bound, one-shot password or recovery OPAQUE attempt. Its guarded finish refreshes only the same session's authentication stamp and preserves absolute expiry. Login cannot redeem a reauthentication attempt. Username changes require an active account, recent authentication, a matching account revision and a unique nonreserved lowercase name. Email changes preserve all account and credential IDs. Starting a change increments the account revision, replaces outstanding email authority and atomically invalidates its complete outbox lineage while creating the new capability and prepared email job. Confirmation requires both the capability and recent live authentication; it atomically consumes authority, updates the address and receipt, invalidates verification delivery and enqueues a linked security notice to the old address. Email unavailability gates email changes, never password/recovery changes.

For browser account verification, `CRYKIT_ACCOUNTS_HTTPS=1 npm run dev:accounts` enables the pinned Wrangler TLS path with a disposable OpenSSL loopback certificate and matching `SERVICE_ORIGIN`. It requires `openssl` and changes no trust store. The matching Playwright configuration ignores certificate validation only in its test contexts. Use HTTP for the Chromium proof's service-worker cache checks and HTTPS for WebKit's Secure-cookie journeys; Chromium's service-worker certificate validation can reject a self-signed worker script even when its page context ignores HTTPS errors. The ordinary HTTP dev mode remains available. Neither harness changes production cookie security, provider state or hosted routing. This self-signed certificate limitation does not satisfy preview verification; release acceptance must exercise Chromium against trusted preview HTTPS.

## Verified device approval

A requester generates a libsodium sealed-box key pair, a random request ID and an independent request capability in transient memory. Start sends the public key and SHA-256 capability hash with the email; both known and unknown emails receive a fresh opaque pairing context and a ten-minute receipt. Unknown requests never gain account authority. The comparison fingerprint is the first eight SHA-256 bytes of UTF-8 `JSON.stringify([pairingContext, requestId, requestPublicKey])`, rendered as four uppercase hexadecimal groups. Both account screens must display that complete material; the approving user must explicitly compare it before calling `approveDevice`. An authenticated pending-request list supports discovery, and public request-ID lookup provides a fallback without exposing capability or private-key material in URLs.

The approver re-fetches owned pending metadata, verifies its public key, account, context, expiry and fingerprint, then seals the unchanged account key together with the exact account/request/context/expiry tuple and a separate random 32-byte completion secret. The server stores only bounded public metadata, sealed ciphertext and capability/completion hashes. Ciphertext transport requires canonical unpadded base64url, rejecting impossible lengths and nonzero unused trailing bits before persistence. Completion requires both requester capability and decrypted completion secret. Its D1 guarded batch checks the request's state, hashes and strict expiry, plus the approving session's complete live account/device/session authority, then consumes the request and creates the requester device/session atomically. A replay cannot issue another session. The incoming replaced cookie is revoked in that same transaction. A sealed box does not authenticate a sender by itself; server-owned approval authority and exact decrypted context validation are both required.

`GET /api/v1/account/devices/requests` returns `{ requests, hasMore }`, with at most 20 owned, unexpired pending requests ordered newest first. Each request contains `accountId`, `requestId`, `pairingContext`, `requestPublicKey`, `fingerprint` and `expiresAt`; no email, capability, private key or completion secret is exposed. A capped response is explicitly incomplete. `GET /api/v1/account/devices/requests/:requestId` uses the same metadata and neutral invalid-request response for missing or foreign IDs. Approval rechecks live authority and exact public key inside its transaction, independently of the client's preflight.

Account metadata exposes `devicePage: { devices, currentDevice, hasMore, nextCursor }` alongside its existing credential revisions, session and policy fields. `GET /api/v1/account/devices?cursor=...` continues the scan. Pages contain at most 50 rows in descending creation-time/ID order, with the current device pinned separately even when it lies outside the page. It can also occur in `devices`; displays combining the pinned row and page must deduplicate by ID. Cursors are authenticated, account-scoped and expire ten minutes after the initial page; continuing a scan preserves that expiry. Restart an expired scan from its first page. Newly created devices appear on a refreshed first page, not in the already traversed prefix of an older scan.

Device removal revokes every associated session and cancels approved-but-unconsumed grants issued by that device. Unapproved requests have no authenticated device association; they remain bounded by expiry or explicit rejection. Removal blocks future service access, does not rotate the account key and cannot erase keys or data already received. The account UI must describe that limit plainly.

`waitForDeviceApproval` polls only while visible, within the request lifetime and bounded attempt count, under the caller's abort signal and profile-validity check. Its abort/visibility listeners and expiry deadline cover in-flight HTTP and inter-poll delays; a cancellation race settles the operation even if a transport ignores its AbortSignal, while late results remain fenced. Status has a separate distributed budget so normal polling cannot consume the start budget. The profile owner must abort the supplied signal immediately on lock, sign-out or profile changes and call `clearDeviceApproval`; changing `isCurrentProfile` alone is not a lifecycle notification, and that predicate is checked before requests and before accepting responses. The profile integration owns generation fencing for in-flight start/approval/completion and any subsequent persistence. Requester expiry timers and completion cleanup zero owned private-key buffers and drop capability references. This path creates no object URLs or persistent plaintext store. Remember-device selection belongs to the account UI and starts unchecked; the completion API requires an explicit boolean.

## Local account access and session ordering

The account lifecycle owns its key and online session context outside React. UI retains an opaque `{accountId,generation}` profile token and calls lifecycle actions. Every asynchronous key use checks its generation before and after work; lock, sign-out and switching abort owned work, clear credential preparation and device-approval secrets, erase owned key buffers, revoke registered object URLs and notify projection cleanup callbacks. Ciphertext remains in its owning repository. A cached key permits local reading even when online authority has expired or been revoked; it never proves upload or device-approval permission.

The separate versioned device store contains opaque account IDs, local password envelopes, remembered envelopes, the last observed session ID and exact pending session IDs. The last observed session ID is only a revocation target after restart and never grants online authority. The store contains no account documents or HTTP bearer tokens. Password envelopes use the pinned local Argon2id policy and never leave the device. Remembering a device is optional and defaults off. Remembered access wraps the account key using a separate nonextractable Web Crypto AES-256-GCM key, random 12-byte IV and authenticated account context; IndexedDB structured-clones that key with its envelope. This protects storage within a browser profile, not with OS or hardware credentials. Disabling remembered access removes the remembered envelope and device key together. Failed storage writes retain the preceding durable record and are reported separately from successful server credential changes.

Participating login finishes, recovery login finishes, device completions, renewals and pending-session reconciliation share the exclusive `crykit-account-session-v1` Web Lock. Acquisition and each native request have separate 30-second deadlines. The callback remains pending through fetch and body settlement, including cancellation, so an outstanding response cannot race a successor cookie write merely because a timeout promise completed. Cancellation cannot undo a server commit or an already-applied cookie. Before attaching online authority, clients compare strict account metadata to the key owner and use the actual session and CSRF values. Uncertain operations leave online access disconnected for explicit reconnect or fresh authentication. Local password derivation is outside the network deadline.

Web Locks coordinate cooperating clients in the same storage bucket. They do not serialize arbitrary callers, extensions, other storage partitions or older account clients that omit this protocol. A known incompatible active account client requires a reload/upgrade boundary before account session operations; guest-only clients have no account cookie writer. When Web Locks are unavailable, online session changes report unavailable access while guest editing and local unlocking continue.

Logout is cookie-neutral: its exact current-session predicate revokes authority without emitting a clearing header that could delete a newer tab's cookie. An invalid residual HttpOnly cookie grants no access. Sign-out first records the original opaque account/session IDs and removes remembered material in one local transaction, then attempts authenticated revocation. Offline or uncertain revocation stays pending across restart. Fresh authentication to the same account may reconcile each recorded ID through `POST /api/v1/account/sessions/revoke`; another account's IDs remain pending. The route checks live caller authority and target ownership in its guarded transaction, preserves existing revocation timestamps, returns neutral missing/foreign results, and emits no cookie. It cannot revoke a newer session unless that exact ID was submitted.

Removing account data from a device is a distinct confirmed action with explicit backup or discard recovery. The account repository supplies real pending-work, export and removal operations; the lifecycle does not invent a substitute account database. Removing a remote device blocks future server access but cannot erase a previously downloaded key or local ciphertext.

The lifecycle browser suite runs actual Worker/client response interleavings and persistent-browser restart. Its owned frontend forwards requests unchanged to the same local Worker and configures only the excluded test entry with that exact loopback origin. Closing the frontend listener and active connections must make an uncached same-origin API request fail before the test counts disconnection. The browser then restarts, loads cached modules, opens IndexedDB and unlocks locally; reopening the same frontend reconnects the original Worker/D1 for exact pending revocation. TLS certificate acceptance is scoped to disposable local contexts/listeners. This avoids WebKit offline emulation while preserving production cookie flags and Origin validation. The ordinary-session restart case never clears or injects cookies; deliberate cookie loss in the remembered-envelope case is separate evidence. Run each engine against a fresh local harness to preserve real shared rate limits rather than weakening their budgets.

## Administrative privacy and recovery acceptance

Administrative reads use the same production Worker entry as customer and public routes. A valid administrator cookie is not a customer session and cannot fetch private revision descriptors or ciphertext. The panel receives account, opaque storage and service metadata plus intentionally public share snapshots. Private build/file/category names, encrypted descriptors, envelopes and key material do not enter those responses, the panel DOM, downloads, browser storage or safe telemetry. The signed local browser acceptance encrypts a private sentinel with the actual revision cipher, publishes it through ordinary customer APIs and checks that the customer can read the exact ciphertext while the administrator cannot.

New member application sessions commit a `session.login` audit atomically with the session. A failed audit grants no session. Routine session reads do not create login audit rows. Bootstrap, confirmations, privileged commands and full-email detail reads retain their attributed audit records; authenticated role denials use the existing command audit. These audit tables retain 90 days. Unauthenticated assertion failures use bounded safe request diagnostics rather than an anonymous database-write sink; their provider log retention is a separate deployment setting. Logs contain authored operation/stage/code values and request/job correlation, not assertions, cookies, email addresses, CSRF values or private content.

Recovery captures exact admin authority, immutable receipts, audit and settings together with the separate email/service job revisions. It discards pre-membership access sessions, member sessions, action confirmations and previews. Independent acknowledged operator removal, invitation cancellation, account deletion and share Stop events are reconciled before reopening. Pending admin revocation intents prevent capture admission and promotion. A restored removed identity remains forbidden; an old application cookie cannot regain authority. An allowed operator obtains a new application session after its Access signature, issuer, audience, lifetime and reconciled membership are checked. A still-valid provider identity can supply that assertion: this does not prove a new identity-provider login or MFA prompt. See the [recovery runbook](accounts-recovery.md).

### Hosted activation probes

Local signed fixtures exercise routing and cryptographic verification, not hosted Access policy. Keep production high-impact confirmation disabled until the deployment owner records each of these checks against the actual environment:

- Enumerate every enabled custom, preview and Worker hostname. Probe the admin HTML, protected assets, ordinary API, invitation entry and confirmation entry through each hostname. Disable unintended hostnames; reject unconfigured origins and forged identity headers. Verify guest and customer paths remain available.
- Inspect parent and more-specific Access application precedence. Ordinary identity must fail the confirmation audience; confirmation identity must fail ordinary management routes. Verify the configured trusted issuer/JWKS and a real non-operator identity, not just an email header or allowlisted domain.
- Require independent MFA on every high-impact login. Test alternative identity providers, AMR/session caching and provider cookie switching. Confirm the separate action window cannot exceed 15 minutes and expired confirmation cannot execute a command.
- Verify admin HTML, assets and API responses remain private and no-store across CDN/browser cache behavior. Verify provider logs and native email transport separately from captured local fixtures, including their retention and resource limits.

The deployment/activation owner records these hosted results; local acceptance does not enable providers, real email, MFA policy or production service bindings.
