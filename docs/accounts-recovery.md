# Encrypted service recovery

Service recovery preserves server identity, encrypted account envelopes, immutable ciphertext and the metadata needed to interpret them. It never decrypts a workspace or obtains an account's plaintext key. The original account password must still unwrap the original account key after recovery. Account exports and device recovery are separate features.

Capture and restore are internal operational functions. There is no customer/admin endpoint for arbitrary SQL, backup creation or restore. The read-only authenticated `GET /api/v1/account/recovery` reports `state`, `lastVerifiedAt`, `ageMs` and a bounded `code`. A paused backup does not disable ordinary account use. `MEASURED_POLICY_REQUIRED` means that capture has no admitted resource envelope; `CAPTURE_NOT_ADMITTED` means that the source, readiness or capacity checks rejected the attempt. Existing verified points remain readable while a new attempt is paused. Explicit reverification retains the last verified point and reports `VERIFYING` until its bounded scan completes. A failed locator/root read, integrity check or original-secret check records a durable paused condition without advancing that recovery point.

## Capture authority and lifetime

Migration `0011-service-backups.sql` installs exact row and encoded-byte counters for the maintained table/column projection in `worker/jobs/recovery-projection.ts`. The projection contains account identity and encrypted credentials, device and security-notice records, email delivery history, sync sequences/publication epochs, reservations and storage generations, chunks/descriptors/dependencies, membership and mutation/head history, publication pins/work/certificates, shares, deletion intents, service jobs and audit. These tuples are source evidence, not a recursive snapshot of earlier snapshots. New authoritative tables must be added to the projection, counters, restore ordering and invalidation rules by their owning migration. Operator/invitation records are not represented before their owning schema exists; an independent ledger event requiring unsupported authority keeps restore closed.

A single guarded D1 transaction checks authoritative rows, encoded bytes, maximum row size, dependency edges, work, statement budget, temporary reservation and global capacity. It rejects incomplete/unsafe storage generations and deleting accounts. The same transaction copies immutable tuples and claims all ready generation pins. Cleanup uses those exact pins, so it either claims an eligible generation first and prevents capture, or loses to the capture pin. Later live commits cannot change the captured sequence, publication epoch or promised object identity. The maximum recorded row size is a conservative high-water value; deleting a large row does not silently lower it.

`SERVICE_BACKUP_POLICY` is a versioned JSON object with `version:1`, `maxRows`, `maxBytes`, `maxEdges`, `maxWork`, `maxTemporaryBytes`, `maxStatements` and `maxRowBytes`. There is no default admitted policy. Each value must come from measurements for the actual deployment, including concurrent application load. The codec admits source tuples no larger than 1,900,000 bytes to leave room beneath D1's row limit. This only pauses service capture; it does not impose a smaller customer cloud quota or remove protected history. Immutable ciphertext references use the accepted sync chunk bound (`plainChunkBytes + streamOverheadBytes`), independently of the metadata row limit.

`captureServiceSnapshot(context, snapshotId)` advances one durable step and returns a `JobReceipt`. The owner repeats the same canonical opaque ID while the receipt is `running`; `complete` means all referenced bytes were verified. A `waiting` attempt requires diagnosis and a new admitted capture ID. Page export handles a bounded fragment of one source tuple, ciphertext copy handles one immutable chunk, and index/verification work handles one item. Metadata fragments use random AES-GCM nonces and snapshot/page associated context under `SERVICE_BACKUP_KEY`. Encrypted index links authenticate the complete item sequence and root manifest. Ciphertext is deduplicated by original immutable object identity and exact digest across retained snapshots. Every copy and verification reads exact bytes, length and SHA-256; an ETag or successful PUT is insufficient.

Every newly allocated backup or restore object has a charged one-shot seed, original seed ETag and distinct permanent content-free marker. Initialization uses create-if-absent; payload writes use only the original seed predicate. Lost responses reconcile the exact assigned object rather than starting another initializer. Expiration atomically claims the final reference before fencing. Payload charges are released only after reading the exact assigned marker and proving it differs from the authorized seed ETag. Unsafe fences remain charged. Managed keys are never deleted, expired or reused, and delayed writers cannot replace verified markers.

`expireServiceSnapshot` advances explicit expiration in bounded steps. It does not select snapshots by age or make a quota-driven protected-history eviction decision. Shared ciphertext survives while another snapshot references it. Account deletion cancels unfinished snapshots before removing their source generations; completed retained snapshots remain independently subject to the deletion ledger and explicit expiration. No further backup copy for a deleting owner is admitted. Snapshot locators and minimal permanent control records survive expiration; an expired locator cannot make fenced payload recoverable.

## Closed restore and original secrets

The original service secrets must be available independently of the backup encrypted by them. `worker/operations/recovery-secret-source.ts` provides a Node-only reader for an explicitly supplied protected structured file. The record is `{version:1, environment:"local"|"preview"|"production", secrets:{...}}`, with exactly `OPAQUE_SERVER_SETUP`, `DUMMY_IDENTITY_SECRET`, `SESSION_SECRET`, `CURSOR_SECRET`, `CAPABILITY_SECRET`, `EMAIL_STATE_SECRET` and `SERVICE_BACKUP_KEY`. Use the original values, never newly generated substitutes. The reader requires a regular file owned by the invoking user, no group/other permissions, no symlink and the requested environment. Configuration stores the source path/identity; values must not enter logs, command arguments or tracked files. Provisioning and hosted secret installation belong to the deployment workflow.

The authenticated manifest stores domain-separated fingerprints of every required original secret. Missing, malformed or syntactically valid mismatched originals reject recovery before metadata installation. The backup key cannot recover itself. Preview and production need independent source records, databases, object buckets and independent revocation ledgers.

The operational sequence is:

1. Provision a separate, never-served staging database and object bucket with the expected schema. Load the explicitly named original secret source and preserve access to the original private backup bucket and independent revocation ledger. Close the staged context with `closeServiceForRecovery` before invoking restore.
2. Repeat `restoreServiceSnapshot(context, snapshotId)` to advance its persisted phase. Authenticate the manifest and secrets, fully validate the independent ledger and every association, download exact ciphertext into fresh fenced object identities, assemble authenticated metadata and install trusted columns. Rebuild quota accounting; do not trust copied counters. Retain all acknowledged deleted-account marker liabilities, including associations newer than the snapshot. Suppress deleted owners before copying their ciphertext or restoring their rows, and apply every Stop sharing event.
3. Keep customer handlers, email and service jobs closed throughout. Discard disposable sessions, challenges, pending verification/approvals, rate state and deletion-status grants. Revoke restored devices, invalidate publication certificates/borrows, abandon stale publication consumers, clear leases and suppress retained email payloads without rewriting accepted/uncertain delivery history. Preserve complete membership, revision, parent/dependency, mutation and head history together. Do not fabricate ancestry or reset client high-water marks.
4. A fully verified staged context remains closed. Freeze the original context; the SQL closure triggers reject writers that passed HTTP middleware before closure. Reconcile original pending Stop/deletion intents and finish or explicitly cancel unfinished snapshots before closure. `promoteServiceRestore(staged, original)` requires the exact original source generation, distinct metadata/object contexts, the same independent ledger, no unresolved original intents and the unchanged fully verified latest ledger head. It retains the old context's entire charged storage liability before opening the staged context. Insufficient capacity leaves it closed.

This promotion function establishes a local context transition, not provider binding/deployment atomicity. It keeps the original resource set closed and retained. The hosted owner must prove supported provisioning, old deployment retirement, interrupted promotion and surviving in-flight effects before changing serving authority. It must not guess that rebinding a Worker is atomic. No source resource disposal is performed by these functions.

Missing/corrupt ciphertext, unavailable/incomplete/regressed ledger coverage, unknown authority events, changed secret identity or exhausted capacity keeps restore closed. Resume the same stage and snapshot after repairing a supported external fault. A changed ledger during verification is not silently accepted; the operational owner must restart reconciliation in a clean closed staging context using the retained source evidence. Do not edit authenticated ledger objects to force progress.

An established device may hold newer local changes or a higher server/publication watermark than the restored snapshot. The accepted client rejects the lower server state with `STALE_CURSOR`, retains its encrypted workspace, pending outbox and profile fence, and pauses sync. Fresh-browser password recovery does not authorize clearing that device's evidence. Automatic convergence across that rollback is not provided; preserve local data and use an explicit recovery workflow.

## Accounting, limits and reproducible evidence

Capture reserves `8192 + encodedSourceBytes * 6 + sourceRows * 512` logical bytes for fixed metadata, encoded intermediate bodies and row/control overhead. Each allocated managed recovery object additionally charges payload plus seed/marker bytes and a conservative 2048-byte control envelope. Paused attempt records are charged; when even that charge does not fit, the precharged singleton records the failure without adding unbounded rows. Restore checks global capacity again after installed metadata and later ledger associations. Permanent marker bodies, object control records and the original frozen resource liability remain charged after promotion. These are logical authoritative admission charges, not SQLite file sizes or provider billing measurements.

The independent revocation ledger is never restored from an older service snapshot or expired with ordinary backups. Its retained body bytes and operation costs are a separate physical resource boundary; see [account deletion](account-deletion.md). The service counter does not certify that independent resource's physical storage, indexes or request usage. Deployment admission must budget it in addition to live, staged and backup resources. There is no finite growth guarantee for permanent markers/control records.

Run the focused recovery, deletion and cleanup tests with `npm run test:worker -- worker/jobs/service-backup.test.ts worker/jobs/service-recovery-browser.test.ts worker/jobs/deletion.test.ts worker/jobs/cleanup.test.ts`, and run `npm run typecheck`. Set `CRYKIT_SYNC_MEASUREMENTS` to a private writable JSONL file for the `o03-local-recovery` receipt. It records source/snapshot logical bytes, native D1 row work, statement/binding/SQL maxima, backup object/body totals and separate ledger totals. The small synthetic workload contains one account and one committed ciphertext revision. A local sample used approximately two thousand D1 statements across durable steps, a largest batch around thirty-five statements, and a few thousand native rows read/written. It is a reproducible small-workload observation, not a maximum admitted service benchmark or a daily schedule guarantee.

The isolated browser rehearsal performs real original-password OPAQUE registration/login, account-key wrapping, encrypted revision upload, closed staged restore, fresh-page key unwrap and exact original ciphertext decryption. It also holds an established browser's newer watermark and real pending local outbox across the older restore and verifies unchanged state after rejection. Synthetic bodies are checked for absence of the plaintext account key and plaintext content. Fault tests exercise real guarded SQL rollback, pin/cleanup ordering, dedup references, delayed conditional payload writes, secret mismatch, complete ledger associations and interrupted closed phases.

Cloudflare limits checked on 2026-10-15 include D1 Free's 50 queries per invocation, 500 MB per database and 5 GB per account; Paid permits 1,000 queries per invocation and 10 GB per database. D1 limits a row/string to 2,000,000 bytes, bound parameters to 100, SQL to 100,000 bytes and an entire batch to 30 seconds. The source capture must fit that single batch; splitting it across calls would break its consistency guarantee. See [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).

Free D1 also permits 5 million rows read and 100,000 rows written per day. Snapshot capture, accounting triggers, page/copy progress, retries, independent jobs and normal application traffic all consume capacity. For a measured workload requiring `W` row writes per completed capture, `floor(100000 / W)` is only an upper bound before any other traffic; it is not a schedule admission decision. See [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/). Worker Free CPU is 10 ms per invocation and memory is 128 MB per isolate; local elapsed time does not establish either bound. See [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).

The full account sync protocol already has a documented workload-dependent Paid requirement in [sync storage limits](account-sync-storage.md#deployment-limits-and-reproducible-measurements). Recovery adds no asserted Free compatibility. Its supported fallback is visibly paused capture with retained last verified points, or closed restore, until measured admission exists. There is no automatic daily backup schedule or age-based expiration enabled by this change. Daily capture and up-to-30-day retention are operational targets, conditional on actual data growth, available capacity and hosted verification. No hosted CPU/memory, physical storage, concurrent R2 writer, daily window or retention duration has been established by the local rehearsal.

## Administration authority during recovery

Apply the additive administration recovery migration to an isolated staging database. Its maintained projection includes operators, bootstrap intents, both administrative audit tables, immutable command receipts, invitation records, settings and durable revocation intents. Sessions, confirmations and previews are captured as evidence but omitted on install. The default staging settings singleton is replaced with its exact captured values; global charges are rebuilt through owning triggers, including each job's separate `admin_revision` JSON-array charge. Restoring uses the deployment ceiling; reopening checks the restored owner project ceiling too, after adding all retained original liabilities. A lower ceiling can therefore leave an otherwise verified restore closed without deleting data.

Operator removal and invitation cancellation commit immediate live denial, command audit, an immutable queued receipt and a frozen `admin_revocations` event in one guarded transaction. The bounded service reconciler appends that exact event to the independent ledger, then acknowledges the intent. The receipt's job ID resolves through the existing administrative job-detail route. Ledger outages leave a pending diagnostic and automatic scheduled retry; retries never reissue the event or undo accepted removal. The migration queues preexisting revoked operators and cancelled invitations for independent reconciliation, with migration observation time and no fabricated prior acknowledgment. Finish these intents while the original service is open before closing it. Pending intents block new snapshot admission and promotion, including migrated records without a historical command receipt.

Before reopening, replay the complete authenticated ledger through its latest unchanged head. `operator-revoked` advances the captured membership revision and leaves it revoked. `invitation-revoked` binds the invitation to its creator operator ID and cancels that invitation; it does not revoke the creator. Customer sessions and disposable admin authority are not restored. Email payloads and eligibility remain suppressed, while accepted/uncertain attempt history and irreversible deletion/Stop cleanup remain intact. Original service secrets, account envelopes, ciphertext, revision IDs and history keep their original identities.

Version 1 snapshots produced before administrative job revisions remain readable. Only the exact original email-job tuple width and service-job tuple width receive the migration's default `admin_revision = 1`; exact modern tuples retain their captured revision. Unexpected widths or invalid job field types fail closed. This normalization affects staging rows, never authenticated backup bytes. Snapshots without operator authority do not invent an owner from a customer or an Access email. Any explicit private owner bootstrap remains the deployment operator's reviewed provisioning responsibility; there is no public bootstrap or automatic owner promotion.

After local promotion, require a new CryKit administrative application session under freshly verified Access identity and reconciled membership. Previously issued application cookies, confirmations and previews cannot be reused. This requirement does not force a new identity-provider authentication or establish hosted MFA; the separate confirmation application and its activation probes remain mandatory for high-impact actions. If the latest ledger changes or a required resource is unavailable, keep the stage closed and follow the existing restart/reconciliation procedure. Do not repair authority by editing immutable snapshot or ledger objects.

## Deployment operation and rollback

Use the named structured secret store and isolation inventory in [account deployment](accounts-deployment.md#original-secrets-and-restoration) before recovery. Original keys must be backed up independently and restored in a closed-stage rehearsal before activation. The [preview acceptance record](accounts-preview.md) distinguishes local proofs from hosted resource/promotion checks. Rollback means pausing cloud effects while retaining schema-compatible guest/local access; never revert persistent schema, recreate OPAQUE setup or silently discard original/history/draft data. Application logs, non-identifying summaries and audits follow the [privacy retention policy](accounts-privacy.md#retention-and-removal); encrypted snapshots, independent revocations and permanent markers have their separate lifetimes.
