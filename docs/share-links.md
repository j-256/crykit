# Share build and team snapshots

Choose **Share build** on a saved build card to share its latest checkpoint, or open a specific checkpoint and choose **Share build**. Choose **Share team** on a saved Team. Choose **Copy link** to send its snapshot. **Open preview** opens the same link in another tab. If clipboard access is unavailable, the URL is selected so you can copy it manually.

Links contain the pinned loadout, calculation inputs, Game Setup, and required personal definitions with their uncertainty and source references. A team carries four ordered slots, including slots without an assigned build. Each slot pins a saved build checkpoint. Sharing a tracked party plan also exports its effective checkpoint assignments without character identities. Character identities and observations, inventory, learning, progress, and history remain in the sender's browser. Build titles and the team title are included. **Include written notes** adds rotation notes, written assumptions, and checkpoint names, which are excluded by default; personal definition descriptions and provenance remain part of the shared definition.

Opening a link displays a read-only preview using the same grouped loadout sheet as the build and character editors. **Loadout** keeps fixed class growth ratings visible alongside colored Base, Equipment, Level, Gender, and Total stat columns, equipment and passive definition details, PP capacity, and calculated stats with growth and damage breakdowns. The saved calculation gender affects Total and survives **Save a copy**; an unspecified gender uses a labeled no-bonus preview. A missing calculation or unknown level keeps totals unknown. Plans without a model marker use the native PC evaluator with their saved inputs. **Checks & notes** shows equipment findings, the native power coefficient and base physical hit curves, effective ability costs, saved battle scenarios and their supported outcomes, saved calculation inputs, and included written notes. Definition fields and source references resolve from the shared snapshot and its pinned catalogs. Calculation inputs cannot be changed in the preview. Preview assumptions do not replace absent or unknown inputs in the shared snapshot or saved copy. Character observations, learning, and inventory checks require local Playthrough records.

**Save a copy** adds fresh builds and checkpoints using one storage transaction. It reuses a Game Setup with the same rules, catalog pins, uncertainty, provenance, and personal overrides, preferring the active setup. Names and record identities do not determine whether the configuration matches. Every saved copy can be edited immediately using its own behavior, including a configuration different from the active Playthrough. Choose another Game Setup in the editor to adapt it; saving pins the new rules without changing earlier checkpoints. New Game Setup names are checked against saved names without regard to case or surrounding spaces. A collision adds `(shared)`, then `(shared 2)`, and so on until the name is unique. Existing setups keep their names.

A team copy creates an independent Team with four build slots. No characters or Playthrough setup are required; adopting it into tracked characters is a separate action. Saving a copy preserves the active Game Setup and team, existing observations, and inventory. Identical personal definition records and their referenced lineage can be reused; differing custom definitions retain separate records without changing existing definitions. A conflicting personal definition lineage for an already customized catalog definition produces an error and preserves the existing personal versions. A failed save rolls back the added records and leaves the preview available for another attempt.

Catalog references retain exact revision pins. The preview resolves available definitions and rebuilds effective mod catalogs from pinned source layers. A declared missing mod source stays unresolved: selected-entry names and identities keep the loadout readable, but do not supply stats or effects. Imported catalog snapshots and original import files are not embedded in the URL. Recipients can import their own matching JSON and attach local artwork in the shared view. Artwork stays in that view and is absent from saved copies and links. Personal definitions and their transitive lineage and requirements are included. Undeclared missing catalog revisions remain an error.

Loadout warnings offer recovery actions for the affected selections or Game Setup rules. Missing-source and permission warnings can open a matching JSON upload dialog directly. Accepted files update the shared preview or open editor draft after the import transaction succeeds. Draft notes and selections survive the import, while saving a new checkpoint remains explicit. A mismatch, failed write, or failed interpretation leaves saved checkpoints intact and explains the remaining problem.

Unchanged native entries in the withdrawn historical baseline can resolve through a receipt recording complete definition equality with an available, fingerprint-pinned native snapshot. The receipt contains identities and checksums, without copying definition bodies. Saved pins remain unchanged. Active mod replacement links, including links through another alias of the same native identity, exclude an entry from this native-only resolution. An available exact snapshot remains authoritative, and an unreviewed revision cannot supply a missing definition.

The entire URL has a 65,536-character application budget. The dialog shows its length and remaining capacity. The decoded snapshot is limited to 1 MiB of UTF-8 JSON. Long notes and custom definitions consume more room; varied text compresses less than repetitive text. Some messaging applications can reject or truncate links below the application's budget. Shorten optional notes or use a private backup file for data that does not fit. A backup includes additional private records and replaces planner data when restored, so it is a separate transfer workflow.

The payload lives after `#` and is processed locally without a sharing service. Browser HTTP requests exclude the fragment, but anyone who receives the complete URL can decode it. Compression provides no confidentiality. Links are fixed snapshots: later edits require another link, and a copied link cannot be revoked.

## Send a long link

In Discord, paste the complete URL directly into the message box. If it exceeds the message limit, Discord [turns it into a text attachment](https://support.discord.com/hc/en-us/articles/360034632292-Sending-Messages) named `message.txt`. The recipient can triple-click the URL in the preview to select it, copy it, and paste it into their browser's address bar. This opens the same shared snapshot without a backup restore. Calculation details require the matching definitions in the recipient's browser.

## Versioned wire contract

The route is `#/share/v4/<payload>`. The payload uses unpadded base64url encoding of a four-byte, big-endian decoded-length header followed by raw DEFLATE bytes. The JSON envelope declares `version: 4`, `kind`, `title`, a minimal `records` graph, and team slot/checkpoint and Game Setup references where applicable. Record structure reuses the native backup schemas, while sharing validates its own envelope and dependency graph. Decoding uses a fixed output buffer bounded by the declared length, rejects output whose size differs, checks safe JSON structure, validates the envelope, and runs native semantic graph validation against available catalogs before displaying or saving records.

Version 4 adds selected-entry display receipts and pinned mod source receipts. Names and model identities are limited to entries selected by the shared checkpoint. Source receipts identify the project, file checksum, parser revision, and optional versioned content fingerprint. Versions 1 through 3 remain readable. Version 3 uses an `archived` boolean instead of obsolete Build `kind` and `state` classifications. Obsolete labels in version 1 and 2 links are discarded at decoding. Version 2 permits checkpoints from the same build to use different behavior presets and retains custom mod choices with an unknown state. Version 1 retains its original same-preset ownership validation.

Share format versions are independent of the persisted planner format. A future encoder must use a new version for incompatible wire changes and retain a decoder or migration for supported older links. Saving a copy gives builds and checkpoints new identities, reuses equivalent dependencies, and remaps new personal definitions, Game Setups, and derived mod catalog pins into the persisted format. Planner payload version 2.4.0 adds optional Build display receipts and Game Setup source receipts while retaining independent Teams, custom mod choices, and archive visibility. IndexedDB upgrades planner data and undo history together in a transaction; any migration error leaves the previous database unchanged. Supported native backup envelopes accept planner payload versions 2.0.0 through 2.4.0, migrating older payloads before validation.

## Matching local mod files

The `json-content-v1` fingerprint sorts object keys by JavaScript string ordering, preserves array order and all source fields, normalizes equivalent JSON number notation without rounding through JavaScript numbers, and hashes the canonical text with SHA-256. Whitespace and equivalent string escapes do not change it. Negative zero remains distinct. File checksums continue to identify the original bytes and protect retained imports and exports; content equality is separate evidence and does not certify Workshop origin.

A content match does not replace a saved catalog pin. Matching local JSON automatically fills the read-only preview once all required sources are available, including after reload. The preview and saved copy use local file revisions; the original link remains unchanged and its checkpoint can still be viewed. Library parser revisions 3 and 4 share the same planning projection; revision 4 adds content fingerprint metadata under a new immutable catalog revision. An older parser interpretation or recognized unavailable historical baseline requires a new Game Setup revision for the preview, with a visible notice that its results may differ. Selected mod entries rebind only through their recorded project/model identities; display names never resolve definitions. Unresolved selected identities or unsupported baseline replacements produce an actionable notice and preserve the original checkpoint.

Each accepted upload reports that the matching source was saved in the browser. The preview lists remaining required sources and applies matching definitions when they can be prepared. Parse, content-match, persistence, and preview-preparation failures remain visible. A failed import rolls back database changes; failed preview preparation returns to the original checkpoint.
