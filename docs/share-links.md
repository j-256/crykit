# Share build and team snapshots

Choose **Share build** on a saved Build or a specific checkpoint. On a shared Team, select the checkpoint in history and choose **Share team**. The link uses that checkpoint's four ordered slots, including empties, member names, and its independently captured catalog pins. A member's name belongs to its Team checkpoint; renaming it preserves the original Build and older Team checkpoints. Mixed-context and empty legacy Teams need an explicit shared Game Setup before creating a new link. **Copy link** copies the URL; **Open preview** opens the same snapshot. If clipboard access is unavailable, the URL is selected for manual copying.

A shared Build opens directly to its loadout. A shared Team opens with a roster; select a member to inspect that member's equipment, passives, calculations, and notes. Empty positions remain visible. **Checks & Notes** puts equipment findings before coverage help, with expandable rows for previews, calculation inputs, and written notes. **Game Setup & sources** uses the same disclosure controls for saved rules, source requirements, and matching definitions. Missing mechanics remain unknown, and **Add matching files** opens the relevant source controls. Saved Teams lead with their roster, keep **Save as Build** beside each member, and put older revisions under **Checkpoint history**. Open **Edit your copy** to change a copied checkpoint's notes or create an editable checkpoint with a local Game Setup.

Public links contain selected names, exact selected identities, available source requirements, equipment relationships, and supported calculation inputs. A missing definition does not prevent sharing a saved selection: its name remains a placeholder, and unavailable type or source metadata stays explicitly unknown. They exclude private definition bodies, effects, descriptions, source JSON, filenames, paths, artwork, private object IDs, library indexes, account identity, Playthrough observations, inventory, learning, drafts, save bytes, and precomputed stats. Personal overrides follow the same receipt-only boundary. **Include written notes** is unchecked each time the dialog opens and adds only the saved user-authored rotation notes, assumptions, and checkpoint notes. Review required mods and omitted content before copying.

The viewer resolves definitions and artwork from its own workspace using canonical exact source identities and selected record identities. Complete source bodies remain usable offline even if original upload bytes or artwork are unavailable. Matching names, native numeric IDs, and different parser interpretations never substitute for the required source. When an entry has no origin receipt, only its exact source reference or a locally saved composition matching its composition digest can resolve it. Another revision or retained selection cannot borrow definitions from the active setup. Add matching JSON to save it in your library without enabling mods or changing an active Playthrough. Calculations preserve saved equipment grouping and unknown inputs. A composed setup also requires a matching local composition and all pinned sources, including disabled layers. Its digest covers payload receipts, interpretations, layer order, enabled states, replacement links, and identity mappings; those private mappings remain absent from the link. Matching sources alone can restore individual details while composition-dependent calculations remain unavailable. Localized combined definitions require the captured composition and record mechanical and text contributors separately.

Public share links carry equipment roles but omit internal slot acceptance metadata. Shared check feedback omits findings caused only by that missing metadata because they offer no user action. It must not infer known acceptance from a standard slot name or role. Keep the validation report undetermined and preserve equipment, class, hand-use, and passive findings. This presentation does not alter persisted copied setups or their exact source receipts.

**Save a copy** creates an independent Build or Team and an immutable source-context setup in one transaction. Team copies preserve every ordered slot, including empties. Equipment groups receive fresh planning identities; personal selections remain fingerprint-bound unavailable receipts even when the viewer can enrich them from an existing personal definition. No sender library, artwork, source original, inventory, or private object is requested or copied. A failed transaction leaves the workspace unchanged. The copied checkpoint reopens with its historical lock intact. **Edit notes** saves a new checkpoint in that exact source context. To change selections, choose a **Local Game Setup** and **Create editable checkpoint**. This uses exact matching definitions from your library, requires selected sources and slots to be enabled in that setup, and preserves the original checkpoint and its source receipts. Missing, ambiguous, or changed parser interpretations remain blocked. Copied setup receipts cannot become an active Playthrough or planning default.

Snapshots include their checkpoint's actual public catalog lock. A payload without that field leaves the lock unknown and cannot be copied faithfully; its owner must create a complete link. No catalog lock is guessed from selected entries or current defaults. A missing display name, required setup source receipt, or conflicting selected-entry metadata prevents publication with an actionable error. Missing catalog-entry type or origin metadata alone does not prevent publication.

Equipment groups publish only the relationship among selected public slot IDs. A captured nonempty allocation ID shared by several selected slots produces one group; singletons and distinct copies remain ungrouped. The original allocation values are excluded. Invalid configured groups, including different items grouped together, remain configurations for normal validity reporting rather than being silently repaired.

## Public v6 wire contract

The route is `#/share/v6/<payload>`. The payload is unpadded base64url of raw UTF-8 JSON, without compression. The independent strict schema is `src/interchange/public-share-schema.ts`; it can be bundled for the Worker without private repositories, cryptography, or game data. The envelope requires version `6` and `dataGeneration: "catalog-sources-1"`. Prelaunch versions and missing or different generation markers fail before source resolution. The envelope contains `version`, `dataGeneration`, `kind`, `title`, `setup`, `slots`, selected `receipts`, and optional explicitly included `notes`. A Build has one occupied slot; a Team has exactly four ordered slots. An occupied Team slot may contain its explicit `name`, independently of note inclusion. Copying, adapting, and resharing preserve that name. Older unnamed slots remain readable without rewriting historical checkpoints; Build slots reject this field.

Decoded JSON is capped at 256 KiB, depth 32, and 20,000 nodes. Titles, Team member names, and IDs allow at most 1,024 characters; selected-entry names and labels 256; each note 16,384. Oversized private titles or member names prevent sharing instead of being truncated. Selected receipts are capped at 1,024; equipment, passives, source layers, and display slots at 64; growth and status inputs at 128. Calculation fields are individually allowlisted, finite, and bounded by their native domains. Nested unknown fields, unsafe prototype keys, missing selected receipts, duplicate or unselected group members, and path-like identity strings are rejected. Unknown input states remain explicit without copied provenance text.

Personal receipts use `personal-definition-v1` SHA-256 identities over selected semantic content. Private IDs, timestamps, acquisition provenance, and lineage pointers are excluded; personal reference dependencies are identified by content. `composition-v2:sha256:` revisions replace private setup IDs with the complete composition digest. Ordinary source pins use canonical source-specific revisions and cannot contain composition revisions. Catalog receipts retain selected entity identities and explicit original contributors. Mechanical and localized text references remain separate, including through numeric remapping. Exact saved contributor receipts survive missing effective views; names and citation similarity never certify an origin. A composition must retain every pinned source body before a new link can certify its digest. Missing entry kind or origin is `null`; conflicting evidence prevents publication. Personal receipts require complete type, origin, and fingerprint evidence. The private `retainedSelections` marker is never a public field.

The full URL has a 65,536-character budget, including its origin and route. The dialog shows actual capacity. Raw encoding avoids compressed expansion work and allocation before validation; consequently a valid snapshot below the JSON limit can still exceed the portable URL budget. Shorten optional notes or share a smaller selection when that happens. Text is never silently truncated. A private backup is a separate workflow with additional private records.

The payload lives after `#`, which browser HTTP requests omit. Anyone with the complete URL can decode it. Portable links are fixed snapshots: edits require another link and copied links cannot be revoked. Only v6 public links are supported. Ask the author for a new link if an older link is unavailable.

## Local source recovery

A viewer sees placeholders until its own workspace supplies matching definitions. Selected-entry names identify what the author chose; they do not supply mechanics. Exact source identities and content fingerprints determine a match. The `json-content-v1` fingerprint preserves array order, source fields, and exact JSON number values, while ignoring object-key order, whitespace, and equivalent string escapes. Byte checksums still identify original import files; a content match does not certify Workshop origin.

Accepted matching JSON is saved in the viewer's own library. Private artwork is resolved from that library. Import failures leave the existing workspace intact, and missing definitions remain unknown. A different parser interpretation remains unavailable until the exact interpretation is supplied; recovery never substitutes a packaged default or newer revision. Local editable Builds retain their own mod-recovery workflow, including draft preservation and explicit checkpoint saving.

## Saved data and backups

The launch boundary applies to both public links and saved data. Copied setups use source context version 2, and all copied checkpoints use context version 3. These contexts retain exact selections, names, contributor references, and null metadata through reopening, note edits, and backups. Unknown kinds are not converted into typed unavailable-definition receipts. Prelaunch contexts are rejected rather than migrated or reinterpreted. Supported launch checkpoints remain transactional and immutable. See [data formats](data-formats.md) and [workspace backups](workspace-backups.md) for persisted formats.

## Hosted links

An active verified account can publish a hosted link from the Share dialog. Publication stores only the strict v6 public snapshot described above. Written notes and the current public screen name are separate unchecked choices; withheld screen names never appear. Preview the selected checkpoint and notes before publishing. Private edits do not change a hosted link until its owner explicitly chooses Update shared version. Reopening the dialog lists owned links for explicit selection; titles and matching content never associate a private Build or Team with a hosted link.

Hosted links are unlisted, so anyone who receives one can view or copy it. Stop sharing makes the hosted ID unavailable, including while independent revocation recording is pending. A read-only owner can still stop an existing link. Completion is reported only after independent revocation acknowledgment and the final guarded database transition. An uncertain result offers the same request for retry; reopening a pending link recovers its exact Stop request. Creating another publication allocates a fresh ID. Stopping a hosted link cannot retract another person's saved copy or revoke a portable link.

Deploy the client and Worker validators for the launch format together before enabling publication. The Worker rejects prelaunch publications, reports stored unsupported formats as `UNSUPPORTED_VERSION`, and reports malformed stored snapshots as `INTEGRITY_FAILED`; neither path returns the stored payload. Rollback must preserve launch data without opening it in prelaunch code.

Hosted reads bypass service-worker caches, request no HTTP storage, and carry no-index response headers. Missing or stopped IDs never fall back to private storage or static assets. Hosted JSON retains the 256 KiB admission limit; portable links retain their separate full-URL limit. The hosted viewer uses the same recipient-owned enrichment and independent-copy implementation as portable v6 links.

## Hosted sharing and privacy

When the optional account service is enabled, a deliberately published hosted snapshot is public content, separate from private encrypted account sync. Review the [upload and privacy terms](accounts-privacy.md) before publishing. Stopping access follows the independent revocation ledger and cannot erase recipient copies. Hosted share API and admin paths bypass service-worker caches. Deployment, complaint handling, and capacity gates are recorded in [account deployment](accounts-deployment.md) and [account capacity](accounts-capacity.md).
