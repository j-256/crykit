# Share build and team snapshots

Choose **Share build** on a saved Build or a specific checkpoint. On a shared Team, select the checkpoint in history and choose **Share team**. The link uses that checkpoint's four ordered slots, including empties, member names, and its independently captured catalog pins. A member's name belongs to its Team checkpoint; renaming it preserves the original Build and older Team checkpoints. Mixed-context and empty legacy Teams need an explicit shared Game Setup before creating a new link. **Copy link** copies the URL; **Open preview** opens the same snapshot. If clipboard access is unavailable, the URL is selected for manual copying.

A shared Build opens directly to its loadout. A shared Team opens with a roster; select a member to inspect that member's equipment, passives, calculations, and notes. Empty positions remain visible. **Game Setup & sources** holds the saved rules, source requirements, and matching definitions. Missing mechanics remain unknown, and **Add matching files** opens the relevant source controls. Saved Teams lead with their roster, keep **Save as Build** beside each member, and put older revisions under **Checkpoint history**. Open **Edit your copy** to change a copied checkpoint's notes or create an editable checkpoint with a local Game Setup.

Public links contain selected names, exact selected identities, available source requirements, equipment relationships, and supported calculation inputs. A missing definition does not prevent sharing a saved selection: its name remains a placeholder, and unavailable type or source metadata stays explicitly unknown. They exclude private definition bodies, effects, descriptions, source JSON, filenames, paths, artwork, private object IDs, library indexes, account identity, Playthrough observations, inventory, learning, drafts, save bytes, and precomputed stats. Personal overrides follow the same receipt-only boundary. **Include written notes** is unchecked each time the dialog opens and adds only the saved user-authored rotation notes, assumptions, and checkpoint notes. Review required mods and omitted content before copying.

The viewer resolves definitions and artwork only from the recipient's own workspace, matching the recorded project, source revision or content fingerprint, and selected model identity. Missing files leave mechanics unknown; matching names or native numeric IDs are insufficient. When an entry has no source origin, only its exact bundled baseline reference or a viewer-owned composition matching its selected composition fingerprint can resolve it. Another revision or a retained selection cannot borrow definitions from the active setup. Add matching JSON from the viewer to save it in your own library without enabling mods or changing an active Playthrough. Matching private artwork already in that library appears automatically. Calculations use the exact available baseline and selected definitions, preserving saved equipment grouping and unknown inputs. For a composed mod setup, the viewer also needs a locally saved composition matching the snapshot's fingerprint and its exact source files. This preserves authored replacement links, disabled layers, and scoped identities when resolving class innates, automatic statuses, and ability costs. Matching files alone can restore selected details while calculations remain unavailable. A different supported parser interpretation is labeled explicitly and never replaces the shared historical pins.

**Save a copy** creates an independent Build or Team and an immutable source-context setup in one transaction. Team copies preserve every ordered slot, including empties. Equipment groups receive fresh planning identities; personal selections remain fingerprint-bound unavailable receipts even when the viewer can enrich them from an existing personal definition. No sender library, artwork, source original, inventory, or private object is requested or copied. A failed transaction leaves the workspace unchanged. The copied checkpoint reopens with its historical lock intact. **Edit notes** saves a new checkpoint in that exact source context. To change selections, choose a **Local Game Setup** and **Create editable checkpoint**. This uses exact matching definitions from your library, requires selected sources and slots to be enabled in that setup, and preserves the original checkpoint and its source receipts. Missing, ambiguous, or changed parser interpretations remain blocked. Copied setup receipts cannot become an active Playthrough or planning default.

Snapshots include their checkpoint's actual public catalog lock. Earlier v5 links without that field remain readable, but faithful copying requires their owner to update the link. No catalog lock is guessed from selected entries or current defaults. A missing display name, required setup source receipt, or conflicting selected-entry metadata prevents publication with an actionable error. Missing catalog-entry type or origin metadata alone does not prevent publication.

Equipment groups publish only the relationship among selected public slot IDs. A captured nonempty allocation ID shared by several selected slots produces one group; singletons and distinct copies remain ungrouped. The original allocation values are excluded. Invalid configured groups, including different items grouped together, remain configurations for normal validity reporting rather than being silently repaired.

## Public v5 wire contract

The route is `#/share/v5/<payload>`. The payload is unpadded base64url of raw UTF-8 JSON, without compression. The independent strict schema is `src/interchange/public-share-schema.ts`; it can be bundled for the Worker without private repositories, cryptography, or game data. The envelope contains `version`, `kind`, `title`, `setup`, `slots`, selected `receipts`, and optional explicitly included `notes`. A Build has one occupied slot; a Team has exactly four ordered slots. An occupied Team slot may contain its explicit `name`, independently of note inclusion. Copying, adapting, and resharing preserve that name. Older unnamed slots remain readable without rewriting historical checkpoints; Build slots reject this field.

Decoded JSON is capped at 256 KiB, depth 32, and 20,000 nodes. Titles, Team member names, and IDs allow at most 1,024 characters; selected-entry names and labels 256; each note 16,384. Oversized private titles or member names prevent sharing instead of being truncated. Selected receipts are capped at 1,024; equipment, passives, source layers, and display slots at 64; growth and status inputs at 128. Calculation fields are individually allowlisted, finite, and bounded by their native domains. Nested unknown fields, unsafe prototype keys, missing selected receipts, duplicate or unselected group members, and path-like identity strings are rejected. Unknown input states remain explicit without copied provenance text.

Personal receipts use `personal-definition-v1` SHA-256 identities over the selected definition's semantic content. Private IDs, timestamps, source provenance, and lineage pointers are excluded; personal reference dependencies are identified by content. Composition identities hash the exact captured composition, replacing the private setup-record ID. Catalog receipts retain the selected entity identity and exact source project/revision requirements. A composed selected entry retains its saved exact project/model identity when the original raw catalog is unavailable; its source revision must match the captured composition. Missing catalog-entry kind or origin is represented by `null`; conflicting evidence prevents publication. Personal receipts require complete type, origin, and fingerprint evidence. A native origin within a composition requires an unchanged entity from the exact baseline, never just the composed catalog ID. Fingerprints are identity evidence, not permission to recover old mechanics. The private `retainedSelections` marker is never a public field.

The full URL has a 65,536-character budget, including its origin and route. The dialog shows actual capacity. Raw encoding avoids compressed expansion work and allocation before validation; consequently a valid snapshot below the JSON limit can still exceed the portable URL budget. Shorten optional notes or share a smaller selection when that happens. Text is never silently truncated. A private backup is a separate workflow with additional private records.

The payload lives after `#`, which browser HTTP requests omit. Anyone with the complete URL can decode it. Portable links are fixed snapshots: edits require another link and copied links cannot be revoked. Only v5 public links are supported. Ask the author for a new link if an older link is unavailable.

## Local source recovery

A viewer sees placeholders until its own workspace supplies matching definitions. Selected-entry names identify what the author chose; they do not supply mechanics. Exact source identities and content fingerprints determine a match. The `json-content-v1` fingerprint preserves array order, source fields, and exact JSON number values, while ignoring object-key order, whitespace, and equivalent string escapes. Byte checksums still identify original import files; a content match does not certify Workshop origin.

Accepted matching JSON is saved in the viewer's own library. Private artwork is resolved from that library. Import failures leave the existing workspace intact, and missing definitions remain unknown. Supported parser reinterpretations are labeled in the preview and do not replace the snapshot's historical source receipts. Local editable Builds retain their own mod-recovery workflow, including draft preservation and explicit checkpoint saving.

## Saved data and backups

Public link versions are independent of persisted planner versions. Copied checkpoints with unknown catalog-entry metadata use public source context version 2, preserving the exact selections, names, and null values through reopening, note edits, and backups. Complete receipts continue to use context version 1, whose schema remains unchanged. Unknown types are not converted into typed unavailable-definition receipts. Older readers reject version 2 rather than reinterpreting its unknown values. Retiring an old public link does not remove a Build or Team already saved in a workspace. Native backup import and transactional persisted-data migrations continue to preserve existing checkpoints, catalog pins, source receipts, provenance, and unknown values. See [data formats](data-formats.md) and [workspace backups](workspace-backups.md) for the supported persisted formats.

## Hosted links

An active verified account can publish a hosted link from the Share dialog. Publication stores only the strict v5 public snapshot described above. Written notes and the current public screen name are separate unchecked choices; withheld screen names never appear. Preview the selected checkpoint and notes before publishing. Private edits do not change a hosted link until its owner explicitly chooses Update shared version. Reopening the dialog lists owned links for explicit selection; titles and matching content never associate a private Build or Team with a hosted link.

Hosted links are unlisted, so anyone who receives one can view or copy it. Stop sharing makes the hosted ID unavailable, including while independent revocation recording is pending. A read-only owner can still stop an existing link. Completion is reported only after independent revocation acknowledgment and the final guarded database transition. An uncertain result offers the same request for retry; reopening a pending link recovers its exact Stop request. Creating another publication allocates a fresh ID. Stopping a hosted link cannot retract another person's saved copy or revoke a portable link.

Hosted reads bypass service-worker caches, request no HTTP storage, and carry no-index response headers. Missing or stopped IDs never fall back to private storage or static assets. Hosted JSON retains the 256 KiB admission limit; portable links retain their separate full-URL limit. The hosted viewer uses the same recipient-owned enrichment and independent-copy implementation as portable v5 links.

## Hosted sharing and privacy

When the optional account service is enabled, a deliberately published hosted snapshot is public content, separate from private encrypted account sync. Review the [upload and privacy terms](accounts-privacy.md) before publishing. Stopping access follows the independent revocation ledger and cannot erase recipient copies. Hosted share API and admin paths bypass service-worker caches. Deployment, complaint handling, and capacity gates are recorded in [account deployment](accounts-deployment.md) and [account capacity](accounts-capacity.md).
