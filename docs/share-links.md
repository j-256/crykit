# Share build and team snapshots

Choose **Share build** on a saved build card to share its latest checkpoint, or open a specific checkpoint and choose **Share build**. Choose **Share team** on a complete team scenario. Choose **Copy link** to send its snapshot. **Open preview** opens the same link in another tab. If clipboard access is unavailable, the URL is selected so you can copy it manually.

Links contain the pinned loadout, calculation inputs, Game Setup, and required personal definitions with their uncertainty and source references. A team carries four ordered slots, including slots without an assigned build. It carries the effective saved assignments, including assignments inherited from a recorded-party baseline. Character identities and observations, inventory, learning, progress, and history remain in the sender's browser. Build titles and the team title are included. **Include written notes** adds rotation notes, written assumptions, and checkpoint names, which are excluded by default; personal definition descriptions and provenance remain part of the shared definition.

Opening a link displays a read-only preview using the same grouped loadout sheet as the build and character editors. **Loadout** keeps fixed class growth ratings visible alongside colored Base, Equipment, Level, Gender, and Total stat columns, equipment and passive definition details, PP capacity, and calculated stats with growth and damage breakdowns. The saved calculation gender affects Total and survives **Save a copy**; an unspecified gender uses a labeled no-bonus preview. A missing or unknown calculation level uses a labeled level-60 preview; absent calculations assign growth to the primary class for that preview. **Checks & notes** shows equipment findings, supported guide estimates, saved calculation inputs, and included written notes. Definition fields and source references resolve from the shared snapshot and its pinned catalogs. Calculation inputs cannot be changed in the preview. Preview assumptions do not replace absent or unknown inputs in the shared snapshot or saved copy. Character observations, learning, and inventory checks require local Playthrough records.

**Save a copy** adds fresh builds and checkpoints using one storage transaction. It reuses a Game Setup with the same rules, catalog pins, uncertainty, provenance, and personal overrides, preferring the active setup. Names and record identities do not determine whether the configuration matches. Every saved copy can be edited immediately using its own behavior, including a configuration different from the active Playthrough. Choose another preset in the editor to adapt it; saving pins the new rules without changing earlier checkpoints. New Game Setup names are checked against saved names without regard to case or surrounding spaces. A collision adds `(shared)`, then `(shared 2)`, and so on until the name is unique. Existing setups keep their names.

A team copy requires four distinct characters selected from the recipient's Playthrough and becomes a draft team. Saving a copy preserves the active Game Setup and team, existing observations, and inventory. Identical personal definition records and their referenced lineage can be reused; differing custom definitions retain separate records without changing existing definitions. A conflicting correction lineage for an already corrected catalog definition produces an error and preserves the existing corrections. A failed save rolls back the added records and leaves the preview available for another attempt.

Catalog references retain exact revision pins. The preview resolves them from catalog snapshots available in the recipient's browser and regenerates effective mod catalogs from the pinned source layers. An unavailable revision produces an explicit error rather than substituting another version. Imported catalog snapshots and original import files are not embedded in the URL; a recipient needs the same imported catalog when a build depends on it. Personal definitions and their transitive lineage and requirements are included. Catalog upgrades can make an older link unavailable if its required snapshot is absent.

The entire URL has a 65,536-character application budget. The dialog shows its length and remaining capacity. The decoded snapshot is limited to 1 MiB of UTF-8 JSON. Long notes and custom definitions consume more room; varied text compresses less than repetitive text. Some messaging applications can reject or truncate links below the application's budget. Shorten optional notes or use a private backup file for data that does not fit. A backup includes additional private records and replaces planner data when restored, so it is a separate transfer workflow.

The payload lives after `#` and is processed locally without a sharing service. Browser HTTP requests exclude the fragment, but anyone who receives the complete URL can decode it. Compression provides no confidentiality. Links are fixed snapshots: later edits require another link, and a copied link cannot be revoked.

## Versioned wire contract

The route is `#/share/v2/<payload>`. The payload uses unpadded base64url encoding of a four-byte, big-endian decoded-length header followed by raw DEFLATE bytes. The JSON envelope declares `version: 2`, `kind`, `title`, a minimal `records` graph, and team slot/checkpoint and Game Setup references where applicable. Record structure reuses the native backup schemas, while sharing validates its own envelope and dependency graph. Decoding uses a fixed output buffer bounded by the declared length, rejects output whose size differs, checks safe JSON structure, validates the envelope, and runs native semantic graph validation against available catalogs before displaying or saving records.

Version 2 permits checkpoints from the same build to use different behavior presets and retains custom mod choices with an unknown state. Version 1 links remain supported with their original same-preset ownership validation.

Share format versions are independent of the persisted planner format. A future encoder must use a new version for incompatible wire changes and retain a decoder or migration for supported older links. Saving a copy gives builds and checkpoints new identities, reuses equivalent dependencies, and remaps new personal definitions, Game Setups, and derived mod catalog pins into the existing persisted format. Planner payload version 2.1.0 stores the checkpoint ownership model and optional custom mod choices. IndexedDB upgrades planner data and undo history together in a transaction; any migration error leaves the previous database unchanged. Native backup envelope version 2.0.0 accepts both planner payload versions 2.0.0 and 2.1.0, migrating older payloads before validation.
