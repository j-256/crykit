# Operator access

Administrative authority is independent of customer authentication. A customer cookie, email header, matching customer email or local fixture header grants no operator access. The Worker verifies a signed Access assertion on every administrative request and binds active membership to its exact issuer and stable subject. Missing configuration fails closed. The verifier uses pinned `jose` 6.2.12 (MIT); the dependency notice generator includes its upstream license from the package lock and installed license file.

`ADMIN_ACCESS_CONFIG` is a strict JSON object with `version:1`, `issuer`, `jwksUrl`, `adminAudience`, `confirmationAudience` and `confirmationEnabled`. The issuer is an exact HTTPS origin. The key URL must be that issuer's `/cdn-cgi/access/certs`; JWT-provided URLs and keys are never fetched or trusted. Audiences must differ. Assertions require RS256, signature verification, exact issuer and single expected audience, a nonempty stable subject, bounded email, issued-at and expiration. Ordinary token lifetime is at most one hour and confirmation token lifetime at most 15 minutes. Issued-at constrains lifetime; it does not prove MFA.

The key cache expires after five minutes and permits refresh at most once per 30 seconds per configured issuer endpoint. Unknown signing keys may trigger a refresh after that cooldown. A refresh failure never falls back to expired keys. Fetches have a three-second abort deadline, a 64 KiB response bound, a bounded key count and manual redirect handling that rejects non-200 responses. The isolate retains only a bounded set of configured endpoints. Rotation within the cooldown can temporarily deny a new key; retry after the cooldown. Authentication telemetry contains bounded operation and error codes, never assertions or key material.

## Sessions and confirmation

`GET /api/admin/v1/access-session` creates or reads an Access-identity session before membership. Its `__Host-crykit-admin-access` cookie grants only the invitation acceptance flow. `requireAccessSession` returns the verified identity and session-bound CSRF authority for that consumer; it does not grant membership. The acceptance landing and its dedicated assets under `/admin/accept-invitation/` use this pre-membership authority. Other admin assets require active membership.

`GET /api/admin/v1/session` and initial admin asset navigation require active membership and create or read `__Host-crykit-admin-session`. The response supplies the role, implemented session permissions, nonsecret session ID, CSRF and expiry. Both cookies are Secure, HttpOnly, SameSite=Lax, Path=/, with no Domain. Sessions expire at the earlier of one hour and their original assertion's expiry. A refreshed assertion cannot extend an existing session. Membership state/revision and the current signed assertion are checked on every request. Membership changes invalidate captured sessions and confirmations; customer sessions remain independent.

Mutations require the exact configured Origin and session-bound `x-csrf-token`. `POST /api/admin/v1/confirmations` accepts only `{commandDigest}` and captures the operator, membership revision, current admin session and exact canonical digest. `POST /admin/confirm/api/v1/complete` accepts only `{challengeId}` under the distinct confirmation audience and the same actor/session. Ordinary JWTs cannot complete it. The resulting deadline cannot exceed the challenge, ordinary session, confirmation token or 15 minutes, and retries never extend it. The command digest is the later command layer's canonical digest, including intended action and target. Confirmation is reusable for that exact digest within the valid window. A new digest needs its own challenge. No bearer or CSRF token belongs in a URL or localStorage.

`requireOperator` and `requireActionConfirmation` are request-time checks. A command must also compose `operatorGuard` or `actionConfirmationGuard` into its own guarded D1 mutation batch so a revoked membership or expired session cannot win a read/write race. Confirmation completion and its audit record commit together. The command layer owns permissions, command receipts, target-revision checks and its own audit semantics; the session permission list does not invent those commands.

## Explicit initial-owner provisioning

There is no HTTP bootstrap endpoint or first-user promotion. `bootstrapOwner(verifiedIdentity, intentId, context)` is an internal deployment operation. Before invoking it, obtain explicit authorization for the exact intended issuer/subject, verify a real ordinary Access assertion with `verifyAccessIdentity`, and compare the returned stable identity with that approved principal. Email, directory search results and unverified payloads are insufficient. Bootstrap rejects reconstructed identity objects and expired identities. Use one persisted opaque intent ID for retries. The owner membership, permanent bootstrap intent and content-free security audit event commit atomically; a different intent or identity cannot replace an existing owner.

Keep the approved identity and provisioning evidence in private operational records. Do not put personal identity values, assertions, control-plane tokens or secrets in repository fixtures. The application runtime has no Cloudflare management credential. Out-of-band recovery requires its own explicitly authorized deployment procedure; it is not a public reset API.

Security audit rows contain only internal IDs, bounded action codes, correlation IDs and timestamps. They are immutable under update and expire through bounded indexed cleanup after 90 days. Bootstrap intents survive audit retention. Session and challenge cleanup is bounded and ordered around foreign keys. Administrative metadata is globally charged, and recovery closure rejects writes to the actual admin tables.

## Deployment and acceptance gates

Production remains assets-only. The isolated preview configuration selects the account Worker with customer, signup and email gates closed; admin access remains unavailable without its separately qualified Access configuration. `wrangler.admin.example.jsonc` is a disabled preparation template, not an activated deployment. Supply the reviewed account bindings and secrets, replace synthetic issuer/audiences/origin, and configure Access coverage before enabling it. The protected runtime paths are `/admin`, `/admin/*` and `/api/admin/v1/*`, including admin assets. Keep all admin-only assets beneath `/admin/`. The template, preview and local configurations use Worker-first routing for those paths. The Worker also rejects admin requests for an origin other than `SERVICE_ORIGIN` and returns no-store responses.

Cloudflare documents [selective Worker-first routing](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/) and [Access JWT verification](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/). Local signed-issuer tests prove the application boundary, including the production entry bundle; they do not prove hosted path precedence, cached asset behavior, alternate hostnames or provider MFA. Before activation, probe every direct and custom hostname, encoded/normalized path variant, asset route and cache response under the actual deployed configuration. Confirm guest/customer routes remain reachable without operator Access.

Keep `confirmationEnabled:false` until a separately audited confirmation Access application covers `/admin/confirm/*`, has a different audience and at most 15-minute lifetime, and enforces independent MFA Require every login. Verify provider MFA/AMR caching and alternate login paths directly. A fresh JWT alone does not establish those conditions. Unsupported policy keeps high-impact commands disabled.

The recovery projection includes operator, bootstrap, audit, invitation, settings and independent revocation authority through the additive administration recovery migration. Restored sessions, confirmations and previews remain unusable; latest independent revocations are reconciled before reopening. A pre-admin snapshot does not invent missing operator authority. See the [recovery runbook](accounts-recovery.md#administration-authority-during-recovery). Hosted resource qualification and rollout probes remain activation gates; local synthetic success establishes neither hosted capacity nor MFA behavior.

## Guarded commands and operational queries

`src/account/admin-protocol.ts` defines strict versioned commands, receipt and preview schemas, bounded query inputs and summary projections. Both operator roles can read operational metadata and manage ordinary account restrictions, quotas, customer sessions, verification resends, withheld usernames, selected public shares and eligible existing jobs. Only the owner can change service settings, invite/remove administrators or request permanent account deletion. The owner cannot remove the owner membership. Customer roles never participate in these permissions.

Create an action ID once, request `POST /api/admin/v1/actions/preview`, and submit the same command to `POST /api/admin/v1/actions`. Preview captures the exact canonical command digest, target revision, settings revision, operator session and a deadline no longer than 15 minutes. An expired preview or changed target/configuration requires a new preview/action ID. Blocking an account, revoking all its sessions, stopping a share, changing service settings, managing operators/invitations and permanent deletion require the separate confirmed digest. Deletion also requires the exact account ID in `command.confirmation`. The final F04 transaction checks live issuer/subject membership and session authority, confirmation when required, preview scope/deadline, settings and target revisions, effect-specific guards, audit, receipt and any job intent together. An audit transaction failure returns unavailable and emits `AUDIT_TRANSACTION_UNAVAILABLE` without raw errors or parameters.

Exact action retries return the immutable original receipt, even after the target advances or is deleted, including when a concurrent identical action commits during target preparation. Reusing an ID with different parameters fails. `GET /api/admin/v1/actions/:id` returns only the authenticated actor's receipt. A queued receipt records accepted intent; it does not claim completion of external storage or email delivery. Share revocation uses the existing frozen pending Stop event and trusted independent-ledger reconciliation. Permanent deletion uses the existing account deletion journal, including snapshot cancellation, fencing, outstanding liability transfer and safe cleanup. Their accepted irreversible cleanup continues after operator revocation.

`GET /api/admin/v1/overview`, `/accounts`, `/accounts/:id`, `/shares`, `/shares/:id`, `/jobs`, `/jobs/:id`, `/settings`, `/audit` and `/operators` expose allowlisted metadata. Account and operator lists mask email. Account detail commits its sensitive-read audit before selecting the full address. Lists default to 50 rows and cap at 100. Lists accept `order=asc|desc`, defaulting to `asc`; one exact `email`, `username`, `accountId`, `shareId` or `jobId` filter can combine with its route's facets. Accounts accept `access=pending|active|read-only|blocked|deleting`, shares accept `state=active|stopping|stopped`, jobs accept `type=email|deletion|cleanup` and `outcome=pending|queued|running|waiting|failed|complete`, and audit accepts authored `action` values and `outcome=complete|queued|denied|read`. Operators accept only order and paging. Wrong-route, repeated and unknown query parameters fail. Authenticated cursors bind the actor, endpoint, normalized filter, order and facets without retaining raw searches; pages are request reads rather than a frozen snapshot. Generic object/revision counts and application accounting do not identify private categories, names or keys. Share detail reads only the intentional public snapshot. Responses label observation time, database source, request freshness, unknown provider headroom and unobserved offline outboxes. Overview adds effective settings and nullable logical capacity from one settings/counters read; missing global counters produce `capacity: null`, and capacity does not measure provider headroom. Its account count covers activated accounts, its bounded recent failures and oldest unfinished job cover service jobs, and its 24-hour email states describe job transport state rather than message delivery. Account session details are bounded and explicitly mark truncation.

The admin workspace requests newest-first pages of 50 and shows only the current page count. Previous and Next use server cursors; changing a filter resets paging and the inspected detail. Accounts search one exact email, username or account ID and can narrow by access; shares search one exact share or account ID and can narrow by state; jobs search one exact job or account ID and can narrow by type and outcome. Account-filtered jobs exclude email jobs because their metadata has no account ID. Audit filters by action and outcome, while operators use paging only. A detail link includes a validated opaque ID in the URL fragment so an inspected account, share or job can be reopened. These reads can change between pages and must not be treated as a complete inventory.

The overview separates application capacity utilization from the share of accounted storage attributed to encrypted payload, reserved metadata and stored metadata. The distribution appears only when those disjoint counters have a known positive total; exact byte values remain visible. Activated accounts exclude pending registrations. The oldest unfinished job and recent service failures cover service jobs; the failure list is capped. Email bars count observed job states during the previous 24 hours and do not establish recipient delivery. Provider storage allowance, provider mail headroom and offline device outboxes remain unobserved.

The settings allowlist is `registrationPaused`, `uploadsPaused`, `sharingPaused`, `emailPaused`, `maxAccountBytes` and `projectCapacityBytes`. Capacity settings cannot exceed the deployment's `STORAGE_CAP_BYTES`. Ordinary signup admission, final upload/commit/publication guards, live backup capture admission and object allocation, final project quota checks and email lease/send-start checks enforce these settings. Live backup transactions read the persisted owner ceiling and check final liabilities atomically; lowering it preserves retained snapshots and safe cleanup. Closed staged restore uses the deployment ceiling; reopening also checks the restored owner project ceiling after adding all retained original liabilities, as described in the [recovery runbook](accounts-recovery.md#administration-authority-during-recovery). Lower quotas preserve existing data; pauses preserve reads and local editing. Email pauses preserve queued authority and do not grant verification. Settings cannot change provider plans, routes, credentials or deployed code.

Owner settings show observed values alongside a local draft and a before/after review of changed fields. Capacity inputs accept Bytes, KiB (1,024 bytes), MiB (1,048,576 bytes) and GiB (1,073,741,824 bytes), using exact integer arithmetic and rounding fractional conversions up to a whole byte. Changing the displayed unit alone does not change stored bytes. Project capacity must be positive and account quota may be zero; invalid or out-of-deployment-range values cannot be previewed. Reset draft restores the last observed values; Discard draft and refresh explicitly replaces local edits with a new server read. A failed read keeps the last observed values visible but disables preview until refresh succeeds. Preview settings change opens the server's revision-bound impact review, and Apply action still requires the separate Access confirmation. Cancelling that review retains the draft.

Job retry never accepts executable parameters or resets attempts. Existing deletion/cleanup retries require an unfinished failed attempt without a live lease. Email retry preserves O01's eligible, unexpired, known-unsent state and cumulative attempt limit. Cancellation is limited to unstarted eligible email roots without started descendants; accepted deletion journals cannot be cancelled. Verification resend creates a bounded capability for the existing pending registration's stored recipient and atomically invalidates the prior verification generation and its email lineage. Operator state/revision changes invalidate only newly created staff verification/invitation email roots linked by immutable action receipts, including their resend descendants. They preserve unrelated customer-origin mail, existing operational retries and already-started accepted/uncertain delivery history.

`0013-admin-commands.sql` adds receipts, expiring previews, command/query audit, invitation storage and settings while consuming the actual C01 membership/session tables. Separate monotonic `admin_revision` columns on service and email jobs invalidate previews when lifecycle state changes; they do not replace account `expected_revision`, leases or attempts. New rows and added revision bytes are globally charged. Audit rows are append-only under update and retained for 90 days; permanent receipts preserve idempotency after audit expiry. The administration recovery migration extends exact snapshot accounting and reconciles independently acknowledged operator/invitation revocations before reopening. Disposable sessions, confirmations and previews are not reactivated; the closed-state fences remain active. See the [recovery runbook](accounts-recovery.md#administration-authority-during-recovery) for pending-intent and original-secret requirements.

## Administrator invitations

Before inviting an administrator, the deployment operator must explicitly allow the intended email through the ordinary admin Access policy. Access policy admission and CryKit membership are separate prerequisites. The owner preview and invitation email state this setup step; the Worker never receives a provider management token or changes Cloudflare membership. Hosted policy/MFA activation and the panel UI require their separate delivery checks.

The owner issues `operators.invite` for an exact email and administrator role using the normal preview and high-impact confirmation. The guarded command creates a 24-hour invitation, a purpose-separated capability hash, the O01 encrypted email outbox and the immutable action receipt together. Its receipt job ID is the actual email root. An active membership email or pending invitation for that normalized address rejects a second invitation. An expired pending invitation must be explicitly cancelled before creating another; expiry never extends through Retry.

Mail links to `/admin/accept-invitation/#<capability>`. Only that landing and its acceptance-only asset namespace admit a verified pre-membership Access session. The UI must remove the fragment before further navigation and keep the capability in request memory. `POST /api/admin/v1/invitations/accept` accepts strict `{capability}` with the pre-membership cookie, exact Origin and session-bound CSRF. The same guarded batch rechecks the verifier-authenticated email/issuer/subject, exact live pre-membership session and deadline, pending invitation/revision/expiry, active creator authority and eligible root. It grants administrator membership bound to issuer/subject, consumes the capability, invalidates the email lineage, records acceptance audit and creates a fresh bounded admin session. The host-only admin cookie is emitted only after commit.

Wrong email returns forbidden; unknown, expired, cancelled or replayed capabilities return invalid request. An existing issuer/subject membership, including a revoked membership, is an explicit conflict rather than implicit reactivation. A duplicate active email also conflicts. Audit failure rolls back the grant, consumption, session and email invalidation. Concurrent acceptance grants only one membership. Owner cancellation uses the same audited command path and invalidates the selected root and descendants. Revoking or advancing the creator membership invalidates its exact receipt-linked invitation mail and prevents acceptance, while already-started accepted/uncertain send history remains intact. No action can mark mail delivered.

The service-job `canRetryJob` predicate accepts only failed pending work in the existing deletion or cleanup phases, with no live lease and a valid cumulative attempt counter. It describes eligibility, not live actor authorization; the final command transaction retains the operator, target revision, preview and effect guards. `canCancelJob` is false for these durable service journals because they are cleanup or an already accepted irreversible deletion. Email Retry/Cancel continue to use O01's independent eligibility, expiry, attempts and lineage predicates. Required cleanup never gains a quota or ciphertext rewrite bypass from Retry.

Admin-bearing recovery includes invitation authority, independent revocations and operator/session invalidation. Local captured-email and signed-issuer tests do not establish hosted Access policy, MFA, hostname or cache behavior.

Operator removal and invitation cancellation return immutable queued receipts after live denial and audit commit. Their exact receipt-linked job detail remains pending until the bounded service reconciler acknowledges the frozen independent-ledger event. An unavailable ledger leaves a safe diagnostic for scheduled retry; it does not restore live access or rewrite the original receipt. New member application sessions also commit an attributed login audit atomically; ordinary session refreshes do not add audit rows.
