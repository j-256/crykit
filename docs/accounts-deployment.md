# Optional account service deployment

Guest editing remains available without signing in or a working account API. The account service uses the existing product origin and hash routes; private account content is encrypted by the browser before durable account storage or upload. The Worker never receives a workspace decryption key. Production `wrangler.jsonc` remains assets-only. The concrete `wrangler.preview.jsonc` selects the production service entry with isolated preview storage and disabled account, signup and email gates. It omits sender, Access and recovery-policy settings until their qualification. The disabled [account example](../wrangler.accounts.example.jsonc) is a configuration template, not an activation or provisioning command.

Read the [preview acceptance record](accounts-preview.md), [capacity policy](accounts-capacity.md), [privacy and upload terms](accounts-privacy.md), [security contract](accounts-security.md), [admin Access contract](admin-access.md) and [recovery runbook](accounts-recovery.md) before activation. An isolated preview authorization does not authorize production, a purchase, a message to a real recipient, or general public uploads. General public uploads require owner approval of the published terms and an actual complaint contact.

## Environment configuration

Replace placeholders in a private reviewed configuration for exactly one environment. Preview and production must have different D1 database IDs, object buckets, backup buckets, independent revocation-ledger buckets, secrets, sessions, sender settings and Access audiences. Never copy local fixture IDs or use `worker/testing/local-entry.ts` in a hosted environment. The entry is `worker/index.ts`; the pinned OPAQUE static-WASM adapter is generated by the example's build command without changing the package or password protocol. Keep the Worker name and Custom Domain bound to the existing intended environment. Disable workers.dev and provider preview URLs.

| Setting or binding | Requirement |
| --- | --- |
| `DB` | Dedicated D1 database, with the ordered additive migrations in `worker/migrations` |
| `OBJECTS` | Private immutable encrypted payload generations |
| `LEDGER_BACKUPS` | Separate private encrypted service snapshots and recovery objects |
| `REVOCATION_LEDGER` | Independently retained private deletion, stopped-share and operator-revocation ledger; never roll it back with a snapshot |
| `ASSETS` | Reviewed `dist`, Worker first for `/api/*`, `/admin`, `/admin/*` |
| `SERVICE_ORIGIN` | Exact HTTPS product origin, without a path or trailing slash |
| `ACCOUNTS_ACTIVE`, `SIGNUP_ACTIVE`, `EMAIL_SENDING_ACTIVE` | Start `false`; independent operational gates |
| `STORAGE_CAP_BYTES` | Deployment ceiling; preview uses 64 GiB (`68719476736` bytes); a persisted owner ceiling can be lower |
| `CLOUD_NETWORK_LIMITER`, `CLOUD_ACCOUNT_LIMITER`, `CLOUD_AUTH_LIMITER`, `CLOUD_LOCATION_LIMITER` | Native rate-limit bindings; use separate namespace IDs for preview, production and local use |
| `CLOUD_DAILY_REQUEST_BUDGET`, `CLOUD_MONTHLY_REQUEST_BUDGET` | Optional positive integer service admission overrides; defaults and scope are in [capacity limits](accounts-capacity.md#observation-and-response) |
| `CLOUD_DAILY_WORK_BUDGET`, `CLOUD_MONTHLY_WORK_BUDGET` | Optional positive integer expensive-work overrides; weights and scope are in [capacity limits](accounts-capacity.md#observation-and-response) |
| `NATIVE_EMAIL`, `EMAIL_FROM` | Native binding restricted with `allowed_sender_addresses` to the exact fixed sender |
| `EMAIL_HEADROOM` | Start `unknown`; `available` is an explicit reviewed operational assertion, not a capacity measurement |
| `ADMIN_ACCESS_CONFIG` | Version 1 JSON: exact issuer, issuer JWKS URL, distinct ordinary and confirmation audiences; `confirmationEnabled:false` until hosted MFA proof |
| `SERVICE_BACKUP_POLICY` | Omit until the actual deployment has a measured admissible capture envelope; see recovery |

R2 buckets must have no public domain, public development URL, image proxy, external game-data fetcher, analytics injection or lifecycle deletion/expiration of managed keys. Inventory every deployed writer. Only the assigned one-shot seed, payload conditional on its original seed ETag, and permanent assigned removal marker may write a managed key. Do not add a TTL, unconditional repair/copy, key reuse or delete sweep. A marker remains globally charged even after account deletion. Provider lifecycle and overlapping-write behavior require hosted verification; configuration names do not prove either.

Disable persisted Workers Logs and traces on the account producer. Disabling only automatic invocation logs does not remove Cloudflare's request URL enrichment from stored custom console logs; this was observed in hosted telemetry on 2026-10-21. The private diagnostic/alert Worker receives the existing Tail stream, copies only validated authored fields and persists its own sanitized output. Tail invocations describe consumed script names rather than the producer's HTTP request; fixed private notification requests use a constant internal URL. Never forward the raw Tail event, request headers, URL, exception message or stack. Check representative hosted records, including provider metadata, before claiming URL-free diagnostic retention. See [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) and [Tail Workers](https://developers.cloudflare.com/workers/observability/logs/tail-workers/), checked on 2026-10-21. Disabling producer persistence does not retroactively redact older provider records.

The account preview configures a 1,000 ms CPU limit per invocation. This is a deliberate Paid deployment bound, not a measured CPU requirement or a monthly spend cap. [Custom CPU limits](https://developers.cloudflare.com/workers/wrangler/configuration/#limits) are enforced on Cloudflare's network rather than by local emulation. Check hosted CPU and failures after deployment without increasing the limit to conceal an unexpectedly expensive request. The existing Free-compatible mode remains guest assets-only delivery.

## Original secrets and restoration

The deployment operator supplies the path in `CRYKIT_SERVICE_CONFIG`, an absolute configurable path to a protected structured JSON store outside source and build inputs. This is an operator storage convention, not a Worker environment variable or an implemented credential-loader CLI. Use mode `0600`, restrict its parent directory and reader access, and keep an independently recoverable encrypted copy. Every configured store filename must end in `-service-secrets.json`, for example `crykit-service-secrets.json` or `preview-service-secrets.json`. The source and asset privacy checks reject this reserved suffix at any depth, including backup extensions. Keep the store outside source and build inputs even with this guard; do not rename it to evade the exclusion. Never put values in Wrangler `vars`, Vite variables, shell history, logs, fixtures or ordinary backups. Do not use a general personal password notebook as an automation source.

The store's explicit fields are `version:1`, `environments.preview` and `environments.production`. Each environment records `workerName`, `origin`, `databaseId`, `objectBucket`, `backupBucket`, `revocationLedgerBucket`, `emailFrom`, `adminAccessConfig`, `operatorContactUrl`, and `secrets`. The `secrets` object contains `OPAQUE_SERVER_SETUP`, `DUMMY_IDENTITY_SECRET`, `SESSION_SECRET`, `CURSOR_SECRET`, `CAPABILITY_SECRET`, `EMAIL_STATE_SECRET` and `SERVICE_BACKUP_KEY`. `operatorContactUrl` is the operator's approved public complaint/privacy destination; it is not an admin identity or a runtime Worker setting. Publish it alongside the approved terms before opening general uploads. Missing contact approval keeps that launch gate closed.

Generate the OPAQUE server setup once for a genuinely new environment using the pinned implementation in a private provisioning process. The other named secrets are independently generated canonical base64url encodings of 32 random bytes. Preserve all original values with their environment and authenticated recovery fingerprints. Missing or malformed required account secrets return unavailable readiness; the deployed entry never creates a replacement setup. Email-secret/readiness failure pauses signup and email operations independently of established login/sync. Missing recovery policy or key keeps capture paused without inventing a recovery point.

Before activation, back up the original non-reconstructible secrets and exercise restoration from that protected store into a closed isolated stage. A syntactically valid replacement key is not the original key. Verify the original account password unwraps the original key in the browser and decrypts original ciphertext. The backup encryption key must remain recoverable outside the backup it encrypts. Do not print secrets while recording this proof; retain only nonsecret resource identities, fingerprint checks and outcomes.

## Access and bootstrap

Protect actual HTTP paths `/admin`, `/admin/*` and `/api/admin/v1/*` separately from the guest/customer application. Use ordinary Access identity plus explicit application membership. The confirmation application covers `/admin/confirm/*`, has its own audience and at most a 15-minute lifetime, and requires independent MFA on every login. Verify actual policy eligibility, seat availability, AMR matching, session reuse and alternate login routes. Leave high-impact confirmation disabled if that evidence is unavailable. Workers Paid does not establish a Zero Trust entitlement.

Use only the internal `bootstrapOwner` procedure described in [admin bootstrap](admin-access.md#explicit-initial-owner-provisioning). Obtain the owner's approval of the exact issuer/subject, verify a real ordinary Access assertion, and persist one intent ID for retries. There is no HTTP bootstrap endpoint, first-user promotion, customer-role promotion or email-only identity shortcut. Keep operator identity in protected deployment configuration. An address supplied for Access admission is not a public complaint contact or permission to send a test message.

## Migration, bounded maintenance and activation

1. Inventory the isolated environment and every actual binding, lifecycle rule, sender, Access application and existing writer. Preserve the production deployment and existing local databases.
2. Install the lockfile with `npm ci`; build with `npm run build:preview`, run focused contracts and privacy/assets checks, then follow coordinated [publication verification](development.md#publication-verification). Inspect the production-entry bundle for fixture controls, local identity bypass and browser-only crypto. Never publish `.account-tests` or source maps.
3. Apply each authored migration in order to the exact isolated database while account handlers are closed. Do not edit old migrations or reset a persisted database to make a migration pass. Check the resulting schema and counters. Never apply local fixture migrations to live bindings accidentally.
4. Install original secrets and prove restoration. Verify readiness remains unavailable under missing configuration and guest startup/edit/export still works with account crypto/API unavailable.
5. Verify email and Access gates below, run closed recovery and conditional-object overlap proofs, and record admitted capacity. Keep only independently qualified capabilities enabled.
6. Review the exact configuration and dry-run bundle against the binding inventory. Deployment commands remain inactive until resource IDs and Access coverage are verified. The example intentionally includes no routes and no active schedule; it cannot establish placement or activation by itself.

After hosted qualification, a single five-minute schedule (`*/5 * * * *`) is the proposed bounded maintenance cadence. Each invocation uses the existing capped email dispatcher and service-job runner; it is not an unbounded drain or a daily backup creator. Observe backlog age and partial failures with request/job IDs and safe phase timings. Concurrent invocations rely on durable leases and exact receipts. Three automatic attempts per email job is the maximum; an accepted native `messageId` means accepted for sending, not delivered. Uncertain sends do not automatically resend. Do not enable multiple overlapping equivalent schedules to hide backlog.

Sender-domain authentication, exact sender allowlist, account-wide monthly headroom, the real reputation-based daily allowance and suppression reporting must be verified through supported provider controls. Disable sending-domain stored message preview with `preview_enabled=false` before capabilities enter real mail. Worker `preview_urls=false` is unrelated. Local captured mail proves no native delivery. Keep `EMAIL_HEADROOM=unknown` and sending inactive until those gates pass. Native send evidence requires an explicitly authorized recipient; never use email to unlock encrypted data. See [email capacity and sources](accounts-capacity.md#email-and-access).

## Rate-limit notices and owner alerts

Account actions, sync and hosted sharing retain a safe request reference and the server's earliest retry time. The frontend explains temporary traffic protection separately from a service-wide usage pause, keeps local editing available, and offers a prefilled [Contact us](mailto:abuse@crykit.lasers.app) email. The email includes only the error category, time, optional request reference and app version. Never include the page URL: verification, approval and recovery URLs can carry private capabilities. Notices also appear inside open dialogs. A later successful request clears only its matching notice; old responses and profile/session replacements cannot publish or erase a successor's notice.

Owner alerting uses an independent Tail Worker built from `worker/alerts/index.ts`, with `wrangler.alerts.example.jsonc` as its inactive deployment template. For preview, deploy `crykit-preview-alerts` first and retain the producer attachment in `wrangler.preview.jsonc`. Use a private deployment configuration to set `ALERT_SOURCE_WORKER`, `SERVICE_ORIGIN`, `ALERT_EMAIL_TO`, `EMAIL_FROM`, `ALERTS_ENABLED=true`, and the native `NATIVE_EMAIL` binding with exact sender and recipient restrictions. Keep the owner's recipient private. Use distinct names, Durable Object namespaces and native limiter namespace IDs for every environment. Enabling preview alerts does not activate production alerts.

The helper has no public hostname, disables workers.dev and preview URLs, and returns 404 from its HTTP handler. It receives producer Tail events, copies only authored bounded error metadata, and can observe a 429 even when the producer coalesces its console output. Request headers, URLs, email addresses, keys, ciphertext and imported content never enter the notification payload. The pinned local runtime can omit `scriptName`; the private Tail attachment supplies that source boundary, while a different explicit script name is rejected. The helper never binds the account database, object buckets, authentication secrets or customer email queue. It therefore remains able to notify the owner while customer cloud operations or scheduled customer jobs are paused.

An approximate native gate admits at most one alert-processing attempt per error category per minute per Cloudflare location. One SQLite-backed Durable Object atomically reserves notification attempts across locations, isolates and restarts. Both categories have a 15-minute cooldown. Traffic-limit notices have eight reserved attempts per UTC day, and service-pause notices have two separate attempts, preventing traffic notices from spending the pause allowance. Later notices group observed samples, which are not an exact request total. Preserve the namespace during normal deployments: replacing it resets those operational allowances. Unknown stored state fails closed. This state contains only versioned notification counters and times; it does not change account backups or persisted user formats.

Reserve before sending and retain the reservation when delivery is uncertain. A native `messageId` establishes acceptance for sending, not delivery. An ambiguous send is never blindly resent; continuing incidents can produce another bounded attempt after the cooldown. Inspect the helper's `operator-alert` diagnostics for accepted or failed delivery. Alert delivery is best effort, and the UI must not claim that an operator was notified. Disabling `ALERTS_ENABLED` stops owner email without changing customer rate limits.

The Durable Object reports `stage=delivery, code=ACCEPTED`, and the Tail handler also reports `stage=acknowledgment, code=ACCEPTED` after validating the object's explicit accepted reply. Both records describe the same send and share its support reference; do not count them as separate notifications. HTTP 200 alone is insufficient because grouped notices also return it. Grouped replies add no acknowledgment log, and failed, malformed or unknown replies never establish acceptance. The acknowledgment reads the existing response without another email send, Durable Object request or storage write. It bypasses optional diagnostic sampling but follows the existing globally reserved notification allowances. A hosted preview comparison on 2026-10-21 retained the Durable Object receipt with an active real-time log subscription but omitted it without one, while email delivery, invocation success and Tail diagnostics remained observable. The provider's internal cause is unproven; the extra acknowledgment covers that observed gap without making either logging path a durable delivery audit.

Enable `DIAGNOSTICS_ENABLED=true` on the privately configured helper to retain sanitized diagnostics independently of owner email. The same native limiter uses separate `diagnostic:` keys derived only from authored operation, stage, code and limiter names, admitting an approximate sample per key per minute per Cloudflare location. Diagnostic admission cannot spend notification admission. Parsing and forwarding have fixed batch bounds; these records are samples rather than a complete traffic history or exact denial count. Opaque request/job/mutation references, source Worker/version identifiers, occurrence times, safe phase timings and authored route templates support correlation without retaining raw paths or query values. Runtime exceptions retain only a generic failure code.

For a received alert, open the private diagnostic Worker's Observability Logs, select the email's time window and filter `requestId` by its support reference. The same reference joins the originating diagnostic and the `operator-alert` delivery result or acknowledgment when those records are retained. Emails label the management link as "Open admin panel" and identify the affected route separately. Database-backed denials report the blocking policy, scope, allowance/window, stored admitted-request or work-unit count and retry guidance using the existing denial read. Counts exclude denied attempts and are not a billing meter. Native bindings expose only success, so their policy/scope and conservative retry guidance are available while threshold, count and exact reset remain explicitly unavailable. A missing diagnostic or reference does not establish that an incident did not occur.

[Tail Workers](https://developers.cloudflare.com/workers/observability/logs/tail-workers/), checked on 2026-10-20, require Workers Paid and charge CPU time; this is an inherent Paid dependency of owner alerts. Durable Object requests, duration and SQLite storage and native email have their own applicable allowances. A reproducible upper estimate for email is ten reserved attempts per UTC day per environment, before provider rejections; tail execution still occurs for each producer invocation, and the approximate native gate precedes durable-state work. These limits do not cap the Cloudflare bill. The Free-compatible fallback remains guest assets-only use with the Tail attachment omitted and the helper undeployed. Workers Paid does not require a website Pro upgrade for this feature. Reverify provider allowances and actual usage before making billing claims.

Verify the real Tail-to-state-to-email path, concurrent coalescing, restart persistence, uncertain delivery, safe payloads, 404 HTTP behavior and client retry/contact notices. Local email capture verifies the delivery boundary without sending mail; a hosted accepted-send check requires an explicitly authorized owner recipient and is separate from proof of inbox delivery.

## Rollback and incident handling

Pause cloud writes, signup, sharing or email using the appropriate guarded service settings when authority remains healthy. If authority itself is unsafe, disable the service deployment gate and preserve guest/local access. Retain the exact encrypted outboxes, unresolved conflicts, historical originals and guest databases. Deploy only a frontend/service version compatible with every persisted schema and accepted wire version. Rollback does not mean reverting D1 or browser schema migrations, deleting newer rows, resetting account keys or discarding pending work.

Use [closed staged recovery](accounts-recovery.md) for a damaged service, retaining the latest independent ledger and original resource liabilities. A code version rollback alone does not restore data or provider policy. If a staged restore cannot satisfy original-secret, integrity, latest-ledger or capacity checks, leave it closed. Record the last verified recovery point and its actual age, never imply newer writes are backed up. Publish safe incident status and use the approved contact for complaints; keep private payloads and credentials out of diagnostic reports.
