# Mod calculations and their boundaries

CryKit applies supported Crystal Edit data from the exact source revisions enabled in a Game Setup. Base data, the selected balance mode, and enabled mod layers supply inputs to the inspected PC 1.6.9.0 formulas. Builds, character calculation plans, comparisons, and read-only shares use the pinned setup. Importing or browsing a source does not enable it.

## Editable data and engine rules

The inspected `SangMod` model and `SangDataManager.ApplyMod` define the Crystal Edit data boundary. `SangDataPatcher.InPlaceAssign` replaces matching numeric identities, while `InPlaceAssignment.Assign` limits localization changes to supported text fields. `ModCompiler` converts supported older editor formats and redirects added identities at game runtime. These are source-inspected PC behaviors; they do not establish another platform's loader or support executable patches.

| Area | Crystal Edit can change | CryKit calculation coverage |
| --- | --- | --- |
| Classes | Growth ratings, innate membership, abilities, learn trees, and equipment permissions | Numeric growth and supported primary/sub-command innates; learning and legality remain separate checks |
| Equipment and passives | Complete modifier lists, numeric values, modifier parameters, PP costs, types, handedness, and flags | Native flat, percentage, per-level, and explicit per-turn modifiers; paired equipment, unarmed effects, weapon bonuses, derived stats, cost overrides, elemental effects, and native caps |
| Genders | Names, appearance, and each `BoostHP` through `BoostLck` flag; additional records | Effective bonus profiles, including added identities, selected Total, contributions, and native base-growth previews |
| BattleConfig | The declared native configuration fields, including weapon and unarmed constants | Sheet constants feed the loadout; supported battle constants feed the selected ability and target scenario |
| Difficulties and enemies | Difficulty records, enemy inputs and behavior records | Separate enemy/difficulty previews and monster targets using the pinned setup difficulty; enemy multipliers do not change player stats |
| Abilities and statuses | Coefficients, costs, existing modifier tags and parameters, status records and references | Effective HP, MP, AP, CT, and cooldown costs; explicit status snapshots, damage/healing, hit/critical thresholds, variance, periodic effects, and status application previews |
| Formula implementation | No Crystal Edit record field replaces the executable's arithmetic | Native growth equations, bonus amounts, integer stages, rounding, modifier semantics, hit curve, and caps stay fixed |
| PP budget, equipment slots, and startup options | These are engine or startup behavior outside the supported record overrides | Existing saved assumptions remain explicit; a source record does not establish a different engine or startup setting |

Mods can select an existing modifier tag and change its parameters. Imported text, descriptions, and authored formulas remain inert. A mod that patches the executable or uses another loading framework is outside this calculation model, even if its displayed game version matches the PC baseline. See the [native package](calculations.md) for formula fingerprints and arithmetic scope.

## Gender bonus profiles

Choose **Calculation gender** in the loadout overview. Options use the effective gender record names and include additional imported profiles. A profile can remove the original HP bonus, enable Strength, or combine any supported flags. Each enabled flag uses the corresponding native bonus formula before equipment, modifiers, derived stats, rounding, and caps. Appearance does not select a bonus profile in CryKit.

The bundled Final Fantasy Project Overhaul source turns off the bonus flags on its Male and Female records. The bundled Crystal Project Remix source defines named Tough, Quick, Smart, and Lucky profiles with additional identities. Those are facts from the packaged revisions, not assertions about every release of either mod.

The Build's collapsed **Game Setup** summary names enabled source mods and distinguishes named-only settings. **Rules from game data** leads with the selected bonus profile and its source. **All bonus profiles** groups the effective flags by source; **Other rule changes** and **Difficulty and engine rules** provide further details. These disclosures start collapsed. An unspecified gender provides a no-bonus comparison baseline. The engine's `EnableGenderBoost` flag is an internal development control, not a player-facing option. Missing or invalid flags make that profile unresolved rather than treating absent flags as false. Neutral and other complete profiles can still be calculated. An unavailable saved profile stays saved and displays a recovery reason.

Rule changes use plain-language effect labels, descriptions, and value units. Their info icons reveal the exact technical field names on hover, keyboard focus, or tap; Escape dismisses the help. For example, **Learn free abilities from all classes** describes automatic learning of abilities costing zero JP, including abilities in classes the character has not unlocked, while excluding abilities locked by default. This rule does not establish a character's recorded learning. Loadout compatibility feedback covers equipment and passive-point checks, while stat views separately identify their resting or battle-scenario calculation scope and coverage gaps.

Existing male/female inputs retain their meaning. Added selections use the optional versioned `genderSelection` input and resolve against the exact setup pins. Backups and shares preserve it; application versions without this field cannot import those records. Unknown selection versions and simultaneous legacy/additional selections fail validation before writes.

## Identity, order, and saved revisions

Native family and ID matches suggest replacement links when choosing a source revision. Names alone do not establish replacements. Explicit separate choices and reviewed links remain intact. Changed native innates resolve through the effective catalog even when their owning class is unchanged. Imported classes can use exact native innate records or definitions supplied by another enabled layer. Missing or invalid replacements do not silently restore vanilla effects. Preview abilities, targets, active statuses, and status history are rebound with the loadout when a setup changes.

Composition version 3 assigns stable numeric identities by project and record family. Added records that reuse a source ID remain separate; references in abilities, statuses, learn trees, modifier parameters, and supported rule records follow their owning project. Original native identities still use ordered overrides. The setup retains reservations when a layer is disabled or removed, so later edits cannot silently redirect a saved selection to another project. Explicit replacement links for added identities include the project scope.

These are planner composition identities, not a claim about the numeric mapping stored in a particular game save. Planner priority is a user-selected ordering, not a discovery of the installed load order. Unsupported or missing references remain unresolved.

Historical version 1 and 2 compositions retain their original interpretation, including version 2 collision diagnostics. Editing their layer composition explicitly upgrades the new setup revision while preserving the older revision. Original bytes, source snapshots, observations, and checkpoint pins remain unchanged. New imports carry rule-projection version 2; historical imports that archived rule changes need reimporting and explicit selection of the new source revision.

## Battle scenarios

Open **Checks & notes > Ability and hit-chance preview**, choose an ability, then choose **Add battle scenario** and select a self or monster target. The selected ability's name and labeled source facts identify what you are previewing. Effective costs and the ability result appear before the optional conditions, with damage or healing emphasized and hit and critical thresholds beside it. **Damage breakdown** reveals critical amounts and variance; **Base ability costs** reveals the original cost parameters. Zero effective costs remain visible. **Your character** inherits calculated stats from the build's level, growth, bonus profile, equipment, and passives. **Target** uses the chosen monster's data and the pinned difficulty and mod rules; a self target uses your character's values. The cards show maximum HP, MP, and AP without asking you to enter them again.

Current HP, MP, and AP are separate optional assumptions under **Resources**. Leave them blank when the selected calculation does not need them. An affected unknown result offers an action such as **Set actor HP** or **Set target HP** that opens and focuses the relevant input. **Use full actor resources** and **Use full target resources** fill known maxima explicitly. Active statuses have their own disclosures. **Advanced conditions** holds elapsed actor and target turns, repeated actions, automatic battle-start statuses, prior status applications, and threat or charging conditions. These inputs never update recorded character observations. Builds, character plans, comparisons, backups, and read-only shares retain the scenario.

Resting calculations exclude active statuses. Merely carrying an automatic-status effect no longer makes every resting stat unknown. A scenario can include guaranteed automatic battle-start statuses; chance, elapsed duration, immunity, prior application, or unknown life state can make their presence uncertain. Selecting an active status explicitly supplies the snapshot assumption. A status's remaining count is not a multiplier on its stat effects. Older saved status selections stay separate until explicitly adopted into a scenario.

**Status impact** compares the full scenario with one selected actor or target status removed, including any selected aliases of that same resolved status identity. Other inputs stay fixed, including current resources, remaining statuses, turn counts, and automatic-status assumptions. A self target shares the actor's statuses, so removing an actor status can affect both sides of that calculation. Automatic effects can restore a removed status or leave its presence uncertain; the comparison reports that limitation instead of claiming an absent status. Missing inputs remain unknown, including a saved current resource amount that exceeds the maximum after removing a status. Each difference is specific to the remaining scenario and includes interactions and integer rounding; separate status differences are not additive and do not describe a fixed bonus.

The shared modifier evaluator applies source groups and native integer stages before using the effective values in costs and battle formulas. Unknown inputs affect the results that read them. For example, missing target HP can leave HP-dependent damage unknown while a fixed MP cost remains available. **Periodic and status effects** shows additional supported outcomes. **Formula reference** groups read-only coefficient, learning, and formula details. The separate **Base hit-chance calculator** lets you change target evasion to inspect that formula stage; it does not change the battle target or its calculated evasion. A target's difficulty comes from the exact Game Setup, not the independent Reference-page controls.

## Remaining calculation limits

A battle scenario is a numeric snapshot, not an encounter simulator. Hit, critical, and status chances are thresholds before Luck and failure protection. Damage and healing precede random variance rolls, survival effects, and resource clamping. Random status choices are conditional previews. Target legality, action scheduling, status lifecycle progression, reactions, and random history remain outside the preview. Unsupported tags, incomplete numeric records, unsupported editor formats, unavailable sources, unknown personal inputs, and unsupported platform/version choices remain explicit coverage gaps. A mathematical total does not prove equipment legality, ownership, learning, or a complete encounter outcome.
