# Account deletion and service cleanup

Delete account requires the exact `DELETE MY ACCOUNT` confirmation, a live customer session with CSRF protection, and authentication within the preceding ten minutes. The request atomically records a deletion journal, audit entry and independent revocation intent before blocking the account, revoking sessions/devices, stopping public shares, invalidating pending device payloads and linked email lineages, and terminalizing unfinished publication consumers. Accepted publication certificates are invalidated only after those consumers become terminal. A failed authority batch rolls all of this back.

The browser stores a separately generated random 32-byte deletion-status capability in tab-scoped session storage before submission. Requests send it only in `x-deletion-status`; neither URLs nor JSON bodies carry it. The service retains only its domain-separated digest in `deletion_status`, outside the account/auth recovery projection. `GET /api/v1/account/deletion` returns only an authored phase, pending/complete state and bounded diagnostic. It grants no session or account access. A lost request response can therefore be reconciled after session revocation. New requests also retain their original account context bound to that exact grant. An explicit retry requires the same account and exact confirmation, checks status first, and replays the same grant if no journal is found. A missing status does not prove an earlier request cannot still commit, so retry failures preserve the grant. Older capability-only grants remain readable but cannot be assigned a retry owner. Closing the tab can lose progress access but does not cancel deletion. Local encrypted copies, unsaved work and downloaded backups are not erased by this server lifecycle.

Service jobs claim a time-bounded lease against the exact captured phase, cursor and attempt. Each invocation advances bounded work and persists the outcome; interruption leaves the journal pending. Successful completion requires the deleting account's expected revision, actual storage fencing, independent ledger acknowledgment, removal of account-owned metadata and encrypted key envelopes, and zero account-owned logical liabilities. Metadata removal follows an authored dependency order and removes at most 100 rows per step. Existing storage fencing processes at most 32 object slots per generation step. No managed storage key is deleted, expired, reused or repopulated with plaintext.

Deletion replaces every issued managed ciphertext slot with its assigned content-free marker using the accepted storage fence. Marker bytes, digest and inequality with the original seed predicate are verified before releasing payload/seed charges. A delayed initializer cannot replace an existing marker; a delayed payload write retains its original seed ETag predicate. An unsafe fence stays pending with `INTEGRITY_FAILED`; ordinary retries cannot clear it. Account removal preserves the permanent marker and minimum opaque control row as global liabilities.

The independent ledger records an initial empty-liability account-deleted event, then separate frozen account-deleted intents for bounded groups of closed markers. Each association uses the accepted versioned ledger codec. An association is persisted before external writes; its exact immutable event, pages, index and head must verify before its D1 acknowledgment. Each marker belongs to a recorded group, and final transfer checks exact marker/key coverage. This composition admits arbitrarily many bounded groups within actual account/storage limits without imposing the ledger codec's per-association bound as an account quota. Partial, lost or failed ledger operations never produce a completed deletion receipt.

Stopped-share reconciliation consumes the exact pending event retained by the authorized Stop operation. It can finish the independent acknowledgment and guarded stopped pointer/receipt after that original customer session is revoked. Account deletion completes each pending authorized Stop from its original frozen event under the deletion job guard before advancing to account-wide revocation and removing the owned share records. This preserves recovery authority for partially written independent Stop events; an outage keeps deletion pending, and late identical writers converge on the same event. Operator and invitation revocation commands must supply their own later administrative authority; the service does not expose a temporary customer-to-admin bypass.

Ordinary cleanup uses the accepted generation, unfinished-publication, retained-pin and scan-lease predicates. Expiry alone cannot retire accepted history, original files, checkpoints or unresolved conflict closures. Staging becomes eligible at its original 24-hour deadline only when those predicates permit it. Cleanup remains available when account capacity is exhausted. Actual service-backup pins, copy jobs and closed restore promotion belong to the backup producer and must be composed into these predicates before backup capture is enabled.

Logical counters include the permanent managed marker bodies, their retained opaque metadata, and all new deletion/job/status/intent/audit records. Global metadata accounting uses the generated encoded JSON-tuple lengths; it is not a physical SQLite page estimate. Deletion releases outstanding descriptor reservations exactly once and does not waive charges because a lease expired. Revocation bookkeeping may proceed at capacity to preserve deletion safety; ordinary subsequent writes still face existing capacity admission. Independent ledger bucket object bodies are a separately measured retained resource, not included in this logical counter. Whole-provider storage, physical indexes, billing, hosted request limits and backup-copy admission require the deployment/recovery resource projection; these counters do not establish full provider-cap coverage.

A reproducible resource measurement is available by setting `CRYKIT_SYNC_MEASUREMENTS` to a private output file and running the Worker deletion test named `deletes more than one ledger association limit without capping owned objects`. Its synthetic workload reserves multiple full upload declarations, closes every admitted slot, completes deletion and records the actual remaining logical counters plus independently listed ledger object count/bytes. Each closed slot retains a 32-byte marker and an opaque control row; each liability group adds a frozen D1 intent and independent ledger records. Marker installation requires a PUT and exact verification GET per processed slot, plus guarded D1 release; interrupted retries may repeat these operations. Deletion is not net-zero service growth.

Service audit rows expire after 90 days through bounded cleanup. Application diagnostics retain only authored phases/codes, random correlation/job identifiers and useful timings. Hosted application-log retention of seven days and any non-identifying aggregate retention of 30 days remain deployment configuration duties; this feature adds no analytics or aggregate collection. Email preserves its accepted three-attempt maximum and distinguishes accepted-for-send from delivery. Account deletion removes retained email payloads and prevents future linked resends while preserving already-started accepted/uncertain attempt history.

A restored older database must remain closed until the complete independent ledger has been verified against its trusted minimum and applied. Any account-deleted event suppresses that account; all of its acknowledged liability associations must reconstruct surviving global marker obligations, including groups beyond a single association. Missing, partial, corrupt or regressed coverage must keep restore closed. The journal and ledger tests prove independent retained evidence and delayed live writers; they do not constitute a complete service backup/restore implementation, an original-secret restore rehearsal, or a physical all-object erasure deadline. Existing retained recovery copies follow their owning retention policy and cannot reactivate a deleted account.
