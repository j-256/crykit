# Build mechanics and native calculations

The Build editor checks equipment rules against the selected source definitions. New calculation plans use the inspected PC 1.6.9.0 formulas and numeric records from the [exportable calculation package](calculations.md). Model-less plans use the same native evaluator when their numeric inputs are supported. These checks work on unowned equipment and unlearned passives. Scenario validation separately checks recorded stock, learning, passive PP limits, class unlocks, and Game Setup applicability. Saving a plan never changes observed character stats, inventory, or learning.

## Equipment checks

Exported primary-class equipment categories provide permissions. The sub-command does not supply its class's equipment list. Supported permission descriptions such as Equip Sword and Equip All add categories. Explicit innate descriptions supply Dual Wield and Two-Handed; Shapeshift can inherit a documented sub-command innate. Custom Crystal Edit classes use their own exported fields and native passive references. A saved imported-layer configuration resolves those native references across its enabled layers through the effective catalog. Similarly named vanilla records do not establish missing identities.

Equipment categories map to main hand, off hand, head, body, and two accessory slots. The inspected PC executable fixes this layout; Game Setup displays it as a derived rule. Imported slot and requirement evidence remains available to party validation, with unresolved values shown explicitly.

A two-handed weapon reserves both hands even when selected in one hand with the other empty. If the same copy is displayed in both hand slots, use **Same copy as**; its stats and stock demand count once. Separate weapons require Dual Wield. A one-handed weapon can share both hand slots when Two-Handed is present. Known unique-equipment flags, duplicate passive selections, disabled class selections, and wrong equipment roles produce conflicts. Missing hand counts and unknown permission effects produce unresolved findings where they matter. Plans can still be saved with conflicts.

## Passive PP budget

Passives are stored as an ordered, variable-length list, not as Game Setup slots. Build pickers exclude a passive already selected in another row by its logical definition identity, while retaining the current selection. Older or imported duplicate selections remain saved and produce validation conflicts. Each passive contributes its documented PP cost to one total. The inspected PC executable permits up to 10 PP across all equipped passives, so new Game Setups use that limit. Game Setup does not offer an arbitrary PP override. Imported mods can change individual passive costs through their definitions. Unknown costs keep the total unresolved, and a known nonnegative subtotal over the limit proves the Build invalid even when another selected cost is unknown.

The Crystal Edit [equipment schema](https://github.com/iconmaster5326/CrystalProjector/blob/main/schema/json/equipment.yaml) identifies equipment type, two-handed occupancy, and unique-equipment fields. The [passive schema](https://github.com/iconmaster5326/CrystalProjector/blob/main/schema/json/passive.yaml) identifies PP and innate/learnable flags. The application prefers those properties from native game source records and retains older export records without changing old catalog snapshots.

## Game Setup and mod rules

Game Setup records the base game version, difficulty, and enabled mod revisions. Platform and game mode appear under base game details. Builds save their own setup with each checkpoint; changing a Playthrough does not retarget saved Builds or Teams. A mod title alone cannot establish calculation effects.

Fresh authoring starts with Normal difficulty, using the native difficulty identity 0. This is an editable planning default, not an observation of a tracked game. Existing or imported setups retain their selected, unknown, or unrecorded difficulty when copied, revised, or migrated. Difficulty-dependent estimates remain unresolved when the saved difficulty is unknown.

Supported Crystal Edit format 34 imports retain battle settings and difficulty definitions with the exact source revision. Enabled layers apply in order. A non-localization BattleConfig replaces the complete prior configuration; difficulty records replace matching identities. Incomplete or unsupported settings leave affected calculations unresolved. The resolver uses inspected PC 1.6.9 Standard, Vanilla, and Chaos difficulty data without asserting parity for other versions or platforms.

Supported gender records supply effective bonus flags and additional named profiles. Native innate overrides and cross-layer class references feed the same calculation. Exact native family and ID matches suggest reviewable replacement links when choosing sources. Versioned compositions retain historical projections. Composition version 3 allocates added identities per source project and rewrites supported native references before combining enabled records; older compositions require explicit upgrade before using those semantics. [Mod calculation coverage](mod-calculations.md) separates editable data, fixed engine rules, and battle-context limits.

Dual Wield, Two-Handed, and unarmed stat constants feed PC character calculations. The shared loadout sheet uses the same pinned rules for stat contributions and detailed totals in Builds, recorded character snapshots, and read-only share previews; newer mod revisions do not retarget those snapshots. Game Setup retains difficulty-dependent hit modifiers and enemy HP and stat multipliers with their source. The loadout's base physical hit curve excludes difficulty; the battle scenario's final hit stage uses the pinned difficulty where applicable. Enemy multipliers do not apply to player stats. Bestiary pages provide separate mode and difficulty previews. None of these surfaces simulates a complete encounter.

## Verified PC calculations

The **Loadout** tab and character current page share calculated totals, level and growth controls, neutral/male/female comparisons, recorded-total comparisons, and sample damage benchmarks. New plans assign every level to the primary class until an allocation is edited. Numeric steps, rounding, caps, native inputs, and source evidence are structured data that can be exported independently of planner data. See [calculation format, controls, compatibility and scope](calculations.md).

## Saved calculation inputs and previews

Enter level and growth history under **Loadout > Stats > Calculated stats**, and choose **Calculation gender** in the stats overview. **Checks & notes > Ability and hit-chance preview** selects a numeric ability record and target evasion. New Builds and edit drafts without saved calculation inputs start with a level-60 plan following the primary class; opening the editor does not change the saved checkpoint. Character sheets offer **Plan level-60 native calculations** explicitly, and read-only shares preserve absent plans. Missing levels, incomplete allocations, unknown character selections, and unsupported source records remain unknown. An unknown saved level is never filled in for display.

Model-less inputs follow the native PC evaluator without modifying the saved checkpoint. Retained legacy active statuses and custom per-stat bonuses remain explicit unsupported resting-sheet assumptions. A separate adoption action copies legacy statuses into a versioned battle scenario; adding a scenario alone does not silently reinterpret them. The editor preserves recorded levels, observed totals, historical snapshots and unrelated imported data. Community descriptions remain reference facts and are never parsed into numeric formulas.

Growth uses the native class ratings, per-stat gender flags, intermediate integer truncation and final rounding. The shared character calculation applies native flat and percentage order, derived statistics, weapon modifiers, and resource caps. Build overviews, comparisons, character sheets and read-only shares use that same evaluator. Unknown gender displays an explicitly labeled no-bonus preview with separate male and female comparisons; it does not infer gender from appearance.

The ability preview calculates the **native power coefficient before battle effects** from the selected calculated stats, including enabled scenario stat modifiers. It uses the native base and scaling coefficients, including null inheritance versus explicit zero and separate nested truncation for each core-stat term. Negative power represents healing. Resource-based power and contextual ability modifiers, defense, crits, variance, targeting and conditional effects are excluded from this stage. It is not full battle damage or a claim that the ability is learned or usable. Base costs remain labeled as native HP-percent, MP/AP, CT and cooldown parameters. The separate effective-cost panel applies enabled source modifiers and shows the actual calculated HP amount paid, effective MP/AP costs, CT delay, and cooldown. LP cost preserves fractional values as the native learn tree does; affordability uses exact JP. The whole-LP equivalent describes sufficient whole units without rounding the stored cost.

The physical hit preview calculates only the native accuracy/evasion curve. It preserves single-precision interpolation and integer truncation across the complete curve, including endpoints and zero evasion. Zero target evasion produces 100% at this stage. Ability accuracy, hit modifiers, guaranteed overrides, difficulty, Luck and miss protection require battle context and are excluded. The curve is not the selected ability's final hit chance. Add a battle scenario for the ability-specific hit stage with effective actor and target stats, source modifiers, overrides, and difficulty; its output is labeled before Luck.

## Battle scenario scope

**Add battle scenario** enables saved planning inputs for elapsed actor and target turns, active statuses, automatic battle-start effects, current resources, a monster or self recipient, recipient statuses, repeated actions, threat relationships, and prior status applications. The same snapshot feeds effective stats, costs, target-aware damage or healing, critical amounts, hit and critical chances before Luck, variance amounts, periodic HP/MP/AP effects, and status chances and durations. Equipment, passive, and status modifiers preserve the native source-group ordering and integer truncation. An unavailable modifier input leaves only the affected calculation and its dependents unresolved.

Resting sheets exclude automatic statuses without hiding the ordinary loadout totals. In a battle scenario, the calculator checks applicable chance, life state, immunity, and duration conditions. Random or uncertain status presence requires explicit active-status selection. Missing resources or threat relationships remain unknown and are required only when a formula reads them.

## Remaining limits

The interface calculates a selected battle snapshot and named native preview stages. It does not schedule actions or reactions, roll random outcomes, simulate complete status lifecycles, apply runtime resource payments or survival effects, or prove an action is legal. On-application and removal events require an explicit snapshot reflecting their resulting state. Numeric imports use supported Crystal Edit records; incomplete or unsupported records remain unresolved. A known unsupported platform or game version blocks calculations, and named mods without numeric rules cannot establish their effects. The PC 1.6.9.0 package uses the [verified shared Windows/macOS gameplay baseline](platform-coverage.md); Nintendo Switch and other unreviewed platforms retain their own evidence boundaries.

The [PC steal mechanics research](steal-mechanics.md) records availability, success, Luck, failure protection, multi-entry display, and guaranteed-attempt mod formulas. The exportable combat module supplies steal arithmetic for explicit inputs; the planner has no interactive steal-outcome simulation. Both retain the inspected PC scope without establishing Nintendo Switch parity.

PC calculations use the pinned Game Setup's recognized Standard, Vanilla, or Chaos mode. The calculation panel shows that choice without a second mode selector. When Game Setup mode is unknown, a retained calculation mode or the standard model is shown as an explicit calculation assumption; difficulty-dependent estimates remain unresolved.
