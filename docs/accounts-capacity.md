# Account capacity and operating limits

The default allowance for newly verified accounts is 512 MiB (`536870912` bytes), bounded by the owner and deployment ceilings. Changing this default does not resize existing accounts or remove their data. The isolated preview deployment ceiling is 64 GiB (`68719476736` bytes), including staged and retained account data and counted backup usage. This permits 100 full account allowances plus 14 GiB of shared headroom; it is not a guarantee that every backup or concurrent temporary copy will fit. The ceiling does not reserve provider storage in advance. Local fixtures retain their independent 2 GiB ceiling. Warn at 80 percent. Account logical usage is not physical provider usage. Quota, pauses or a reduced ceiling preserve protected data and guest/local editing; never silently evict originals, drafts, conflicts or history to create space.

Owner settings may lower the account/project allowance within the deployment ceiling. Increasing the deployment ceiling does not overwrite a lower persisted owner ceiling. Live transactions recheck the owner ceiling; closed staged restore uses the deployment ceiling and reopening also checks the restored owner ceiling after retained original liabilities. Reserved bytes, metadata, unfinished uploads, backup temporary work, snapshots and permanent marker/control liabilities all compete for headroom. The independent revocation ledger's physical growth must be budgeted separately. The shared application ceiling is not a provider billing or hard spend cap.

In the owner admin panel, each service Pause or Resume button opens a server preview for that setting and requires the configured Access confirmation before applying. Capacity edits remain a separate draft until previewed; canceling a service review leaves that draft intact. Capacity fields accept nonnegative decimals in Bytes, KiB, MiB and GiB, rounding fractional conversions up to a whole byte: 2.5 KiB is 2,560 bytes and 2.6 KiB becomes 2,663 bytes. The rounded value must fit the field's minimum, deployment capacity and safe-integer limit. Stored metadata and reserved metadata already count toward accounted storage; the panel's figures are application accounting, not physical provider usage.

## D1, Worker and R2

Official documentation checked on 2026-10-15 describes [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [Worker limits](https://developers.cloudflare.com/workers/platform/limits/) and [R2 pricing](https://developers.cloudflare.com/r2/pricing/). Recheck these at deployment, including aggregate usage by unrelated services.

| Resource | Documented boundary and implication |
| --- | --- |
| D1 queries per Worker invocation | Free 50, Paid 1,000; supported maximum sync calls can exceed Free, so the full protocol requires Paid |
| D1 database size | Free 500 MB per database, Paid 10 GB; application byte quotas do not bound SQLite pages/indexes |
| D1 query/batch shape | 100 bindings, 100 KB SQL, 2 MB row/string/blob, 30-second query/batch duration; consistent capture must fit its one guarded batch |
| D1 Free daily rows | 5 million read and 100,000 written; retries, triggers, indexes, capture and maintenance consume shared allowances; exceeding daily limits interrupts D1 operations |
| Worker CPU and memory | Free HTTP CPU 10 ms; 128 MB per isolate; local wall time is not hosted CPU or heap proof |
| R2 Standard Free allowance | 10 GB-month storage, 1 million Class A and 10 million Class B operations per month; Standard overage is $0.015/GB-month, $4.50/million A and $0.36/million B |

Paid is justified by the supported transaction shapes and arbitrary-recipient email, not by assuming every operation exceeds Free. Guest assets-only use remains the supported Free-compatible mode. Smaller sync batches alone do not establish complete Free compatibility. No separate smaller account protocol is claimed here. An existing Workers Paid subscription is not proof of other product entitlement, sufficient headroom or a verified runtime bound.

Reproduce local sync measurements using `CRYKIT_SYNC_MEASUREMENTS` and the commands in [sync storage](account-sync-storage.md#deployment-limits-and-reproducible-measurements). The earlier dense-input fixture measured roughly 760 sync statements, 98,000 rows read and 48,000 rows written in its final guarded batch. Those are historical local measurements of that request shape, not the final composed application's hosted ceiling. Accepted closure certificates, per-preparation empty-page sharing and bounded local reads change the cost shape; final composition must measure their actual emitted implementation. Include middleware, triggers, failure classification, retries and abandoned work rather than counting only successful helper calls.

Measure the actual pinned OPAQUE start/finish CPU, peak memory, request duration and concurrent load on the deployed Worker. Browser password work is separate. No admitted hosted OPAQUE CPU number is established by the local packaging proof or this runbook. Keep account activation conditional on the actual deployment result. Record exact build identity, workload dimensions, observed versus projected values, safe phase timings and partial failures. Do not raise warning thresholds or verification deadlines to hide a limit.

Physical storage estimates must include D1 pages/indexes, encrypted payloads, metadata, 24-hour staging, retained originals/history, snapshots, temporary capture/restore copies, frozen original resources and the independent ledger. A projection for a daily unique changed ciphertext volume `C` retained for `D` days is at most `C * D` added backup payload before deduplication savings, plus manifests, metadata, seeds, markers and temporary reservations. This is a planning estimate, not a measured compression ratio or retention promise. Each closed managed key retains a 32-byte marker plus control metadata indefinitely; fence cleanup costs at least one PUT and one verification GET per key before retries and D1 work. Keys must never be expired to reduce these costs.

Recovery admission uses the exact measured policy in [service recovery](accounts-recovery.md#capture-authority-and-lifetime). No policy means paused capture. Daily capture and up-to-30-day retention remain targets, not a runtime SLA. Keep last verified points when capture degrades, show their actual age and support independent private backup. Do not turn customer quotas into guessed capture ceilings or split the atomic capture into unsafe partial snapshots.

## Email and Access

[Email Service pricing](https://developers.cloudflare.com/email-service/platform/pricing/) and [limits](https://developers.cloudflare.com/email-service/platform/limits/), checked on 2026-10-15, require Workers Paid for arbitrary recipients. The account-wide allowance is 3,000 accepted emails per billing month, then $0.35 per 1,000. Accepted hard bounces consume allowance; boundary rejections and suppressed recipients do not. Verified destinations are a Free-compatible restricted-testing option and do not consume those sending quotas; they do not support general public signup.

Projected accepted-message demand is `signups + 2 * emailChanges + invitations + deliberateResends + otherAccountServices`. For example, 1,000 signups, 500 email changes and 100 invitations project 2,100 messages before resends and other services. Automatic attempts are capped at three per job; attempt count is not an accepted-message counter. An accepted native `messageId` is not a delivery receipt. Preserve uncertain outcomes without automatic resend.

The real daily limit depends on account reputation and is not a fixed documented starter allowance. It and shared daily/monthly headroom remain unknown until supported account inspection. Keep `EMAIL_HEADROOM=unknown` until reviewed. Verify [sender restrictions](https://developers.cloudflare.com/email-service/configuration/send-bindings/), [suppression reporting](https://developers.cloudflare.com/email-service/concepts/suppressions/) and [stored message preview](https://developers.cloudflare.com/email-service/observability/logs/#message-preview). Sending-domain `preview_enabled=false` is required because mail carries capabilities; Workers preview URLs are unrelated. Native entitlement, authenticated sender configuration, suppressed/bounced reporting and actual recipient-authorized acceptance/delivery are distinct evidence.

Cloudflare Access seats and independent MFA are a separate product check. Verify remaining seats in the actual Zero Trust plan and entitlement for [independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/) and [application MFA requirements](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/mfa-requirements/), documentation checked on 2026-10-15. The public Free offering's seat allowance is not proof of this account's remaining seats or a supported confirmation policy. Preserve `confirmationEnabled:false` until the hosted configuration proves the separate audience, short lifetime and independent MFA on every login, including AMR/session caching behavior. Unsupported policy leaves high-impact operations disabled.

## Observation and response

Monitor logical account/project usage at 80 percent, physical D1/R2 growth, staging age, permanent markers, unsafe fences, capture pauses/age, independent-ledger acknowledgment lag, job backlog, email attempts/uncertainty/suppression and shared sending headroom. Retain application logs seven days, non-identifying summaries 30 days and audit 90 days, and verify provider/export retention. Do not log addresses, private names, keys, capability URLs or imported content. Use authored operation/stage/code, request/job/mutation IDs and durations.

[Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/), checked on 2026-10-16, provides three-day retention and 200,000 events per day on Free, versus seven-day retention and 20 million included events per month on Paid with $0.60 per additional million. The seven-day application-log policy therefore requires Paid with this native log configuration; Free's shorter retention does not meet that policy. The supported Free fallback remains guest assets-only use. Disable persisted producer logs because Cloudflare also enriches custom console logs with request URLs. The existing private Tail consumer retains only validated diagnostic samples, using an approximate native gate per authored diagnostic key per minute per location; automatic invocation logs remain disabled on that helper. This is sampled evidence rather than complete request accounting. A reproducible volume estimate is `requests * mean_authored_events_per_request`; transaction and continuation events must be included in that mean. Hosted event volume has not been measured, and other Workers share account allowances. Inspect actual ingestion and retention before claiming coverage. Reverify pricing for deployments on or after 2026-12-01, when Cloudflare documents a transition to [Observability pricing](https://developers.cloudflare.com/observability/pricing/).

At capacity, stop new allocations through the guarded policy and keep reads, safe cleanup and local editing available. Review one exact eligible envelope cleanup candidate at a time; snapshots, incoming dependencies and unfinished work still block it. A fresh device cannot promise complete discovery. Restore remains closed if retained original plus staged liabilities do not fit. Diagnose a failed fence without releasing its reservation. Cost alarms and application gates reduce risk; neither is an undocumented provider hard spend limit.

Storage admission does not bound request costs. Native Worker admission rejects excessive network, authentication and location traffic before any recovery or session query reaches D1. An authenticated account also has a native budget shared across its networks and checked before session renewal. Existing D1 authentication and public-share limits retain their independent authority checks. Native bindings are required when accounts are active; missing bindings fail closed while guest assets remain available.

| Admission control | Initial allowance | Scope |
| --- | --- | --- |
| Native network requests | 12,000 per minute | Network and Cloudflare location |
| Native authenticated requests | 7,200 per minute | Account and Cloudflare location |
| Native credential-operation requests | 60 per minute | Network and Cloudflare location |
| Native aggregate requests | 24,000 per minute | Cloudflare location |
| Durable daily cloud admission | 500,000 attempts | Service, UTC day |
| Durable monthly cloud admission | 5,000,000 attempts | Service, UTC calendar month |
| Durable daily expensive work | 2,000,000 admission units | Service, UTC day |
| Durable monthly expensive work | 3,000,000 admission units | Service, UTC calendar month |

Synthetic three-device conflict recovery measured approximately 3,700 requests in a rolling minute on 2026-10-20, including exact original retention and publication. The account allowance provides approximately twice that measured burst. Network and aggregate allowances accommodate overlapping clients; these measurements do not establish capacity for every shared network or workload.

[Native rate limits](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), checked on 2026-10-19, are permissive and eventually consistent within each Cloudflare location. They shed load rather than provide exact accounting. Device-approval status polling retains its dedicated D1 budgets instead of spending credential-operation admission; it still passes native network/location and durable service admission. The daily and monthly service allowances use one guarded D1 transaction with the recovery-open check, without a preceding read or a separate recovery round trip. Both windows reserve an attempt before route work, including rejected requests and retries. Readiness requests and scheduled maintenance invocations count too. Fixed operational rows reuse the existing counter format and survive ordinary Worker restarts. Counters restored from a recovery point are not an independent billing ledger; inspect provider usage before reopening a restored service.

`CLOUD_DAILY_REQUEST_BUDGET` and `CLOUD_MONTHLY_REQUEST_BUDGET` may override the request defaults with positive safe integers. `CLOUD_DAILY_WORK_BUDGET` and `CLOUD_MONTHLY_WORK_BUDGET` independently bound expensive customer mutations: upload reservation costs one unit plus its declared chunks, chunk PUT costs two, upload finish costs one, and explicit cleanup costs 128. Commit costs 128 plus its declared parent, dependency, chunk, proposed-head and expected-head references. Authenticate the customer and validate the command shape before reserving work, then reserve both windows atomically before mutation. Failed attempts and retries retain their charge. These coarse weights distinguish SQL-heavy mutations from reads; they are not measured billing units. Transitive closure and database triggers can vary independently of declared command size. Work reservation adds one guarded D1 batch on these mutation routes. Ordinary admission also checks work saturation without allocating empty work counters. A mutation that cannot fit its remaining work allowance pauses before changing data.

Exhausting a request or work window returns `SERVICE_PAUSED` with its remaining retry interval. Customer cloud operations pause before route work; guest editing, local originals/outboxes and owner administration remain available. Scheduled email and cleanup pause before leasing jobs, retaining their original identity and state for a later eligible invocation. Existing job expiry and authority checks still apply; pausing never extends a capability's lifetime. Native rejection returns `RATE_LIMITED`. Account and sharing clients recognize non-CryKit edge rejection bodies, and sync preserves their retry floor. Admission rejections produce bounded per-isolate diagnostic summaries instead of one authored log event per rejected request; these summaries are not an exact global traffic counter.

These are admission allowances, not dollar budgets or caps on D1 rows, R2 operations, CPU, logs or shared account spend. Each admitted request can perform several billable operations, and initial Worker invocations remain billable even when admission rejects them. Measure those operations and their physical usage alongside these controls. Inspect effective edge rules for every exposed CryKit hostname, including earlier skip rules, rather than assuming a zone-wide rule protects each product. A combined rule shares its configured counting characteristics across matching host branches; a host condition alone does not create an independent per-host counter. Preserve other products' protection when changing shared rules.

Client notices distinguish traffic protection from a service usage pause and expose safe retry/contact details. [Owner alerts](accounts-deployment.md#rate-limit-notices-and-owner-alerts) use an independent Tail Worker and globally reserved notification allowances, preserving the customer admission path and keeping notifications possible during a cloud pause. Their email, Tail CPU and Durable Object usage must be included in physical cost measurement. A notification cap is not a cap on rejected requests or provider charges.

The Tail handler emits one additional authored acknowledgment per accepted owner alert, with no added record for grouped notices. The existing separate reserved daily allowances permit at most ten such acknowledgments per environment per UTC day under the notification policy, or 310 across a 31-day month. This is an upper estimate for the added authored events, separate from other diagnostics, provider duplication and shared account traffic. The existing Durable Object delivery receipt can describe the same send, so correlate both by support reference instead of counting log records as emails. Reading and validating the existing notification reply adds no email attempt, Durable Object request or database write.

[Workers CPU limits](https://developers.cloudflare.com/workers/wrangler/configuration/#limits) bound CPU per invocation, not monthly spending. [Budget alerts](https://developers.cloudflare.com/changelog/post/2026-06-15-budget-alerts-default-on/), checked on 2026-10-19, are informational and process the prior day's usage once per day. They do not stop traffic or provide an immediate spending cutoff. Treat edge admission, authenticated request budgets, measured CPU limits and billing alerts as separate controls; do not represent a storage quota or an alert as complete protection from billable abuse.
